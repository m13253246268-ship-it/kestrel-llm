# Ciphertext-chain relay tools (lay / boot)

These scripts cover the **"run a layer → hand off → review"** cycle of an RNS-CKKS ciphertext inference chain:
they execute `lay` (in-layer forward pass) + `boot` (bootstrap refresh) layer by layer, pack the result for the
next runner, and let a third party verify it **without trusting the packer**.

Driver sources live in [`../drivers/`](../drivers/) (`t23_m3p.c` / `t23_chain.c`); engine sources live in `src/core/`.

## 0. Prerequisites

| Item | Notes |
|---|---|
| gcc | C11 + OpenMP (MinGW-W64 or Linux gcc); only `libc + libm` |
| PowerShell | PowerShell 5.1 or newer on Windows |
| Data package | **The repository ships no data** (~7 GB). The engine hard-codes its data paths to `.tmp_tok/`, so you must generate them yourself — see [`../preproc/README.md`](../preproc/README.md) |
| Working directory | **All scripts run from the repository root** (each script locates the repo root itself, so you never need to `cd`) |

Once the data is in place, `.tmp_tok/` must contain at least: `chain/sk.bin`, your hop's input ciphertext
`chain/u{L-1}r112_{t}_{h}.ct`, `tail/w{L}/`, `tail/l{L}_*.bin` and `tail/scale{L}.bin`.
A single missing file aborts at the loading stage.

> **Create the directories first**: `New-Item -ItemType Directory -Force .tmp_tok, .tmp_tok\chain`.
> The drivers write with a bare `fopen` and **never create directories**: a missing `.tmp_tok/chain/` gives
> `[FAIL] ct save` / `[FAIL] sk save`, and a missing `.tmp_tok/` makes gcc's `-o` fail with
> `cannot open output file`. `rerun5_lay_boot.ps1` prepares both of these (plus `relay_rerun/`) itself;
> for the other scripts you must ensure them.

> `chain/sk.bin` can be generated by the driver itself: after creating `.tmp_tok/chain/`, run `t23lay` once
> with `T23_PHASE=l0 T23_KEYONLY=1`, and it prints `KEYONLY: sk.bin saved`.

## 1. Tool overview

| Tool | Purpose | Key parameters | Main outputs |
|---|---|---|---|
| [rerun5_lay_boot.ps1](rerun5_lay_boot.ps1) | **Run layers**: `lay` + `boot` hop by hop; skips hops whose outputs already exist (resumable) | `-From -To -LayExe -BootExe -LogDir` | `.tmp_tok/chain/*.ct`, `.tmp_tok/relay_rerun/{lay,boot}*.out`, `timing.tsv` |
| [verify_layer.ps1](verify_layer.ps1) | **Accuracy check**: decrypt → decode → `max\|err\|` against the plaintext reference (independent of the driver's PASS criterion) | `-From -To -Mode lay\|boot -Tol` | `PASS/FAIL` + `max\|err\|`; exit code = number of failed layers |
| [layver_run.ps1](layver_run.ps1) | **Numeric equivalence**: swap only the input ciphertext, keep the thread count, and see whether the next layer's `max\|err\|` still passes | `-TargetLayer -AltDir -BaselineLog` | `.tmp_tok/relay_state/layver_result.txt` |
| [collect_results.ps1](collect_results.ps1) | **Archive**: collect a layer range's ciphertexts / logs / metadata and generate `manifest.sha256` | `-From -To -LogDir -Dest` | `<Dest>/chain`, `<Dest>/logs`, `manifest.sha256` |
| [pack_relay.ps1](pack_relay.ps1) | **Pack**: bundle a layer range into an uploadable zip handoff | `-From -To -Id [-NoKey]` | `.tmp_tok/relay_out/relay_L{a}-{b}_{id}_{timestamp}.zip` |
| [verify_relay.ps1](verify_relay.ps1) | **Verify a package**: check integrity + criteria + structure of a zip | `-Zip [-Keep]` | console detail; exit code = number of failed checks |
| [watch_relay.ps1](watch_relay.ps1) | **Unattended duty**: snapshot state every 15 minutes, start the run automatically once the criterion passes, then archive + verify at the end | `-From -To -IntervalSec -RefDir` | tick log and acceptance summary under `.tmp_tok/relay_state/` |
| [_monitor.ps1](_monitor.ps1) | Background progress monitor (auxiliary) | none | `.tmp_tok/relay_rerun/_status.txt` (refreshed every minute) |
| [fix_crlf.sh](fix_crlf.sh) | Normalise `CRLF` to `LF` in a code tree (for `.sh` files that fail to execute after a cross-platform export) | `[directory]` (defaults to the repo root) | text files only; `.git/` is never touched |

The three binaries are built automatically by the scripts when missing, or can be built by hand:
`t23lay` (np=112), `t23boot` (np=2100), `verify_layer` (np=112) — defaulting to `.tmp_tok/`.

## 2. Manual build (optional — the scripts do this when a binary is missing)

```bash
# lay (in-layer forward, 112 primes)
gcc -O2 -fopenmp -Wno-implicit-function-declaration \
    -I include -I include/core -I include/common \
    -DCKKS_N=2048 -DCKKS_NPRIMES=112 -DBB=32 -DGG=32 \
    src/core/vllm_ntt.c src/core/vllm_ckks.c src/core/vllm_tp.c \
    tools/drivers/t23_m3p.c -o .tmp_tok/t23lay -lm

# boot (bootstrap refresh, 2100 primes; large stack required)
gcc -O2 -fopenmp -Wno-implicit-function-declaration '-Wl,--stack,33554432' \
    -I include -I include/core -I include/common \
    -DCKKS_N=2048 -DCKKS_NPRIMES=2100 -DBB=32 -DGG=32 \
    src/core/vllm_ntt.c src/core/vllm_ckks.c src/core/vllm_tp.c \
    tools/drivers/t23_chain.c -o .tmp_tok/t23boot -lm

# verify_layer (independent review; 112 primes is enough)
gcc -O2 -fopenmp -Wno-implicit-function-declaration \
    -I include -I include/core -I include/common \
    -DCKKS_N=2048 -DCKKS_NPRIMES=112 -DBB=32 -DGG=32 \
    src/core/vllm_ntt.c src/core/vllm_ckks.c src/core/vllm_tp.c \
    tools/relay/verify_layer.c -o .tmp_tok/verify_layer -lm
```

Build-time traps:

1. `-I` must include `include`, `include/core` **and** `include/common` (`vllm_tp.c` depends on `common/vllm_platform.h`).
2. Under PowerShell the **comma inside `-Wl,--stack,33554432` is treated as an argument separator** → quote the whole flag.
3. `boot` uses np=2100 and overflows MinGW's default stack (`0xC00000FD`) → the bigger stack is mandatory.
4. A `.ps1` containing Chinese comments must be saved as **UTF-8 with BOM**; otherwise PowerShell 5.1 reads it as ANSI and reports "unexpected token }".

## 3. Typical workflows

**Relay runner (run a few layers and submit)**

```powershell
# 1) Confirm the input is in place: chain\u{L-1}r112_*.ct and tail\w{L}\
# 2) Run the layers (T23_NT defaults to 4 when unset)
$env:T23_NT = "4"
powershell -NoProfile -ExecutionPolicy Bypass -File tools\relay\rerun5_lay_boot.ps1 -From 5 -To 7
# 3) Self-check accuracy (optional; needs the plaintext references from the data package)
powershell -NoProfile -ExecutionPolicy Bypass -File tools\relay\verify_layer.ps1 -From 5 -To 7
# 4) Pack and submit
powershell -NoProfile -ExecutionPolicy Bypass -File tools\relay\pack_relay.ps1 -From 5 -To 7 -Id yourname
```

**Verifier (review a received package)**

```powershell
# 1) First check the zip's own SHA256 (the value published by the packer)
Get-FileHash .tmp_tok\relay_out\relay_L5-7_yourname_<timestamp>.zip -Algorithm SHA256
# 2) Per-file bytes + criteria + structure inside the package
powershell -NoProfile -ExecutionPolicy Bypass -File tools\relay\verify_relay.ps1 -Zip <package path>
# 3) With the data package you can go further and judge "are the numbers right?"
powershell -NoProfile -ExecutionPolicy Bypass -File tools\relay\verify_layer.ps1 -From 5 -To 7
```

**Reproducer (run L0–4 from the seed)**

```powershell
# Prerequisite: back up and clear chain\'s *.ct (keep sk.bin)
powershell -NoProfile -ExecutionPolicy Bypass -File tools\relay\rerun5_lay_boot.ps1 -From 0 -To 4
powershell -NoProfile -ExecutionPolicy Bypass -File tools\relay\verify_layer.ps1 -From 0 -To 4
```

## 4. Judging criteria (the easiest place to misjudge)

Once running, the log shows `PASS` and a large number of `FAIL` lines at the same time. **This is not a contradiction**:

- **Only the layer-output criterion counts**: for `lay`, `RESULT=PASS` at the end of the log; for `boot`,
  `BOOT=PASS` plus 8 occurrences of `out np=2083` in that layer (4 tokens × 2 components, showing the chain
  really was refreshed to full).
- **Stage-level `max|err| FAIL` lines in groups A/B/C/D are not the criterion**: they compare against a
  plaintext reference from a *non-drifting* input, whereas a real ciphertext chain necessarily carries drift
  from the previous layer. Normalization pulls the magnitude back, which is why the final stage carries the
  `[E2E:ref-deviate-ok]` marker.

  **Why "a stage FAILs while the final verdict is PASS" is not a contradiction** (per the E2E-mode
  comment in `t23_m3p.c` and the planning script `_cfold_plan.py`):

  | Step | Explanation |
  |---|---|
  | Why the stage FAILs | L26/27 use a **real C-fold** (`g_causal` + real C folding); the intermediate `C/D/U2` values deviating from the true values is **expected**, not a defect |
  | Magnitude of the expected deviation | Pre-quantified by the planning script: `\|Δao\| ~ 1.4 / 0.8` — the same order as the observed `[C:attn] 8.5~12` and `[D:o] 14~29` |
  | Why the final verdict is still PASS | The same plan defines the **normalized criterion**: `E2E logits drift 0.14 < margin 2.03` — the internal deviation shrinks to 0.14 at the logits, while the top1 decision margin is 2.03 |
  | Where acceptance moves to | In this mode `C/D/U2` are **report-only (not counted in `fails`)**; acceptance is transferred to the **E2E logits gate** |

  **One line**: a stage FAIL is a difference in an intermediate quantity's *convention* (expected and
  pre-quantified); the final PASS is the *end-to-end logits-gate verdict* — they are not the same
  ruler, and reading them together creates an illusion of self-contradiction.

  **Note: the `fin` gate is a different one from the above.** `C/D/U2` are controlled by `T23_E2EMODE` (without that variable they count into `fails`), whereas the `[F:xnorm]` / `[F:top1]` checks in `fin` (phase 5) pass a **hard-coded `&rf`** — they never count into `fails`, whether or not `T23_E2EMODE` is set. **Do not read the two gates as one.**

  Authority: in the driver source `tools/drivers/t23_m3p.c`, the two `fin` checks pass `&rf` (around lines 1533-1535), while `C/D/U2` pass `e2e ? &rf : &fails` (e.g. around lines 1908, 1973, 2146, 2161); a `[F:top1]` mismatch also only does `rf++` (around line 1589).

## 5. Boundaries (stated honestly)

- **`BOOT=PASS` ≠ numerically correct**: it only means `load / refresh / save` did not fail. To judge the
  numbers you must additionally run `verify_layer.ps1` (or `layver_run.ps1`).
- **`lay`'s `RESULT=PASS` is not proof of correct numbers either**: the relay script sets `T23_E2EMODE=1`, which
  downgrades `C/D/U2` deviations to "reported only" — so **taking the wrong SiLU path (`.tmp_tok/tail/silu{L}.bin`
  missing → shallow layers wrongly use the ÷21 fold) still prints PASS** (measured on layer 0: `max|err|`
  4.2e-2–8.5e-2, `verify_layer` FAILS, while the driver reports `RESULT=PASS (0)`).
  Together these two mean: **criterion logs are for debugging only; acceptance must read `verify_layer`'s `max|err|`.**
- **`verify_relay.ps1` cannot prove "the computation is right"**: it proves the package was not tampered with,
  truncated or padded with extra files; the criterion logs are theoretically forgeable. The only defence
  against forgery is **cross-recomputation**: the flow is deterministic, so two people independently rerunning
  the same layer should get byte-identical output.
- **The thread count is a result variable**: that is exactly why `layver_run.ps1` exists — when a different
  input or a different thread count produces different bytes, equivalence must be judged by `max|err|`, not by
  byte equality.
- **`layver_run.ps1` requires `-TargetLayer >= 1`**: `lay0` takes the plaintext-encryption branch and reads no
  ciphertext from the chain, so injecting an alternative `u0r112` and running `lay0` compares nothing at all.
