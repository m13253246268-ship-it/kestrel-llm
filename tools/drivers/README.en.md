# Layer-chain drivers (lay / boot / fin)

These two C files are the **layer drivers for the FHE ciphertext inference chain**, used together with the
RNS-CKKS engine in `src/core/` (`vllm_ntt.c` / `vllm_ckks.c` / `vllm_tp.c`).
They are **not part of the inference engine proper** (`vllm_shs`); they exist to run **homomorphic-encryption
tests / community relay**.

## 0. Can you actually run it?

| Step | What you need | Status |
|---|---|---|
| **Build** (§4) | Just `gcc` (with `-fopenmp`, `pthread`) | ✅ doable inside the repo |
| **Run** (§5) | **~7 GB data package** (`sk.bin` + `tail/w{L}/` weights + `tail/l{L}_*` plaintext references) | ⚠️ **the repo ships no data**; generate it yourself — see [`../preproc/README.md`](../preproc/README.md) |

> Measured (2026-09): both §4 commands build successfully as written; running the binary in a directory
> **without the data package** exits with `sk load fail`. So "builds fine, needs data before it runs"
> is expected behaviour, not a broken environment.

Three easy traps:

1. **Do not pass a CJK absolute path to `-o`** (Windows/MinGW): `-o D:\中文路径\x.exe` fails with
   `cannot open output file ...: No such file or directory`; use a relative ASCII name (`-o t23lay`).
2. **`lay0`'s "plaintext seed" is three files**: `chain/sk.bin` (can be generated with
   `T23_KEYONLY=1`) + `tail/l0_u1.bin` (input reference) + `tail/w0/` (weights). Check these first when
   debugging.
3. **`fin` cannot run on its own**: it reads `u27r112`, so the whole chain must be finished first
   (lay0 → boot0 → … → lay27 → boot27).

## 1. What they are

| File | Role | Phases |
|---|---|---|
| `t23_m3p.c` | `lay` (intra-layer forward) + `fin` (final logits) | `T23_PHASE=lay` / `fin` |
| `t23_chain.c` | `boot` (bootstrapping refresh, noise-budget reset) | `T23_PHASE=boot` |

## 2. Chain protocol (two hops per layer)

```
lay{L}  : u{L-1}r112  -->  u{L}        criterion RESULT=PASS
boot{L} : u{L}        -->  u{L}r112    criterion BOOT=PASS (out np=2083)
fin     : u27r112     -->  logits      compared against tail/logits.bin (top1)
```

Each hop dumps **8 ciphertexts** (4 tokens × 2 ciphertext components), named `{prefix}_{t}_{h}.ct`
with `t=0..3`, `h=0..1`.
Layers are 0-based: `lay0` starts from the plaintext seed; `lay1` reads `u0r112`, and so on.

## 3. Data-directory convention (important)

Data paths inside the drivers are **hard-coded to `.tmp_tok/`**. Prepare it under your working directory:

```
<working-dir>/.tmp_tok/
├── chain/   sk.bin, u{L}_{t}_{h}.ct, u{L}r112_{t}_{h}.ct
├── tail/    w{L}/ per-layer weights, l{L}_*.bin plaintext references,
│            logits.bin, embed.bin, xnorm_f.bin, ...
└── l0/ l1w/ l1r/   layer0 / layer1 dedicated weights and references
```

The data package is ~7 GB (weights + plaintext references + secret key) and must be generated by
yourself: see [`../preproc/README.md`](../preproc/README.md) (sizes, formats, generation order and
verification are all documented there).
`chain/sk.bin` can be generated by the driver itself:
`T23_PHASE=l0 T23_KEYONLY=1 ./t23lay` (it prints `KEYONLY: sk.bin saved`).

## 4. Build

```bash
# lay / fin  (chain of 112 60-bit primes)
gcc -O2 -fopenmp -Wno-implicit-function-declaration \
    -I include -I include/core -I include/common \
    -DCKKS_N=2048 -DCKKS_NPRIMES=112 -DBB=32 -DGG=32 \
    src/core/vllm_ntt.c src/core/vllm_ckks.c src/core/vllm_tp.c \
    tools/drivers/t23_m3p.c -o t23lay -lm

# boot  (2100 primes; a big stack is mandatory, otherwise 0xC00000FD on MinGW)
gcc -O2 -fopenmp -Wno-implicit-function-declaration '-Wl,--stack,33554432' \
    -I include -I include/core -I include/common \
    -DCKKS_N=2048 -DCKKS_NPRIMES=2100 -DBB=32 -DGG=32 \
    src/core/vllm_ntt.c src/core/vllm_ckks.c src/core/vllm_tp.c \
    tools/drivers/t23_chain.c -o t23boot -lm
```

> Under PowerShell the comma in `-Wl,--stack,33554432` is parsed as an argument separator → quote the
> whole option.
> `-I` must cover `include`, `include/core` **and** `include/common` (`vllm_tp.c` depends on
> `common/vllm_platform.h`).

## 5. Running

| Env var | Meaning | Example |
|---|---|---|
| `T23_PHASE` | `lay` / `boot` / `fin` | `lay` |
| `T23_LAY` | layer index (`lay` only) | `5` |
| `T23_BI` / `T23_BO` | boot input/output prefixes (`boot` only) | `u5` / `u5r` |
| `T23_E2EMODE` | end-to-end mode (ignore stage-level FAIL caused by reference deviation) | `1` |
| `T23_NT` | worker-thread count of the in-house thread pool `vllm_tp` | `4` |

```bash
# layer 5, both hops
T23_PHASE=lay  T23_LAY=5 T23_E2EMODE=1 T23_NT=4 ./t23lay  > lay5.out  2> lay5.err
T23_PHASE=boot T23_BI=u5 T23_BO=u5r   T23_NT=4 ./t23boot > boot5.out 2> boot5.err
```

## 6. Judging criteria (layer output only)

- `lay` → `RESULT=PASS` at the end of the log
- `boot` → `BOOT=PASS`, plus exactly 8 `out np=2083` lines for that layer (refreshed back to the full
  modulus chain)
- **Stage-level `max|err| FAIL` on A/B/C/D is NOT the criterion.** Those stages compare against a
  plaintext reference computed from a *non-drifting* input, whereas a real ciphertext chain necessarily
  carries drift from the previous layer. Normalization pulls the magnitude back, and the final stage
  carries the `[E2E:ref-deviate-ok]` marker.

## 7. Thread count (measured)

**`T23_NT=4` is currently optimal; adding threads does not speed things up.**
Same machine, same phase (`lay0`'s `[A+B]` segment; baseline 225 s):

| Configuration | `[A+B]` | Verdict |
|---|---|---|
| 4 threads / OpenMP default | 225 s | **fastest** |
| 8 threads / OpenMP default | 255 s | **+13% (slower)** |
| 14 threads / OpenMP default | >384 s | **>+70% (slower)** |
| 4 threads / `OMP_NUM_THREADS=4` | 263 s | **+16% (slower)** |

Reason: the `[A+B]` matmul is dominated by the **OpenMP region** (which already occupies all 16 logical
cores by default), while `vllm_tp` workers are **spin-waiting**. Together they oversubscribe the machine
and steal cores from each other. The phase is also **memory-bandwidth bound** (intermediate buffer
≈112 MB), so adding threads cannot add bandwidth.

## 8. Known blemish (honest note)

The **Chinese comments** in both files carry legacy encoding residue: mojibake such as `鈶?`, plus some
lines merged together (e.g. `锛? *`).

- **It affects neither compilation nor numerics** — the code itself has passed per-layer bit-level
  reproduction.
- The damage is **irreversible** (some bytes were lost). Cleaning up means rewriting the comments
  semantically; re-decoding cannot restore them.

**The copies in this directory are byte-identical to the sources that produced the published results**
(first 16 hex digits of SHA256):

| File | SHA256 |
|---|---|
| `t23_m3p.c` | `F3BF25FC7C86EE69` |
| `t23_chain.c` | `9A078E03D6C1C1F0` |
