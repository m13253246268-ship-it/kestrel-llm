# 规则包与预置上下文

面向**工业边缘**的一类需求：设备上跑的模型必须遵守一份**固定且反复使用**的"命名上下文"——
现场规程、设备清单、术语表、工艺参数表、安全红线。这类内容每一轮问答都要用到，若每轮都当作
普通 prompt 重新 prefill，代价随对话轮数线性叠加。

**规则包（rulebook）** 就是把它预置成一份可复用的**前缀**：离线构建一次、落盘一份 KV 快照，
此后每个请求只付"增量"的 prefill。配套还有**会话存储**与**审计流水**两个模块。

> 本页对应 2026-09 引入的三个 serve 侧模块：`vllm_rulebook` / `vllm_session` / `vllm_audit`。

---

## 1. 能力与开关

| 能力 | 开关 / 入口 | 说明 |
|---|---|---|
| 离线构建规则包 | `--rulebook-build <文本文件> --rulebook-id <ID>` | 加载模型 → 构建 → 退出（一次性） |
| 规则包元信息 | `--rulebook-name` / `--rulebook-version` / `--rulebook-tenant` / `--rulebook-scope` | 版本、租户、作用域；参与快照命名与隔离 |
| 服务端挂载规则包目录 | `--rulebook-dir <目录>` | 注册中心；引擎启动时扫描 |
| 请求级引用 | 请求体 `rulebook_id`（另可带 `session_id` / `tenant_id` / `user_id`） | 引用哪个包、归哪个会话/租户 |
| 会话存储 | `--session-dir <目录>` / `--session-limit N` | 会话历史落盘与上限 |
| 审计流水 | `--audit-log <文件>` | 追加式审计记录（带哈希链） |
| 管理面 | `GET /admin/api/rulebooks` / `/admin/api/config` / `/admin/api/status`（含 `rulebook_hits`） | 列表、当前配置、命中计数；另有删除端点 |

**落盘产物**（均在 `--rulebook-dir` 下）：

```
rb_<id>.json                     元信息
rb_<id>.txt                      注入用的规则文本
rbk_<id>_<ver>_<asm>.kv          预置前缀的 KV 快照
```

其中 `<asm>` 只由**实际注入的 token 序列**决定 —— 因此同一个包在不同选段/不同注入量下是**不同快照**，
不会互相污染。

---

## 2. 机制：预置前缀的 KV 快照复用

1. 离线构建时把规则文本编码、完整 prefill 一遍，得到该前缀的 KV，落盘为 `rbk_*.kv`；
2. 服务端收到带 `rulebook_id` 的请求时，把这份 KV 直接装进 KV 缓存，只对**增量部分**（本轮对话）做 prefill；
3. 命中与否由响应 metrics 与 `/admin/api/status` 的 `rulebook_hits` 反映，`rulebook_tokens` 报告本次注入的 token 数。

> **口径红线（必须随结论一起给出）**：复用路径与"全文重算"的浮点归约顺序不同，因此这是
> **「确定性但近似」**，**不是**全量重算的位级克隆。`--no-prefix-kv` 是回到全量位级结果的**逃生舱**。

---

## 3. 实测（RK3588 / Qwen3-VL-2B / 2026-09）

### 3.1 收益：短手册命中 ≈ 82×

| 指标 | 数值 |
|---|---|
| 无规则包（手册全文塞 prompt，全量 prefill） | **194,275 ms** |
| 命中规则包 | **2,361 ms**（进程内首次 3,174 ms，因需载入快照） |
| **收益** | **≈ 82×** |
| 快照体积 | **59.14 kB / token**（两条独立测量一致） |

### 3.2 硬边界：手册规模决定"有没有收益"

| 手册规模 | 快照 | 复用 | 表现 |
|---|---|---|---|
| **≤ 8192 token** | 落盘 | 是 | **82× 收益** |
| **> 8192 token** | **不落盘**（`DISKKV_MAX_TOKENS = 8192`） | 否 | 每请求全量 prefill |

实测（200,000 B 手册 = 75,146 token）：`reused_prefix=false`、注入 19,467 token（分块选段）、
**每请求全量 prefill 1,562 s**。即**分块检索只解决"注入量"（75,146 → 19,467，−74%），不解决"复用"**。

体积外推（**推算，非实测**）：20K token 手册需 **1.18 GB** 快照，100K token 需 **5.91 GB**。

⇒ **规则包的适用形态是"短而稳定的规则手册"，不是长文档。** 长文档用它，正确性没问题，但性能上等于白付了这套机制的复杂度。

### 3.3 功能正确性（全过）

| 项 | 结果 |
|---|---|
| 离线构建 | 15,000 B → 5,791 token，`chunks=12`，`kv_snapshot=yes`，构建 204.7 s |
| 借用上下文端到端 | 连续 3 次全部 `reused_prefix=true`，`rulebook_hits` 1→3，答案正确 |
| 失效隔离 | 不存在的 id / 含 `/` / 含空格 / 超长 id → **404**；版本不符 → **409** |
| 删除 | 删后请求 404；审计流水记 `rulebook_delete` |
| 会话隔离 | 两个 session 各答自身内容，无串扰 |
| 分块检索 | 75,146 token 手册 + 事实置于**后半段** → **仍能检索到** |

### 3.4 兼容性

- **默认关时与引入前一致**：不带 `rulebook_id`/`session_id` 时，新旧二进制的 `history_tokens`
  序列**逐 token 完全相同**。注：这是 **token-id 级**证据，引擎不暴露 logits，**不能**断言内部浮点/KV 位级一致。
- **可与稀疏档共存**：`--sparse-attn` + `VLLM_SPARSE_PREFILL=1` 下复用正常、召回正确；快照名的 `<asm>` 与
  不开稀疏档时**相同**（`asm` 只由注入 token 序列决定）。
- **`--no-prefix-kv`**：`reused_prefix=false`、每次全量 prefill、`rulebook_hits` 恒 0 ⇒ 逃生舱有效。
- **多包 / 多租户**：两个包交替请求，命中计数各自递增，无串扰。

## 4. 推荐用法

```bash
# 1) 离线构建（一次）：把手册做成规则包
vllm_kestrel --rulebook-build rulebook.txt \
             --rulebook-id field-sop --rulebook-version 1 \
             --rulebook-tenant acme --rulebook-scope plant-a \
             --model /path/to/model.vqf

# 2) 服务端挂载（含会话与审计）
vllm_kestrel --serve --port 8080 --auto-load --model /path/to/model.vqf \
             --rulebook-dir ./rulebooks \
             --session-dir ./sessions --session-limit 64 \
             --audit-log ./audit.jsonl
```

```bash
# 3) 请求带 rulebook_id
curl -s http://127.0.0.1:8080/v1/chat/completions -H 'Content-Type: application/json' -d '{
  "messages":[{"role":"user","content":"本工位的扭矩上限是多少？只回答数值。"}],
  "rulebook_id":"field-sop","session_id":"shift-20260928-a","tenant_id":"acme"
}'
```

**选型建议**：手册 ≤ 约 8K token 时用规则包（拿满 82×）；更长的手册请**自行切分成多个包**
（按主题/章节分），而不是指望单包长手册 —— 后者会因 `DISKKV_MAX_TOKENS` 落不了盘而退化为全量 prefill。

---

## 5. 诚实边界

1. **收益口径依赖"手册短"**：82× 是在 5,791 token 手册上测得；超过 8,192 token 即失去复用。
2. **兼容性证据只到 token-id 级**（引擎不暴露 logits），非位级。
3. **性能表的 B 节为 n=1 单次采样**，未做重复统计与噪声门槛。
4. **`DISKKV_MAX_TOKENS = 8192` 来自源码**，板端仅有"超限未落盘"这一条间接印证。
5. **未做并发/多租户压力测试**：全部测点为单请求串行。
6. `--no-prefix-kv` 的"回到位级结果"是由 `reused_prefix=false` + 全量 prefill + 源码门条件**推断**，
   未做逐 token diff。
7. 运行期产物（`rulebooks/`、`sessions/`、`rbk_*.kv`、`sess_*.json`）已加入 `.gitignore`，
   **不随仓库分发**。
