# 性能与基准

本页汇总 Kestrel（红隼，工程名 `vllm_kestrel`）在 RK3588 平台上的性能数据与**测量口径**。全页数字按版本严格分区，禁止跨版本混比：

- **v1.0 测点（2026-09-12）**：3 模型（2B / 8B / 30B-A3B）× {全层, 逐层} × {组合⑧基线, 组合①, 组合①+⑤}，共 14 个 serve 配置点，全部为当前版本板端实测。
- **v0 历史测点（2026-09-05）**：冷启动 / 8K 长上下文 / KV 恢复 / 与 llama.cpp 同机对照。

> **警告**：v0 数据在 v0 上测得、v1 未复测，不得用于 v1 的任何结论，也不要与 v1 数字混比。v1 已移除 GGUF/safetensors 加载路径并引入逐层推理与 KV v2，冷启动、常驻内存、长上下文与多轮 prefill 的口径都已变化。

## 测量纪律与口径

以下四组口径差异决定了「同一功能在不同表里数字不同」，读表前必须先对齐口径。

**1) 冷页缓存 vs 热缓存**

- 冷页缓存：每个配置点先执行 `sync; echo 3 > /proc/sys/vm/drop_caches` 再跑，为首次前向，含从存储读入 GB 级权重的全部开销。`--stream-test` 的同口径 A/B 均为冷页缓存。
  - **介质口径（2026-09-12 实测）**：v1 的 8B/30B 权重在 **SanDisk microSD 卡**上（`/mnt/VQF` 落在 rootfs，rootfs 在 SD 卡），2B 权重与 L3 目录在 eMMC。两者实测顺序读差 **3.8×**（SD 62.7 MB/s / eMMC 240 MB/s），故 8B/30B 的冷读代价按 SD 卡计。
- 热缓存：权重已在 RAM / 页缓存中，只付算力。serve 稳态表的「热」= 紧接着重发同一请求，全层档权重已常驻 RAM。

**2) 纯权重 RSS vs 含 KV 的 serve 峰值**

- 纯权重口径（`--stream-test`）：只报权重常驻 RSS 与峰值 VmHWM，不含 KV。
- serve 峰值口径：峰值为 VmHWM，**含 KV 缓存**。

**3) 为什么两种口径的倍率不同**

同一模型 30B-A3B：纯权重口径倍率 **23.2×**，serve 峰值口径倍率 **12.8×**。原因是 serve 峰值含 KV，而逐层真正解耦的是**权重**，KV 由 KV v2 惰性分配另管——KV 不随权重驻留档变化，故摊薄了倍率。

> 口径差别导致的倍率不同必须照实说明：`docs/优化配置与边界说明.md` 中「省 4.6×~21.8×、prefill +11~25% / decode +121~259%」那组是 **v0 时期的热缓存**（全层权重已在 RAM / 页缓存）稳态数字，**不作 v1 结论**，不可与本页 v1 数字混用。

**4) `--stream-test` 与 serve 的区别**

- `--stream-test`：验证 harness，32 token prefill + 32 token 贪心 decode，冷页缓存，纯权重口径；用于逐层 vs 全层的同口径 A/B 与 TOKIDS 位级一致性对照。
- serve：真实服务路径（`--serve`）；稳态口径单请求 = 300 token 上文 + 32 token 生成（greedy），多轮追问表为 t2 / t3 两轮。

### 4) 8B：推荐档的价值兑现（以 2026-09-15 RK3588 远程复测为当前公开口径）

上文 §1~§3 覆盖 2B/8B/30B 三档。这一节回答一个问题：**逐层推理最划算的落点在哪——答案是 8B。**

配置：`--threads 4`（`OMP_NUM_THREADS=4 VLLM_THREADS=4`）；**权重在 SanDisk microSD（62.7 MB/s）**。
内存口径与 §1 一致（`--stream-test`，32 token prefill + 32 token decode，冷页缓存 A/B）。
下表 prefill 与 decode **取自同一次冷页缓存运行**（故 decode 高于下方「热页缓存」的线程 A/B 表）：

| 档 | 权重常驻 RSS（prefill 后） | rss_end | prefill 32tok | decode |
|---|---|---|---|---|
| 全层 | 4,189,912 kB | 4,202,988 kB | 67.9 s | 207 ms/tok（4.84 tok/s） |
| **逐层** | **480,348 kB（8.7×）** | **487,912 kB** | 63.2 s | 385 ms/tok（2.60 tok/s） |

serve 逐层档 + 短请求（`enable_thinking=false`、`max_tokens=96`；实测自然结束于 70 token）：

| 档 | TTFT | 端到端 | tpot | 峰值 VmHWM |
|---|---|---|---|---|
| 冷（`drop_caches` 后首次） | 72.613 s | 95.505 s | 331.8 ms | 612,868 kB |
| **热（连续 5 次同请求）** | **中位 1.734 s**（1.711~1.796） | **约 24.5 s**（24.408~24.610） | **中位 330.2 ms**（328.9~330.6） | 824,152 kB |

> 热档 VmHWM 为 5 次累计后的**高水位**（当前复测峰值 824,152 kB）。VmHWM 是进程历史最高水位、
> 单调不减；因此推荐引用本节的 **TTFT / tpot 中位数与范围**，而不是把 VmHWM 误读为单轮瞬时占用。

**8B 为什么是推荐档（三条，均可复现）**：

1. **省内存的收益拿满，代价可控**：权重常驻 4.19 GB → **0.48 GB（8.7×）**，serve 峰值 **0.82 GB**。
2. **热态稳定有物理保障**：权重 6.15 GiB **装得进 15.6 GiB 页缓存**，所以热态不必赌运气——实测 5 次采样的 tpot 仅在 **328.9~330.6 ms** 间波动。
3. **冷启动一次性成本低**：冷态首轮 TTFT **72.613 s**（对比 30B 的 195~211 s），因为成本 ∝ 权重体积 ÷ 介质带宽。

**隐藏的 2×：必须用 `--threads 4`**（同机同模型 A/B，各 2 次重复，热页缓存）：

| 档 | `--threads 4` | `--threads 8` | 比值 |
|---|---|---|---|
| 全层 decode | **186 / 189 ms/tok** | 431 / 433 ms/tok | 4 线程快 **2.3×** |
| 逐层 decode | **370 / 378 ms/tok** | 580 / 582 ms/tok | 4 线程快 **1.56×** |

> RK3588 是 4×A76 + 4×A55，`--threads 8` 会把 4 个 A55 小核拉进 GEMM 并行区。§1 的 8B 数字
> （全层 429 / 逐层 586 ms/tok）正是 **`--threads 8`** 口径，与上表右列吻合；**换到 4 线程后
> 8B 全层 decode 达 5.4 tok/s**。

**一键复现**：`sh tools/bench/bench_value.sh`（参数可用环境变量覆盖，用法见脚本头部注释）——产出
A/B 内存对照、热态稳定度、页缓存证据三部分，并写出 `http.json`；仅依赖 Python 3 标准库。

### 5) 30B-A3B 短请求：能跑到什么程度（2026-09-12 补充测点）

上文各表回答「省多少内存」，这一节回答另一个问题：**30B 在 16 GB 板上到底能不能用。**
同机同引擎（sha256 `e1484740…a8f8e8`），**权重在 SanDisk microSD 卡上**。

配置：逐层 `VLLM_VQF_STREAM=1` + 组合⑤ `VLLM_ACTQ=1 VLLM_MOE_BATCH=1` + 组合①参数。
注意：本例上文仅 22 token，日志为 `[L3] skipped: seq=22 < l3-min-seq=128`，
**L3 与前缀复用未介入**，故下表是「逐层 + MoE 档」，不含组合①的 KV 侧收益。
线程：`OMP_NUM_THREADS=4 VLLM_THREADS=4`。

请求 = **22 token 上文 + 32 token 生成**（greedy，流式）：

| 档 | TTFT | 端到端 | tpot | 峰值 VmHWM |
|---|---|---|---|---|
| 冷（`drop_caches` 后首次） | 211.5 s | 258.8 s | 1,524.5 ms | 666,468 kB |
| **热（紧接着重发同一请求）** | **3.3 s** | **20.8 s** | **564.8 ms** | 918,300 kB |

非流式同请求交叉验证 20.7 s（与流式 20.8 s 一致），该次收尾后进程高水位累计到 933,656 kB。

> **VmHWM 口径**：它是进程**历史最高水位**（单调不减），不是单次请求的稳态占用，逐轮上升
> 属正常记录方式。上表两行是各自实测时刻的水位；8B 的 5 次热态采样同理（§4）。单轮稳态占用
> 是否回落需 `VmRSS` 逐轮采样，**本项目尚未做该采样，列为开放项**。

**关键前提：`enable_thinking` 默认为开**（引擎与 HF `apply_chat_template` 一致，见
`src/serve/vllm_server.c` 的 `resolve_thinking`）。上表那 32 个 token **全部落在思考段内、
未产出答案**——只测「输出 32 token 要多久」会得出偏乐观的可用性结论。补测开关对照
（`max_tokens=256`）：

| 档 | TTFT | 端到端 | 实际输出 | 结果 |
|---|---|---|---|---|
| thinking **开**（默认） | 29.5 s | 221.9 s | **256（打满预算）** | **`</think>` 始终未出现，无答案** |
| **thinking 关**（请求体 `"enable_thinking": false`） | **3.1 s** | **24.5 s** | **40（自然 EOS 结束）** | **给出完整答案** |

thinking 关档的原文输出即答案本身：
「边缘计算是在数据产生地附近进行数据处理和分析的计算模式，而云计算则是在远程数据中心进行集中式数据处理，两者的主要区别在于数据处理的位置和实时性需求。」

> 说明：两次请求都紧跟在一个冷预热请求之后。thinking 关那次是第 3 个请求、页缓存最热
> （TTFT 3.1 s）；thinking 开那次是第 2 个请求，TTFT 29.5 s 反映页缓存尚在回温——
> **两者 TTFT 差异主要来自页缓存状态，不是 thinking 开关本身**。

**结论（修订）**：30B-A3B 在这块板上的可用档 = **关 thinking + 短上下文**——关掉思考后
**24.5 s 拿到完整的一句话答案，峰值内存 0.91 GB**（该次实测 VmHWM 910,748 kB），这才是"能用"的真实数字。默认（thinking 开）
下 256 token 走不完思考段，一次问答实际要预留 300+ token、约 **3~4 分钟**。
冷态 258.8 s 是首次从 SD 卡读入 17.66 GB 权重（其中权重数据段 16.8 GB）的一次性成本，
权重驻留页缓存后回到秒级。

**存储介质实测**（同机 `dd iflag=direct`，1 GiB，绕过页缓存）：

| 介质 | 用途 / 挂载点 | 设备 | 顺序读实测 |
|---|---|---|---|
| **SanDisk microSD** | 8B/30B 权重（`/mnt/VQF`） | `/dev/mmcblk1`（`name=SD64G`、`type=SD`、`manfid=0x000003`） | **62.7 MB/s** |
| eMMC | 2B 权重、L3 目录（`/mnt/emmc`） | `/dev/mmcblk0`（`name=BJTD4R`、`type=MMC`） | **240 MB/s** |

> 这条对照解释了第 1 节 8B/30B 的冷读量级：逐层档「用时间换内存」里的时间，正比于
> **权重体积 ÷ 介质带宽**。上表冷态 211.5 s 对应 62.7 MB/s 的 SD 卡；**若把权重换到
> eMMC（240 MB/s），按带宽比推算首 token 约可降到 56 s 量级——推算，未实测**。

## v0 历史测点（2026-09-05，仅作历史参考）

> **警告（重申）**：以下数据在 v0 上测得、v1 未复测，不得用于 v1 的任何结论，也不要与上文 v1 数字混比。v0 平台：RK3588 (OPi 5 Plus, 8 核 4×A76 + 4×A55, 15GB RAM, eMMC, 无 GPU/NPU 参与)，模型 Qwen3-VL-2B-Instruct；对照引擎 llama.cpp 0.3.0-dev（GGUF Q4_0，~4.09 bit/权重）。
> 位宽对齐提醒：vllm q4 与 GGUF Q4_0 均约 4bit/权重但量化格与算子不同，非位级同一权重，两引擎对照含各自量化差异。

|---|---|---|---|
| vllm_kestrel (VQF mmap) | 2.01 / 2.01 / 2.02（中位 2.01） | 1175 / 1018 / 1263（中位 1175） | ~2465（中位 2465.7） |
| llama.cpp (GGUF Q4_0 mmap) | 5.08 / 5.02 / 5.02（中位 5.02） | 不适用（启动即 mmap） | ~3027（中位 3027.0） |

### 2) 8K 长上下文（内容 token 1K/2K/4K/8K × 3 变体，生成 64 token）

vllm_kestrel，优化档全开（sparse-attn k=32 + spec-k4 + prefix/disk-kv）：

|---|---|---|---|---|
| 1K (1028) | 19.07 / 19.15 / 19.19 / 19.46 / 19.47 / 19.63 | ~53 | 72.4–82.1（中位 73.4） | 26.6–27.3 |
| 2K (2049) | 44.64 / 45.06 / 45.16 | ~45.4 | 84.6–85.0 | 56.1–56.6 |
| 4K (4091) | 100.3 / 100.6 / 101.8 / 102.3 | ~40.4 | 100.7–103.0 | 118.8–120.8 |
| 8K (8109) | 202.0 / 203.0 / 202.6 | ~40 | 131.9–136.7 | 233.6–235.0 |

llama.cpp (GGUF Q4_0) 同机对照：

| 档(prompt tokens) | prefill TTFT(s) | prefill tok/s | decode TPOT(ms) | 端到端 wall(s) |
|---|---|---|---|---|
| 1K (1032) | 12.32 / 12.33 | 83.7 | 98.6 / 105.9 | 18.7 / 19.2 |
| 2K (2056) | 28.63 / 28.71 | 71.6 | 124.6 / 128.1 | 36.9 / 36.9 |
| 4K (4104) | 74.10 / 74.22 | 55.3 | 215.8 / 219.4 | 88.3 / 88.3 |
| 8K (8136) | 212.44 / 212.37 | 38.3 | 409.4 / 411.6 | 235.9 / 235.8 |

加速比汇总（vllm_kestrel / llama.cpp，均含各自权重量化差异）：

| 档 | vllm prefill tok/s | llama prefill tok/s | prefill 比 | vllm TPOT | llama TPOT | decode 比 |
|---|---|---|---|---|---|---|
| 1K | ~53 | 83.7 | llama 1.6× | 73.4ms | 102ms | vllm 1.4× |
| 2K | ~45.4 | 71.6 | llama 1.6× | 84.6ms | 126ms | vllm 1.5× |
| 4K | ~40.4 | 55.3 | llama 1.37× | 102ms | 218ms | vllm 2.1× |
| 8K | ~40.0 | 38.3 | 打平（vllm 1.04×） | 136.7ms | 411.6ms | **vllm 3.0×** |

> prefill 衰减斜率：llama tok/s 84→72→55→38（全量注意力 O(n²)）；vllm 52→45→40→40（sparse-attn k=32 使注意力近线性）。decode 差距随上下文放大：2K→8K llama 劣化 3.3×（126→412ms），vllm 仅 1.6×（85→137ms）。

### 3) KV 恢复

同进程多轮前缀复用（内存 prefix-KV 命中）：

| 引擎/档 | turn1 pt | turn1 prefill/TTFT | turn2 pt | turn2 增量 prefill | 命中 |
|---|---|---|---|---|---|
| vllm 4K | 4091 | TTFT 101.3s | 4120 | ~2.0s（引擎日志 n=34） | PREFIX+DISK |
| vllm 8K | 8109 | TTFT 202.0s | 8138 | ~2.0s（引擎日志 n=34） | PREFIX+DISK |
| llama 4K | 4104 | prefill 74.0s | 29* | 3.34s（prompt_ms） | llama slot KV cache |
| llama 8K | 8136 | prefill 211.5s | 29* | 6.63s（prompt_ms） | llama slot KV cache |

> 两侧首 token 口径不同：vllm 报 TTFT（首 token，含引擎调度）4K 7.9s / 8K 13.8s（相对全量 TTFT 为 12.8× / 14.6×），增量 prefill 本身 ~2.0s（稀疏，与上下文长度无关）；llama 无 TTFT 字段，增量 prefill 3.34s / 6.63s（全量注意力扫长前缀，随上下文增长：1K 1.04→2K 1.74→4K 3.34→8K 6.63s）。8K 恢复场景增量 prefill vllm 2.0s vs llama 6.6s（vllm 3.3×）。

跨进程磁盘 KV 恢复（vllm `--disk-kv`；llama.cpp 无等价物，重启即失）：

| 档 | turn1 全量 TTFT | 快照（F32, 写盘增量） | 重启 boot | 恢复后 TTFT（turn2 +29） | 相对全量加速 |
|---|---|---|---|---|---|
| 8K (8109→8138) | 201.7s | 1.87 GB（+16s wall） | 1.0s | **15.4s** | **13.1×** |

> F32 快照 ~229 KB/token（28 层 × 8 KV 头 × 128 dim × 4B × 2），8K 会话 = 1.87 GB，写/读 eMMC 各 ~15 s；本轮已将快照上限由 768 放宽至 8192 token，使 4K/8K 会话可落盘，代价是 turn1 响应后同步落盘 +16s。引擎层小上下文验证基线（~250 token，放宽前）：prefill 1328ms→285ms（4.7–5.3×），输出逐字节一致。

## 复现方法

引擎为板端 `vllm_shs`，sha256 `e1484740…a8f8e8`。模型（单文件 VQF）：

```text
/mnt/emmc/Modl/Qwen3-VL-2B-Instruct/qwen3vl2b.dual.vqf   (4.16 GB)
/mnt/VQF/8b/qwen3vl8b.q4.vqf                             (6.60 GB)
/mnt/VQF/qwen3-30B-A3B-q4                                (17.66 GB)
```

`--stream-test` 用 `--threads 8`；serve 用 `--serve --port 18080 --device arm-rk3588-opi5 --auto-load`：

```bash
# 组合⑧基线（无前缀复用）
./vllm_shs --serve --port 18080 --device arm-rk3588-opi5 --auto-load --no-prefix-kv

# 组合①：sparse-attn + L3 驱逐 + P3 前缀复用
VLLM_L3_PREFIX_REUSE=1 ./vllm_shs --serve --port 18080 --device arm-rk3588-opi5 --auto-load \
  --sparse-attn --sparse-k 32 --l3-evict --l3-ratio 0.75 --l3-min-seq 128 --l3-path /mnt/emmc/l3bench

# 组合① + 组合⑤（MoE，仅 30B-A3B / q4 权重）
VLLM_L3_PREFIX_REUSE=1 VLLM_ACTQ=1 VLLM_MOE_BATCH=1 \
  ./vllm_shs --serve --port 18080 --device arm-rk3588-opi5 --auto-load \
  --sparse-attn --sparse-k 32 --l3-evict --l3-ratio 0.75 --l3-min-seq 128 --l3-path /mnt/emmc/l3bench

# 逐层档：以上任意命令前加环境变量
VLLM_VQF_STREAM=1

# 同口径 A/B（逐层 vs 全层），冷页缓存：每配置点先清缓存再跑
sync; echo 3 > /proc/sys/vm/drop_caches
./vllm_shs --stream-test --threads 8
```

> **线程口径务必对齐**：§1/§2/§3 的 `--stream-test` 用 `--threads 8`；§4（8B 推荐档）用
> `--threads 4`。RK3588 是 4×A76 + 4×A55，`--threads 8` 会把 4 个 A55 小核拉进 GEMM 并行区，
> 8B 全层 decode 因此从 186 ms/tok（4 线程）退化到 431 ms/tok（8 线程）。**同一张表里的数字
> 必须同线程口径，否则差 2×。**

**一键复现 8B 推荐档（§4）**：

```bash
sh tools/bench/bench_value.sh          # 产出 A/B 内存 / 热态稳定度 / 页缓存证据；仅依赖 Python 3 标准库
# 常用覆盖（默认值见脚本头部注释）：
#   MODEL_DIR=/mnt/VQF/8b/serve MODEL_FILE=/mnt/VQF/8b/qwen3vl8b.q4.vqf
#   N_WARM=5 MAXTOK=96 THREADS=4 PORT=18092 OUT=./bench_value_out
```

短请求测点（上文 22 token + 生成 32 token，逐层 + 组合⑤；请求走 OpenAI 兼容接口）：

```bash
sync; echo 3 > /proc/sys/vm/drop_caches     # 冷档；热档=紧接着重发同一请求
env OMP_NUM_THREADS=4 VLLM_THREADS=4 \
    VLLM_VQF_STREAM=1 VLLM_ACTQ=1 VLLM_MOE_BATCH=1 VLLM_L3_PREFIX_REUSE=1 \
    ./vllm_shs --serve --port 18090 --device arm-rk3588-opi5 \
      --model /mnt/VQF/qwen3-30B-A3B-q4 --auto-load \
      --sparse-attn --sparse-k 32 --l3-evict --l3-ratio 0.75 --l3-min-seq 128 \
      --l3-path /mnt/emmc/l3bench

curl -sN http://127.0.0.1:18090/v1/chat/completions -H "Content-Type: application/json" \
  -d '{"model":"qwen3-30b-a3b","messages":[{"role":"user","content":"请用一句话解释什么是边缘计算，以及它和云计算的区别。"}],"max_tokens":32,"temperature":0,"stream":true,"enable_thinking":false}'
```

> 峰值内存取引擎进程 `VmHWM`（`grep VmHWM /proc/<pid>/status`）。上文本例实测 22 token，
> 日志会打印 `[L3] skipped: seq=22 < l3-min-seq=128`——**短上下文不触发 L3**，如需让组合①
> 生效请把上文加到 ≥128 token。
>
> **`enable_thinking` 务必按需显式指定**：引擎默认与 HF 一致为**开**，此时输出会先走思考段，
> 短预算下可能全是思考、不产出答案。要"短问答"效果请传 `"enable_thinking": false`
> （或用环境变量 `VLLM_ENABLE_THINKING=0`）。

环境变量清单：`VLLM_VQF_STREAM=1`（逐层驻留）、`VLLM_L3_PREFIX_REUSE=1`（P3 共存）、`VLLM_ACTQ=1` 与 `VLLM_MOE_BATCH=1`（组合⑤ MoE）。

日志字段：`[L3] evicted/restored`、`[KV-PREFIX] reuse`、`[VQF-STREAM] enabled`、`[KV-DISK] saved/loaded`、`[PREFILL-TIMING] GEMM/ATTN`。

## 诚实边界

- **x86-64 仅作功能自检与位级一致性对照，不作性能基准**：随版移植层（`tools/build/build_x64.ps1` / `tools/build/check_x64.ps1`）不能用于任何性能结论。
- **30B-A3B 在 16 GB 板上的绝对速度很低，这是硬件边界而非实现缺陷**：无优化基线一轮 300 token 上文要 620 s（tpot 2,240 ms，≈0.45 tok/s），全层档峰值 14.2 GB 已顶到内存上限。**可用档见第 5 节**：关 thinking + 短上下文时 24.5 s 给出完整短答、峰值 0.91 GB；默认 thinking 开时 256 token 走不完思考段。
- **逐层只支持明文 VQF**：VQF-Enc / 内嵌 SM2 签名的权重会被显式拒绝（须全层驻留）；与专家窗口 `VLLM_EW*` 不并存。
- 逐层压缩的是**权重驻留**；KV 底座另由 KV v2 惰性分配约束。
- 速度代价随「权重体积 ÷ 存储带宽」上升：`--stream-test` 冷页缓存下 prefill +12% / −1% / −0.1%，decode +16% / +37% / +16%；serve 稳态热档 tpot +38.7% / +34.6% / +18.2%，热档 prefill 只 +3.3% / +2.7% / +0.4%（均按 2B / 8B / 30B 顺序）。
- v0 与 llama.cpp 对照的所有数字仅作**历史参考**，不得用于 v1 结论。
