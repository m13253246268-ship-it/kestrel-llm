# 优化配置与边界

本页把 Kestrel（红隼）各优化档（命令行开关与环境变量）整理成一份**可查阅的配置手册**：每个档位讲清**机制是什么、收益多少、边界与代价是什么**。收益不夸大，代价与不适用场景照实写。

> **口径分区（读数字前先对齐）**：
> - **v1.0 板端实测测点 = 2026-09-12**：3 模型（2B / 8B / 30B-A3B）× {全层, 逐层} × {组合⑧基线, 组合①, 组合①+⑤} 成矩阵实测。
> - **v0 测点 = 2026-09-05**：v0 上测得、v1 未复测，**不得用于 v1 任何结论**，也不要与 v1 数字混比（v1 已引入逐层推理与 KV v2，口径已变）。
> - 标注「x86 基准机（2026-08-28）」的数字为本地 x86 同条件对照归因，仅供功能自检与位级一致性对照，绝对吞吐 / 加速比**不可外推到板端**。
> - 当前发布版上下文窗口钳制为 `max_seq=8192`（`src/main.c`）；文中「16K+」档为评估期（当时上限更高）的相对结论。

## 组合①：L3 驱逐 × 前缀复用共存（P3）

- **机制**：冷 KV 块 Q4 压缩落盘释放 RAM；`VLLM_L3_PREFIX_REUSE=1`（P3 门）让 L3 驱逐与内存前缀复用**共存**。不加门时二者默认互斥——L3 释放前缀块为 NULL，prefill 无 NULL 检查会崩。
- **收益**：源文档台账「追问轮 prefill **−93%~−97%**」，是 v1.0 收益最大的单项优化。v1.0 板端（2026-09-12）多轮追问 t2/t3：2B 全层 −83.8%/−85.1%、逐层 −80.4%/−83.1%；8B 全层 −90.2%/−90.5%、逐层 −89.5%/−89.8%；30B-A3B 全层 −96.0%/−96.1%、逐层 −95.9%/−96.0%。
- **边界与代价**：`--l3-ratio` 默认 **0.75**（evict 每层最冷 75% 块），依赖 `--sparse-attn`（冷块需稀疏选择信号）；单用户 8K 只用 ~11.7GB RAM，**不触发**，价值在 16K+ 或多用户并发；稀疏 decode 从磁盘 Q4 状态读回，首次访问有 I/O 延迟。**铁律：开 `--l3-evict` 必须同时置 `VLLM_L3_PREFIX_REUSE=1`**，否则前缀复用被静默打掉、多轮追问全量重算。
- 生效自证（2B 全层档板端日志原文）：
```text
[L3] evicted 252 blocks -> /mnt/emmc/l3bench_u65bbfe41 (cursor=9.84 MB, seq=345, keep=332, ratio=0.75, ...), freed 78.8 MB from RAM
[L3] restored 252 prefix blocks from Q4 payload (prefix=377)
[KV-PREFIX] reuse 377-token KV prefix, prefill rest
```

## 组合⑤：MoE 专家激活量化 + 专家批量

- **开关**：`VLLM_ACTQ=1 VLLM_MOE_BATCH=1`。**机制**：MoE 专家激活量化 + 专家批量。
- **收益**：源台账 prefill 实测 **10.78×**。30B-A3B 在组合① 上再叠组合⑤（须 q4 权重）后，第二/三轮追问 prefill 从 ⑧ 基线的 722 s / 822 s 降到 **4.7 s / 3.2 s（全层）**、5.3 s / 3.7 s（逐层），首轮也从 620 s 降到 23 s，tpot 2,240 ms → 504 ms。
- **边界**：只对 MoE 权重（q4）有意义；与组合①、与逐层驻留三者**正交可叠加**。

## 稀疏注意力（`--sparse-attn --sparse-k 32`）

- **机制**：已接入主路径——decode 走 `sparse_attn_head`；prefill 走 `st_attn_batched_packed_sparse`，seq_len > 2×block 时自动启用。默认 `k=32 / block=32 / probe=8`。
- **收益（x86 基准机 2026-08-28，8K prefill 同条件前后测）**：ATTN 61.6s（26.5%）→ **16.0s（7.8%），−74%**；prefill 总时长 232.5s → 206.2s（−11.3%，GEMM 有 ±10% 机器噪声）。4K 历史：ATTN 15.0s → k=32 时 6.7s（k=8：2.0s / k=16：3.2s），ATT 占比 15%→2~7%。
- **边界**：**质量下边界 k=32**（S=4096 验证：needle 召回 YES、ppl 3.37）；k=16 即失败（needle NO、ppl 6.2）；k=8 严重退化（答案错、ppl 7.6）→ **铁律：`--sparse-k` ≥ 32**。decode 稀疏门控 `!use_kv_q4`，故 **`--kv-q4` 与 `--sparse-attn` 互斥**。长上下文收益更大（ATT 占比 4K 15% → 8K 26.5%）。多模态单图（~880 视觉 token）质量一致但 ATT 占比低，**无性能收益**。

## L3 驱逐（`--l3-evict --l3-ratio --l3-min-seq --l3-path`）

- **机制**：已实现但**默认未开**（此前对比中选择了 RAM 稀疏）；把每层最冷比例的 KV 块 Q4 压缩落盘以释放 RAM。
- **收益**：单用户 8K **测不出收益**；价值在 **16K+ 或多用户并发**（RAM 耗尽时才压缩落盘）。与 `--kv-q4` 同用时 L3 可省 ~1GB。
- **边界**：依赖 `--sparse-attn`；`--l3-ratio` 默认 0.75；恢复路径首次访问有 I/O 延迟；必须与 P3 门同开。旧激进记录参考：`--prefill-q8 --sparse-attn --l3-evict --l3-ratio 0.9 --sparse-k 16`（注意 **k=16 已低于质量边界**，勿照抄）。

## 前缀复用（`--prefix-kv`，默认开；`--no-prefix-kv` 关闭）

- **机制**：多轮对话第二轮起，与上轮 token 序列最长公共前缀（LCP≥16）命中时保留 KV，只 prefill 差异部分（模型层零改动，serve 层 `ist_reset(keep)`）。
- **收益**：prefill 加速 **4.99x**（253 复用 231 token），输出逐字节一致；x86 A/B −97.2%。
- **边界**：**与 `--l3-evict` 默认互斥**（置 `VLLM_L3_PREFIX_REUSE=1` 即共存）；多模态路径全量 reset（视觉 KV/mrope 不参与文本前缀）；`--no-prefix-kv` 关闭。部分 prefill 数值上必然 ≠ 全量 prefill，口径为「确定性但近似」。

## 磁盘 KV 持久化（`--disk-kv DIR`）

- **机制**：每次成功文本请求后把 F32 KV 快照落盘 `DIR/kv_<fnv64>.kv`；启动扫描建索引；请求时与 checkpoint 求 LCP（≥16）→ 加载 KV → 只 prefill 差异。支持跨进程 / 重启复用。
- **收益**：prefill 1328ms→285ms（**4.66–5.27x**），输出逐字节一致，日志 `[KV-DISK] loaded/saved`；源台账跨进程恢复 **−97.3%**。
- **边界**：上限 8192 token/文件（`DISKKV_MAX_TOKENS`，覆盖 `max_seq=8192` 窗口）、8 文件（LRU 按 mtime）；F32 保证位级一致但体积大。与 `--no-prefix-kv` 解耦（`ist_reset` 复用门槛为 prefix_kv **或** disk_kv）。

## 推测解码（`--spec [--spec-k N]`）

- **机制**：n-gram 自推测——上下文末尾窗口（最长优先 8→3 token）在历史找重复，取其后的 K token 作草稿；`st_qwen_model_prefill_batch` 一次并行 prefill 验证（每位置 lm_head top-1），贪婪接受，KV 回滚。
- **收益**：输出与正常逐字节一致（数学无损）；文本草稿命中 75%（tpot 25.3→19.5ms，**1.30x**），多模态命中 92%（28.8→17.6ms，**1.64x**）。
- **边界（诚实）**：**仅贪婪文本路径**（temp≤0/top_p≥1/min_p≤0），L3/batch/稀疏（`!g_sparse_attn`）模式禁用；n-gram 只对**精确重复文本**（固定格式列表/代码模板/叠句）生效，自由文本命中率低；编号递增类重复（「第N点」）草稿系统性给旧值、被拒（实测 0% 命中）；收益依赖 decode 本身耗时——2B 本地仅 25ms/token，verify 开销 ~28ms 吃掉了大部分增益，**RK3588（341ms/token）上理论增益 2-3x**；默认关闭，须客户端 `top_p=1.0`。

## 连续批处理（`--batch-max N`）

- **机制**：独立后台线程每步 1 次前向 B token（复用 `st_qwen_model_forward_batch`），HTTP worker 提交 per-request 状态；max 32。
- **收益**：串行 22.0 vs 批量 13.1 tok/s（约 **1.7x**，K=8，8 并发全 PASS）；源台账板端 ~1.7×。
- **边界**：**位级一致性在跨 prompt 下存在 near-tie 双内核翻转风险**（margin 0.71 vs 0.032 级别），非普遍保证；16 线程下 8B 模型 decode 已是内存带宽瓶颈，批增益有限，NPU/更大模型受益更大；x86 仅 **+4.5%**（x86 无效）。

## KV v2 惰性分配 与 `VLLM_KV_NOF32=1`

- **机制**：KV 底座随用随长（不再满窗预分配）；`VLLM_KV_NOF32=1` 去掉 f32 KV 正典，与该惰性分配配套。
- **收益**：让常驻内存与模型体积、层数解耦；README 口径「配合 `VLLM_KV_NOF32=1` 可把 2B 常驻进一步压到 **~222 MB 量级**」。
- **边界**：逐层压缩的是**权重**，KV 底座另由 KV v2 惰性分配约束，二者互不替代；源文件未展开 `VLLM_KV_NOF32` 的独立边界与代价，详见 [docs/KV缓存v2-惰性分配与分层驻留方案.md](../docs/KV缓存v2-惰性分配与分层驻留方案.md)。

## 逐层推理（`VLLM_VQF_STREAM=1`）

- **机制**：分层驻留（逐层加载）——VQF 单文件仍以 mmap 直挂，但每层权重只在参与计算时建立文件页，算完立即 `MADV_DONTNEED` 释放，仅 keep 层（缺省 1 层）常驻。
- **收益（v1.0 板端 2026-09-12）**：纯权重 RSS 省 **4.6× / 8.9× / 23.2×**（2B / 8B / 30B-A3B，`--stream-test` 冷页缓存）；serve 峰值（含 KV）省 **3.5× / 4.9× / 12.8×**。17.7 GB 的 Qwen3-30B-A3B-q4 可在 16 GB RAM 的 RK3588 上服务（全层档同一模型峰值 12.7 GB（`--stream-test`）/ 14.2 GB（serve，含 KV））。语义不变：`--stream-test` 贪心 TOKIDS 序列全层/逐层逐位一致。
- **边界与代价**：**只支持明文 VQF**——VQF-Enc / 内嵌 SM2 签名的权重会被**显式拒绝**（须全层驻留，不可用 `VLLM_VQF_STREAM`）；与专家窗口 `VLLM_EW*` **不并存**（EW 接管层入口钩子）。速度代价随「权重体积 ÷ 存储带宽」上升：`--stream-test` 冷页缓存 prefill **+12% / −1% / −0.1%**、decode **+16% / +37% / +16%**；serve 稳态热档 tpot **+38.7% / +34.6% / +18.2%**，热档 prefill 只 **+3.3% / +2.7% / +0.4%**。
```text
[VQF-STREAM] enabled keep=1 nl=48 segs=11 per-layer=334.1MB data=16847.2MB resident~808.4MB rss=988kB
```

## `--kv-q4`

- **机制**：KV 用 Q4 存储。**收益**：KV 内存 **1.65×** 压缩 / L3 可省 ~1GB。
- **边界**：**与 `--sparse-attn` 互斥**（稀疏 decode 要求 KV 非 q4，门控 `!use_kv_q4`）。此外 f32/q4-KV decode 恒定两遍，比 q8-KV 的单遍慢。

## Q8Q4 混合权重（`--wmode dual` / `--prefill-q8`）

- **机制**：`--wmode dual` 即默认混合模式（wmode=0）；`--prefill-q8` 可单独强制 prefill 走 Q8_0。`--wmode q8`（纯 Q8）与 `--wmode q4`（纯 Q4）是两个极端，`dual` 是其混合默认。
- **收益**：4K prefill dual total 101.3s vs q4 98.9s（**+2.4%**，GEMM 82.3 vs 81.1s 持平）；decode（Q4）TPOT 130ms 正常；x86 A/B +1.8%，复现「质量档、速度几乎持平」。
- **边界**：定位是**质量档而非速度档**——Q8 prefill 精度显著高于 Q4，成本几乎为零；与稀疏注意力正交，可叠加（`--wmode dual --sparse-attn`）。

## 专家窗口（`VLLM_EW*`）

- **机制**：接管层入口钩子（源文件仅此描述）。**收益**：源文件未给收益数字。
- **边界**：与逐层推理 `VLLM_VQF_STREAM` **不并存**；加密 VQF × {`VLLM_VQF_STREAM`, `VLLM_EW`} **互斥**（需全层驻留）。

## 采样与其它档

- **`--min-p P`**（ds4/DwarfStar 默认采样器）：机制为特殊 token 抑制后、top-p 之前应用 min-p 过滤，请求体可覆盖，`--min-p 0`=关闭（默认）；与 top-p 正交叠加，属采样类参数，**贪婪模式不生效**；源文件未给独立收益数字（兼容层单测全 PASS）。
- **`--q2mix-tail N`**：机制为前 N 层 FFN 用 Q2_1、尾部保留 Q4。**已定案关闭**——tail=28（全 Q4）cjk=0.66 正常、tail=12 cjk=0.11 乱码，机制链路正确但 **2-bit 误差在稠密模型主残差路径累积不可救**，默认已改 0；2B 稠密模型关闭，MoE 类模型（注意力 Q4 + FFN Q2）另议。
- **`VLLM_ATTN_ONLINE=1`**（online-softmax 单遍）：读取**仅存在于 x86 开发树**，**aarch64 发布树未实现该开关**——板端 q8-KV decode 恒定单遍（`flash_attn_single_q_q8_neon`，源码即 online 逻辑），f32/q4-KV decode 恒定两遍，**板端无可切换项**。x86 实测：decode（非稀疏 + q8 KV）有效；prefill（S=2048）total 46.0s vs 2-pass 43.5s（**+5.7%**）、ATTN 4.04s vs 3.45s（**+17%**）——单遍需在热循环用标量 `expf`，省下的 KV 扫描不足以抵消，**内存带宽受限平台（如 RK3588）才可能转正**。稀疏 decode 走 `sparse_attn_head` 提前 return，不经此路径。
- **Flash Attention**（`flash_attn_blocked_single_q`）：**结构性不适用**。门控 `!use_kv_q8 && !g_sparse_attn && seq_len ≥ 64`；要求 f32/q4-KV 且非稀疏，与当前 q8-KV + 稀疏栈**互斥**（KV 默认 q8，`use_kv_q8=1`，flash 永远不可达）；flash 为全量注意力，与稀疏 top-k 块设计天然冲突。唯一适用场景是多模态 q4-KV 注意力（`vllm_mm_attn_flash_worker`，已在使用）。**当前配置下无接入价值。**

## 组合与叠加关系

**可叠加**

- 组合① × 逐层推理：同一组合在两种驻留档下收益同量级（2B −80%~−83%、8B −89%~−90%、30B −96%），即**权重驻留轴与 KV 分页轴正交**。
- 组合① × 组合⑤（MoE）× 逐层驻留：三者正交。
- `--wmode dual` / `--prefill-q8` × `--sparse-attn`：正交。
- KV v2 惰性分配 + `VLLM_KV_NOF32=1` + 逐层推理：联用可把常驻压到 ~222 MB 量级（2B）。

**互斥（同时开会拒绝或静默失效）**

| 组合 | 结果 |
|---|---|
| `--kv-q4` × `--sparse-attn` | 互斥（稀疏 decode 要求 KV 非 q4） |
| `--spec` × {`--sparse-attn`, `--l3-evict`, `--batch-max`} | 互斥（spec 仅贪婪文本单路） |
| 加密 VQF × {`VLLM_VQF_STREAM`, `VLLM_EW`} | 互斥（需全层驻留） |
| `VLLM_VQF_STREAM` × `VLLM_EW*` | 不并存（EW 接管层入口钩子） |
| Flash Attention × {q8-KV, 稀疏栈} | 不可达（`use_kv_q8=1` 恒定） |
| `--l3-evict` × `--prefix-kv` | 默认互斥；置 `VLLM_L3_PREFIX_REUSE=1` 后共存 |

**三条铁律**

1. 开 `--l3-evict` **必须**同时置 `VLLM_L3_PREFIX_REUSE=1`，否则前缀复用被静默打掉、多轮追问全量重算。
2. `--sparse-k` **≥ 32**（k=16 即质量失败：needle NO、ppl 6.2）。
3. 加密 VQF（VQF-Enc）⇒ **必须全层驻留**（不可用 `VLLM_VQF_STREAM`）。

## 推荐配置

以下均取自源文件出现过的组合；统一口径 sparse 默认 `k=32 / block=32 / probe=8`。

| 场景 / 模型 | 推荐 | 依据 |
|---|---|---|
| 单用户 / 服务端默认 | `--wmode q4 --sparse-attn --sparse-k 32` | KV 默认 q8，稀疏 prefill+decode 全开 |
| 质量优先 | `--wmode dual --sparse-attn --sparse-k 32` | prefill 用 Q8 混合，速度与 q4 几乎持平 |
| 多轮对话服务 | 上述 + `--disk-kv ./kv_disk --spec --spec-k 4` | 前缀复用（默认开）+ 重启复用 + 推测解码 |
| 重复文本 / 模板 | 上述 + `--spec-k 8` | 草稿命中率高时收益更大 |
| 2B（dual，4.16 GB，RAM 充足） | `--wmode dual --sparse-attn --sparse-k 32`；多轮追问再加组合① | RAM 足够，走质量档 + 默认稀疏 |
| 8B（q4，6.60 GB） | `--wmode q4 --sparse-attn --sparse-k 32`；多轮追问加组合①（板端 −89.5%~−90.5%） | 单用户默认 + P3 |
| 30B-A3B（q4，17.66 GB） | `VLLM_VQF_STREAM=1` 逐层 + 组合① + 组合⑤ | 源文件明确「30B 能被真正用起来的前提」 |
| 最小回退 / 排障（组合⑧） | `--no-prefix-kv`（并关稀疏/批/L3/spec） | 无优化基线 |

```bash
# 2B / 8B：组合① P3（L3 驱逐 × 前缀复用共存）
VLLM_L3_PREFIX_REUSE=1 ./vllm_shs --serve --port 18080 --device arm-rk3588-opi5 --auto-load \
  --sparse-attn --sparse-k 32 --l3-evict --l3-ratio 0.75 --l3-min-seq 128 --l3-path /mnt/emmc/l3bench

# 30B-A3B：逐层驻留 + 组合① + 组合⑤（MoE，须 q4 权重）
VLLM_VQF_STREAM=1 VLLM_L3_PREFIX_REUSE=1 VLLM_ACTQ=1 VLLM_MOE_BATCH=1 \
  ./vllm_shs --serve --port 18080 --device arm-rk3588-opi5 --auto-load \
  --sparse-attn --sparse-k 32 --l3-evict --l3-ratio 0.75 --l3-min-seq 128 --l3-path /mnt/emmc/l3bench

# 组合⑧最小回退基线
./vllm_shs --serve --port 18080 --device arm-rk3588-opi5 --auto-load --no-prefix-kv
```

## 口径警告

- **v0 热缓存数字显式标注**：源文档中「**省 4.6×~21.8×、prefill +11~25% / decode +121~259%**」是 **v0 时期的热缓存**（全层权重已在 RAM/页缓存）稳态数字，**不作 v1 结论**，不可与 v1.0 板端数字混比。源台账「有效优化组合」表中组合②的「权重 RSS 省 4.6×~21.8×」同属该 v0 口径。
- v0 = 2026-09-05，v1 未复测（v1 已移除 GGUF/safetensors 加载路径并引入逐层推理与 KV v2）；**v1.0 板端实测测点 = 2026-09-12**，本页 v1 数字均取此测点。
- 源文档为 **x86 基准机（8B，16 线程，2026-08-28）** 同条件对照的归因分析，跨时间绝对数值受热节流/后台负载影响（曾出现整体 1.5x 波动）；x86 分支仅供**功能自检与位级一致性对照**，绝对吞吐 / 加速比不可外推到板端。
- 单用户 prefill 的真正大头是 **GEMM**（8K 下占 ~71%、ATTN 仅 ~27%），故 ATTN 降 74% 时 prefill 总时长只降 11.3%；要再提单用户 prefill 速度，方向是权重量化/内核效率，而非注意力侧。
- 已知问题（与本页优化无关）：8K+ quality 路径间歇性 prefill 崩溃（在 5120/6400 及 512/2049 处复现过），属既有问题。
