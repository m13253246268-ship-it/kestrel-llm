# 构建与复现

本页讲三件事：**怎么构建**、**构建后怎么自检**、**怎么复现报告里的数字而不误用口径**。

---

## 1) 一级目标：aarch64（RK3588）

```bash
./build_rk3588.sh                    # 构建 + 复制到 ./vllm_kestrel
./build_rk3588.sh --run-tests        # 构建 + 运行 PASS/FAIL 自检
./build_rk3588.sh --static           # 全静态（零 .so 依赖）

# 或直接在板上：
cmake -B build-rk3588 && cmake --build build-rk3588 -j8

# x86_64 Linux 主机交叉编译（需要 gcc-aarch64-linux-gnu）
./build_rk3588.sh --cross
```

- 全静态构建（`-DVLLM_STATIC=ON`）产物 `ldd` 报 not a dynamic executable，可拷到任意
  aarch64 Linux 直接运行。
- 运行建议 `export OMP_NUM_THREADS=8`（RK3588：4×A76 + 4×A55）。
- 非 aarch64 / 非 x86-64 架构会在 `vllm_platform.h` **编译期报错退出**。

## 2) x86-64 分支（功能自检用，不是基准）

```powershell
powershell -ExecutionPolicy Bypass -File tools\check_x64.ps1
#   → 编译 + 跑 --test-l3 / --test-sparse 自检，退出码 0/1

powershell -ExecutionPolicy Bypass -File tools\build_x64.ps1 -Gcc D:\tools\mingw64\bin\gcc.exe
#   → 仅构建，产物 build-x64\vllm_kestrel_x64.exe
```

参数与环境变量：`-Gcc` / `VLLM_GCC`（gcc 路径）、`-OutDir` / `VLLM_X64_OUTDIR`（输出目录）。

> **用途边界（必须照实说）**：x86-64 分支只证明「**能编译 + 数值自检与 ARM 同源**」，
> **不证明 x86 可作为性能基准**。已知开放项：x64 偶发整请求卡死；且 L3 Q4 点积在 x86
> 无 AVX2 内核（走标量回退，**数值对、性能无意义**）。x86 上跑出的任何吞吐/加速比
> 都不能外推到板端。

## 3) 自检清单与期望值

| 命令 | ARM 侧同口径期望 | 说明 |
|---|---|---|
| `--test-l3` | **16 / 16 PASS，0 FAIL** | L3 分层驻留、Q4 打包/反量化、P3 前缀恢复的确定性对拍 |
| `--test-sparse` | **9 / 9 PASS，0 FAIL** | 稀疏注意力与精确 float / INT8-KV 的等价性对拍 |
| `--bench-mixed` | 以自检结果为准 | 换板/换版本首次运行建议跑 |

**换板或换版本首次运行，一律先跑自检并以此结果为准**，不要直接引用文档里的绝对值。

## 4) 复现性能数字的方法与纪律

复现入口就是引擎自带的开关，参数与模型路径逐条列在 [性能与基准](性能与基准.md#复现方法)。

三条纪律：

1. **先分版本**：v1.0 测点 = 2026-09-12；v0 测点 = 2026-09-05。v0 数据**不得**用于 v1 结论。
2. **先分口径**：`--stream-test`（32 token prefill + N token 贪心 decode，冷页缓存）与
   serve 稳态（含 KV 的进程峰值）是两套口径；纯权重 RSS 与 serve 峰值是两把尺子。
   同一个 30B 模型，纯权重口径是 23.2×，含 KV 的 serve 峰值口径是 12.8×——**不是矛盾，是口径不同**。
3. **说明环境**：是否 `drop_caches`（冷/热页缓存）、存储介质（eMMC / NVMe / SSD）、
   线程数。逐层推理的速度代价与「权重体积 ÷ 存储带宽」强相关，换介质结论会变。

## 已知坑：非 ASCII 路径会导致 x64 构建失败

**现象**：仓库 clone 到含中文（或其他非 ASCII 字符）的路径后执行
`tools\check_x64.ps1` / `tools\build_x64.ps1`，编译全部通过但链接失败：

```text
C:/mingw64/.../ld.exe: cannot open output file D:\项目\...\build-x64\vllm_kestrel_x64.exe: No such file or directory
collect2.exe: error: ld returned 1 exit status
rc=1
```

**原因**：MinGW `ld` 无法处理 `-o` 参数中的非 ASCII 绝对路径（控制台代码页 936 环境下）。
对照证据：`vqf_convert/build.bat` 在同一中文路径下用**相对输出名**（`-o vqf_conv.exe`）
就链接成功——问题只在 `-o` 收到非 ASCII 绝对路径时出现。

**绕过**：把产物输出目录指到纯 ASCII 路径，源码路径不用动：

```powershell
powershell -ExecutionPolicy Bypass -File tools\build_x64.ps1 -OutDir C:\vllm_x64_build
# 或设环境变量
$env:VLLM_X64_OUTDIR = 'C:\vllm_x64_build'
```

> aarch64 板端构建走 `build_rk3588.sh`，不受此问题影响；它只影响 Windows/MinGW 的
> x86-64 自检路径。

## 5) 独立复现记录（2026-09-12，x86-64 开发机）

以下为一次**从 Gitee 干净克隆**后的独立复核记录，供参考。**所有数字来自 x64 开发机，
不是板端**，不可与 [性能与基准](性能与基准.md) 的板端数字混比。

| 项 | 结果 |
|---|---|
| 拉取 | `git clone --branch v1.0.0-test` → detached HEAD `v1.0.0-test` = `13430cea`（2026-09-12） |
| 构建 | 需 `-OutDir` 指向 ASCII 路径后成功；产物 `vllm_kestrel_x64.exe` = 1,139,064 字节（x64 动态，非板端 0.8 MB 口径） |
| `--test-l3` | **16 PASS / 0 FAIL** |
| `--test-sparse` | **9 PASS / 0 FAIL** |
| 转换工具 | `vqf_convert/build.bat` 构建成功（`vqf_conv.exe` 161,665 字节）；用 `vqf_convert/test/mk_synth.py` 生成合成 safetensors 后成功转出 VQF v2 单文件（4,107,272 字节，`flags=0x23`） |
| 逐层 vs 全层（8B，6.60 GB VQF） | 全层 prefill 后权重 RSS **4,200,172 kB** → 逐层 **489,584 kB**，倍率 **8.58×** |
| 语义一致性 | 两档贪心 TOKIDS 序列**逐位一致**（与 README 的「语义不变」结论相符） |
| 逐层启动自证 | `[VQF-STREAM] enabled keep=1 nl=36 segs=11 per-layer=103.5MB`（8B 为 36 层） |

**本次未复现的（诚实标注）**：

- aarch64 / NEON 主目标与全部板端数字（1.11 GB、12.8×、822 s → 3.2 s 等）——本机无交叉
  编译器、无 RK3588 板卡。
- 30B-A3B 的 23.2× 倍率——本机无该 VQF 文件。
- 「逐层只支持明文 VQF、加密权重被拒」这条边界——未构造 VQF-Enc 权重验证。
- x64 逐层 decode 代价与板端差异明显（本机实测 +108%，README 板端 8B 为 +37%）——
  再次印证 x86 **不作性能基准**（无 AVX2 L3 内核 + 存储/页缓存条件不同）。
