# 术语与数据口径

本页是引用本项目数字前的**必读页**。分两部分：`术语表` 与 `数据口径`。

---

## 一、术语表

### 权重与格式

| 术语 | 含义 |
|---|---|
| **VQF v2** | 项目自研的权重单文件格式。v1 起引擎**只认它**：mmap 直挂、按需建页，启动不做「读权重 → 量化 → 重排」。由 `vqf_convert/` 从 safetensors / GGUF 转换而来 |
| **VQF-Enc** | VQF 的存储态加密形态：SM4-CTR + HMAC-SM3。加载需 `VLLM_VQF_KEY` |
| **SM2 供应链签名** | 内嵌在 VQF 文件中的签名，绑定权重来源；产出侧 `VLLM_VQF_SIGN_PRIV`，加载侧 `VLLM_VQF_SIGN_PUB` |
| **`--wmode`** | 转换时的量化档（如 `q4` / `q8` / `dual`），随模型文件固定，不在运行时改变 |

### 内存与驻留

| 术语 | 含义 |
|---|---|
| **全层驻留** | 权重的全部层的物理页都常驻内存（默认档） |
| **逐层推理** | v1 新增能力（`VLLM_VQF_STREAM=1`）：VQF 单文件仍以 mmap 直挂，但**每层权重只在参与计算时建立文件页，算完立即 `MADV_DONTNEED` 释放**，仅 keep 层（缺省 1 层）常驻。使**权重常驻 RSS 与模型体积/层数解耦** |
| **keep 层** | 逐层档下保持常驻的层数（缺省 1），由 `VLLM_VQF_STREAM` 的取值控制 |
| **KV v2 惰性分配** | v1 的 KV 底座策略：KV 随用随长，而非启动即按 `max_seq` 全量 `calloc` |
| **L3 分层驻留** | 把 KV block 驱逐到磁盘（`--l3-evict` 等），需要时回填 |
| **P3** | 「L3 驱逐 × 前缀复用共存」：`--l3-evict` + `VLLM_L3_PREFIX_REUSE=1` 必须共存，否则 L3 会静默打掉 prefix-kv |
| **组合①** | `--sparse-attn --sparse-k 32 --l3-evict --l3-ratio 0.75 --l3-min-seq 128 --l3-path <dir>` + 环境变量 `VLLM_L3_PREFIX_REUSE=1` |
| **组合⑤** | `VLLM_ACTQ=1 VLLM_MOE_BATCH=1`（MoE 专家激活量化 + 专家批量），只对 MoE（q4）权重有意义 |
| **两条正交的内存轴** | **权重驻留轴**（逐层推理）× **KV 分页轴**（KV v2 / L3），二者可叠加、收益同量级 |

### 推理与度量

| 术语 | 含义 |
|---|---|
| **prefill** | 处理输入上文的阶段 |
| **decode** | 逐 token 生成的阶段 |
| **TTFT** | 首 token 时间。在本项目的单请求口径下（300 token 上文 + 32 token 生成），表中热 TTFT 与热 prefill 取值相同 |
| **tpot** | 每 token 输出时间（time per output token） |
| **贪心 TOKIDS** | 贪心解码得到的 token id 序列；项目用它做**逐位一致性**对拍 |
| **位级一致 / 逐位一致** | 两种配置下输出 token id 序列完全相同（可对 md5）。逐层推理声称「语义不变」，靠的就是它 |
| **attestation（schema 3）** | 逐响应出证：每个响应携带凭证，magic `VLLM-AT-3`，**含请求原文绑定**（`body_sha = SM3(客户端原始请求体)`） |

### 平台与内核

| 术语 | 含义 |
|---|---|
| **RK3588** | 4×Cortex-A76 + 4×Cortex-A55，本项目当前开发、优化与基准测试平台（**非唯一可运行设备**） |
| **NEON / dotprod / fp16** | aarch64 的 SIMD 与相关扩展，引擎的手写量化 GEMM/GEMV 内核基于它 |
| **`vllm_tp`** | 自研线程池（引擎核心并行用），替代 OpenMP |
| **`stb_image.h`** | MIT 单头文件图片解码器，代码内少数第三方之一 |
| **eMMC** | 板端常见存储介质；逐层推理的速度代价与「权重体积 ÷ 存储带宽」强相关，换 NVMe 结论会变 |

## 二、数据口径

### 2.1 版本分区（最重要）

| 分区 | 测点 | 适用范围 |
|---|---|---|
| **v1.0** | **2026-09-12** | 逐层 vs 全层 × {2B / 8B / 30B-A3B} × {组合⑧基线, 组合①, 组合①+⑤}，14 个 serve 配置点 |
| **v0** | 2026-09-05 | 冷启动 / 8K 长上下文 / KV 恢复 / 与 llama.cpp 同机对照 |

**不得混用的原因**：v1 移除了 GGUF/safetensors 加载路径，并引入逐层推理与 KV v2，
**冷启动、常驻内存、长上下文与多轮 prefill 的口径都已变化**。v0 的绝对值只作历史参考。

> 凡标注「（v0 测点）」的数字，**不得用于 v1 的任何结论**，也不要与 v1 数字混比。

### 2.2 页缓存口径：冷 vs 热

| 口径 | 做法 | 能说明什么 |
|---|---|---|
| **冷页缓存** | 每个配置点先 `sync; echo 3 > /proc/sys/vm/drop_caches` 再跑 | 含从存储读入 GB 级权重的全部开销，是「首次前向」的真实成本 |
| **热缓存稳态** | 权重已在 RAM/页缓存 | 只付算力。**v0 的「省 4.6×~21.8×、prefill +11~25% / decode +121~259%」属于这一口径** |

两者**不可混比**。`--stream-test` 是冷页缓存；serve 稳态表的「冷 / 热」是同一进程内
先 `drop_caches` 后连发同一请求。

### 2.3 内存口径：纯权重 RSS vs serve 峰值

| 口径 | 含义 | 30B 示例 |
|---|---|---|
| **纯权重 RSS** | 只算权重常驻（`--stream-test`） | 11.73 GB → 0.51 GB，**23.2×** |
| **serve 峰值（含 KV）** | 服务进程峰值，含 KV 缓存 | 14,228,868 kB → 1,112,500 kB，**12.8×** |

逐层推理真正解耦的是**权重**；KV 由 KV v2 惰性分配另管——所以含 KV 的倍率必然更小。
引用时必须写明是哪一把尺子。

### 2.4 其它必须交代的环境项

- 线程数（板端 `--threads 8`）、存储介质（eMMC）、`OMP_NUM_THREADS`。
- 是否跑了自检、自检版本（换板/换版本以自检结果为准）。
- x86-64 的任何数字**只作功能自检与位级一致性对照，不作性能基准**。

### 2.5 测量纪律小结

1. 数字只在 `docs/` 的原始报告与 README「性能」一节产生；其它文档只引用、不发明。
2. 引用时带全三个前提：**版本 + 页缓存口径 + 内存口径**。
3. 不漂亮的数字照实写：逐层的速度代价、30B 的低绝对速度、x86 的开放项，都是项目自陈的边界。
