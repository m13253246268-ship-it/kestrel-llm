# 常见问题

## 加载与格式

**Q：v1 还能直接加载 safetensors 或 GGUF 吗？**

不能。v1 起引擎是**纯 VQF 运行时**：只加载自研 VQF v2 单文件（mmap 直挂），内置的
GGUF / safetensors 加载与引擎内转换路径已删除（v0 曾支持）。转换职责移交随版工具
`vqf_convert/`。详见 [快速上手](https://gitee.com/pei-xiaoguang/kestrel-llm/wikis/快速上手#2-权重就位)。

**Q：为什么逐层推理必须用明文 VQF？**

逐层推理靠「丢弃干净文件页、内容由文件重建」保证语义不变（TOKIDS 逐位一致）。加密权重
（VQF-Enc / 内嵌 SM2 签名）走的是解密后加载路径，无法按文件页重建，因此引擎会**显式拒绝**
逐层档，必须全层驻留。这是设计边界，不是 bug。

**Q：`--wmode` 该怎么选？**

转换时决定，随模型文件固定。设备探测会给出建议档（启动日志的 `recommended_wmode=`）。
明文档与混合档的具体机制与代价见 [优化配置与边界](https://gitee.com/pei-xiaoguang/kestrel-llm/wikis/优化配置与边界)。

## 内存与性能

**Q：为什么文档里出现过两组倍率（「省 4.6×~21.8×」和「4.6× / 8.9× / 23.2×」）？**

**口径不同，不是矛盾**。

- 「4.6× / 8.9× / 23.2×」是 **v1.0（2026-09-12）** 的 `--stream-test` **冷页缓存、纯权重
  RSS** 口径。
- 「省 4.6×~21.8×、prefill +11~25% / decode +121~259%」出自
  [docs/优化配置与边界说明.md](../docs/优化配置与边界说明.md)，是 **v0 时期的热缓存稳态**
  口径，**不作 v1 结论**。

引用数字前请先读 [术语与数据口径](https://gitee.com/pei-xiaoguang/kestrel-llm/wikis/术语与数据口径)。

**Q：同一个 30B 模型，为什么一处写 23.2×、另一处写 12.8×？**

前者是**纯权重 RSS** 倍率（11.73 GB → 0.51 GB），后者是 **serve 峰值（含 KV）** 倍率
（14,228,868 kB → 1,112,500 kB）。逐层推理真正解耦的是**权重**；KV 底座由 KV v2 惰性分配
另管，所以含 KV 的倍率会小一些。

**Q：我开了 `--l3-evict`，多轮追问反而变得极慢？**

`--l3-evict` 必须配合环境变量 `VLLM_L3_PREFIX_REUSE=1`，**二者共存才有 P3 收益**；
否则 L3 驱逐会静默打掉 prefix-kv，多轮追问将全量重算 prefill。

**Q：30B-A3B 真的能在 16 GB 板上用吗？**

能跑起来，但要区分「能跑」和「好用」：

- 全层档 serve 峰值 14.2 GB，已顶到 16 GB 板（MemTotal 15.6 GiB）的内存上限，几乎不留
  KV 与进程余量；逐层档把同一模型压到 **1.11 GB**。
- 但 **30B-A3B 在本板的绝对速度很低，这是硬件边界而非实现缺陷**：无优化基线一轮
  300 token 上文要 620 s（tpot 2,240 ms，≈0.45 tok/s）。
- 实用做法是「逐层驻留（1.11 GB）+ 组合① + 组合⑤」——组合⑤ MoE 把首轮降到 23 s、
  追问降到 3~5 s，这是 30B 能被真正用起来的前提。
- **2026-09-12 补充测点（短请求，权重在 SanDisk microSD 上）**：
  - 默认（`enable_thinking` 开，与 HF 一致）22 token 上文 → 32 token 输出：热态 TTFT 3.3 s、
    端到端 20.8 s、峰值内存 0.92 GB（VmHWM 918,300 kB）——**但这 32 token 全在思考段内，没出答案**。
  - **关掉 thinking 后**（`"enable_thinking": false`）：TTFT 3.1 s、**24.5 s 拿到完整的
    一句话答案**（自然 EOS 结束，实出 40 token）、峰值 0.91 GB（VmHWM 910,748 kB）。这才是"能用"的数字。
  - thinking 开 + `max_tokens=256`：跑满 256 token **仍未出现 `</think>`**，一次问答实际
    要预留 300+ token、约 3~4 分钟。
  - 冷态（`drop_caches` 后首次）TTFT 195.7~211.5 s，是首次从 SD 卡读入 17.66 GB 权重
    （其中权重数据段 16.8 GB）的一次性成本。
  - **VmHWM 是进程历史最高水位**（单调不减），故逐轮上升属正常记录方式；单轮稳态占用是否
    回落需 `VmRSS` 逐轮采样，**尚未做，列为开放项**。详见
    [性能与基准](https://gitee.com/pei-xiaoguang/kestrel-llm/wikis/性能与基准)。

**Q：2B / 8B / 30B 三档，我该选哪个？**

**推荐 8B**（2026-09-12 实测，见 [性能与基准](https://gitee.com/pei-xiaoguang/kestrel-llm/wikis/性能与基准) §4）：

- **省内存的收益拿满**：逐层档权重常驻 4.19 GB → **0.48 GB（8.7×）**，serve 峰值 **0.82 GB**。
- **热态稳定有物理保障**：它的权重 6.15 GiB **小于 15.6 GiB 物理内存**，页缓存装得下，所以
  热态不必赌运气——实测连续 5 次同请求，**TTFT 1.95 s、tpot 377 ms，波动仅 ±1.8% / ±0.13%**。
- **冷启动一次性成本低**：73 s（30B 为 195~211 s），成本 ∝ 权重体积 ÷ 介质带宽。

2B 省得少（4.6×）但更快，适合"内存不紧张、要最快"；**30B 是能力上限档，不是推荐档**——
16.4 GiB 权重装不进 15.6 GiB 页缓存，热态稳定性没有物理保障，且需关 thinking 才有短问答效果。

> **8B 档务必用 `--threads 4`**：RK3588 是 4×A76 + 4×A55，`--threads 8` 会把 4 个 A55 小核
> 拉进 GEMM 并行区，8B 全层 decode 从 186 ms/tok 退化到 431 ms/tok（差 2.3×）。

**Q：x86 上跑得挺快，板端也这样吗？**

不能这么推。x86-64 分支**只用于功能自检与位级一致性对照，不作性能基准**：x64 偶发整请求
卡死，且 L3 Q4 点积在 x86 无 AVX2 内核（走标量回退，数值对、性能无意义）。实测差异也很
直观：8B 逐层档的 decode 代价在板端是 +37%，在 x64 开发机上是 +108%。

**Q：逐层推理到底牺牲了多少速度？**

板端 serve 稳态（热档）tpot：**+38.7%（2B）/ +34.6%（8B）/ +18.2%（30B）**；热档 prefill
只 +3.3% / +2.7% / +0.4%。代价随「权重体积 ÷ 存储带宽」上升——本机 8B/30B 权重在
**SanDisk microSD（62.7 MB/s）**、2B 与 L3 在 **eMMC（240 MB/s）**，换介质结论会变。
换来的常驻内存倍数是 4.6× / 8.9× / 23.2×（纯权重 RSS）。

> **线程口径会影响结论**：上表是 serve 稳态（`--threads 8`）口径。8B 换用 `--threads 4` 后
> 全层 decode 从 431 降到 186 ms/tok——**同一张表内必须同线程口径，否则差 2×**。

## 模型支持

**Q：支持 Llama 或旧版 Qwen 吗？**

**未经适配与验证。** 引擎针对并实测验证的是两类 Qwen3 架构：**Qwen3-VL 系列（2B / 8B）**
与 **Qwen3-MoE 系列（如 Qwen3-30B-A3B，文本）**。其他架构转换可能报错或输出不可用，
请勿据此推定为通用推理引擎。

**Q：0.8 MB 是怎么做到的？和其他引擎比体积呢？**

标准构建仅需 gcc + libm，无第三方运行时；全静态构建 `ldd` 报 not a dynamic executable。
代码内的第三方只有 `stb_image.h`（MIT）与 llama.cpp 派生 4x4 asm 内核（MIT），见
[LICENSE](../LICENSE) 第三节。

**但跨框架比体积口径太乱，本项目不做跨框架体积比较**——只报自身数字。

## 构建与部署

**Q：Windows 下 `check_x64.ps1` 报 `ld.exe: cannot open output file ...: No such file or directory`？**

仓库路径含中文。MinGW `ld` 无法处理 `-o` 参数里的非 ASCII 绝对路径。
用 `-OutDir` 或 `VLLM_X64_OUTDIR` 把输出指到纯 ASCII 目录即可，源码路径不用动。
详见 [构建与复现](https://gitee.com/pei-xiaoguang/kestrel-llm/wikis/构建与复现#已知坑非-ascii-路径会导致-x64-构建失败)。

**Q：换了一块板子，怎么确认能跑？**

先跑内置自检 `--test-l3` / `--test-sparse` / `--bench-mixed`，**以自检结果为准**，不要直接
引用文档里的绝对值。设备画像（线程绑定、核心数）与性能档按 RK3588 验证。

**Q：启动日志出现 `[ATTEST] WARN`？**

可验证推理的密钥目录放在了不支持 POSIX 权限的文件系统（vfat/exfat 等）上，`chmod` 不生效，
私钥会变为世界可读。请把密钥目录放到 ext4/f2fs 等文件系统上。

**Q：NPU 能用吗？**

可选。默认后端是零第三方依赖直驱（自研写 stock rknpu 内核驱动）。首次使用需先做板端校准
`./vllm_kestrel --npu --npu-selftest --perf-only`；寄存器命令表未校准通过前，提交路径保持
禁用并自动回退 CPU。
