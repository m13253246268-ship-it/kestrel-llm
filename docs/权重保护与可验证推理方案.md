# 权重保护与可验证推理方案

> 版本：v1.0（2026-09-11，对齐 GitHupSRC 发布树；VQF v2）
> 主题：vllm_kestrel 的三道安全防线——**存储态加密（VQF-Enc，防拷走）、供应链签名（SM2，防替换）、
> 推理出证（attestation schema=3，防伪造/防篡改）**——及其相互关系、端到端使用与统一安全边界。
> 实现位置：[vqf.c](../src/model/vqf.c) / [vqf_format.h](../include/model/vqf_format.h) /
> [vllm_attest.c](../src/serve/vllm_attest.c) / [vllm_crypto.c](../src/common/vllm_crypto.c)。
> 关联文档：[技术文档.md](技术文档.md)（引擎总体架构，§4.5/4.6/6.5 与本档对应）。

## 0. 总览：三道防线与相互关系

要回答的安全问题，恰好是三类审计/取证诉求：

| 资产 | 威胁 | 防线 | 机制 |
|---|---|---|---|
| 权重文件（拷走/拔卡/dump eMMC） | 离线破解权重 | **A. 存储态加密** | SM4-CTR 密文落盘 + HMAC-SM3 防篡改 |
| 模型（被替换/投毒/掉包） | 伪模型以假乱真 | **B. 供应链签名** | SM2 对权重明文摘要签名，验签锚定非对称公钥 |
| 推理输出（记录被改/出处伪造/抵赖） | 归档不可信 | **C. 推理出证** | SM3 转录摘要 + SM2 设备签名，逐请求发凭证 |

一句话：**加密保密、签名保真、出证保实**。三者层次不同、互不替代：

```
   发布方（离线）                      设备（RK3588）                      验证方
 ┌──────────────┐   VQF v2 单文件   ┌────────────────────────┐  凭证   ┌──────────────┐
 │ 原模型 safetensors                │ VLLM_VQF_KEY 解密      │         │ 请求原文      │
 │  └→ 量化+repack → 明文 VQF 内容    │  ├─ HMAC 认证+原位解密 │         │ 输出文本      │
 │  ├─ 口令加密（防线 A，可选）        │  └─ SM2 验签(防线 B)： │         │ attest 凭证   │
 │  └─ SM2 签名 D（防线 B，可选）      │     公钥=内嵌/注入     │         │ 设备公钥      │
 │   私钥 d 永不出此机                 │   ├─ model_fp 固化    │         │  └─ 离线复算验签│
 └──────────────┘                    │   └─ 每次响应 SM2 签名  │         └──────────────┘
                                     │     （防线 C）         │
```

**正交性**（设计要点）：

- **B 与 A 正交**：签名对象是「明文逻辑内容」的摘要 D，与口令/加密无关——同一份签名对明文版
  与任意口令加密版都成立。口令泄露（A 失效）不连坐 B；反之攻击者即使能解密（拿到口令）也
  没有签名私钥，无法伪造一份有效签名去替换模型。
- **C 与 A/B 关系**：C 的 `model_fp`（模型指纹）锚定「目录 + config + 文件尺寸」层；若模型是
  **签名 VQF**（B 开启并验签通过），则权重级信任由 B 提供，C 的指纹与 B 形成「来源签名 →
  响应背书」的完整链。A 是保密层，不参与 C 的语义，但防止模型文件本身被离线研究/窃取。
- 三层责任划分：完整性/防篡改（HMAC，防无口令者改字节）→ 存储加密（SM4，防无口令者读）→
  供应链（SM2 私钥，防无签名私钥者替换）→ 出证（设备私钥，防伪造成绩记录）。任何一层失守
  不自动导致其余层失效。

**按场景启用矩阵**：

| 场景 | 启用 | 说明 |
|---|---|---|
| 本地/开发验证 | 全部默认关 | 明文 VQF mmap 秒级加载、零额外开销 |
| 模型分发防拷走 | A（`VLLM_VQF_KEY` 转换加密） | 一次性加载成本 ~92s，见 §3 |
| 防模型被替换/投毒 | B（签名 VQF + 公钥验签） | 推荐与 A 同开（验签近乎零成本），见 §4 |
| 医疗/法务留证 | C（`VLLM_ATTEST=1`）+ 可选 B | 逐响应凭证离线验签，见 §5/§6 |
| 全套合规部署 | A + B + C | 转换一次加密签名 → 设备验签出证 → 验证方验凭证 |

> 三者默认均关闭，不影响现有 mmap 加载与推理路径；逐项开启见 §6。

## 1. 威胁模型与设计取舍

### 1.1 资产与攻击者

| 攻击者能力 | 能做什么 | 被哪道防线拦 |
|---|---|---|
| 拿到模型文件（无口令） | 读权重、改字节 | A（密文 + HMAC 认证失败拒绝加载） |
| 持有口令 | 解密、改文件并重算 HMAC | B（无签名私钥无法伪造有效签名） |
| 替换整个模型文件 | 用旧版/投毒权重冒充 | B（`sig.pub`/digest/验签失败拒绝加载） |
| 控制设备（root/内核后门） | 伪造任意响应、偷设备私钥 | C 之外无解（信任根上限，见 §7） |
| 事后改归档记录 | 篡改请求/输出/时间 | C（验签必失败） |

### 1.2 诚实起点（明确不做的事）

- **不做运行时密态计算**：权重解密后驻留 RAM 参与推理，A 是「存储态加密 + 加载解密」，
  不是全同态/密态推理（HE 研究内核见 [技术文档.md](技术文档.md) §2.1，另行成文）。
- **不做 ZK/STARK 式「计算本身可验证」**：RK3588 上会产生不可接受的 TTFT 退化；C 做的是
  工程/司法层面的完整性 + 真实性 + 责任追溯——恰是医疗/法务记录合规的核心诉求。
- **不解决信任根物理安全**：若攻击者能同时替换引擎二进制（连同内嵌公钥）与模型，
  B/C 均无法防护（见 §7.2/§7.5）。

## 2. 密码学底座与信任根

全链路国密，纯 C11、零外部依赖、无内联汇编，aarch64 与 x86 均可编译；位级正确性由独立
KAT 驱动（国密标准向量）逐字节验证（red line）。实现：[vllm_crypto.c](../src/common/vllm_crypto.c) /
[vllm_crypto.h](../include/common/vllm_crypto.h)。

| 用途 | 算法 | 标准依据 |
|---|---|---|
| 数据区加密（防线 A） | SM4-CTR | GB/T 32907-2016 |
| 完整性/认证（防线 A） | HMAC-SM3 | GB/T 15852.2（RFC 2104 构型） |
| 口令派生（防线 A） | SM3（单次，见 §7.1） | GB/T 32905-2016 |
| 摘要（防线 A/B/C 共用） | SM3 | GB/T 32905-2016 |
| 签名/验签（防线 B/C） | SM2 | GM/T 0003-2012 |

SM2 签名 API（[vllm_crypto.h](../include/common/vllm_crypto.h#L67-L84)）：

```c
int vc_sm2_pub_from_priv(const uint8_t priv[32], uint8_t pub[64]); /* priv→pub */
int vc_sm2_sign(const uint8_t priv[32], const uint8_t *msg, size_t msglen,
                const uint8_t *id, size_t idlen,
                const uint8_t k[32], uint8_t r[32], uint8_t s[32]);
int vc_sm2_verify(const uint8_t pub[64], const uint8_t *msg, size_t msglen,
                  const uint8_t *id, size_t idlen,
                  const uint8_t r[32], const uint8_t s[32]);
```

要点：

- 签名内部先算 `Z_A = SM3(ENTL || ID_A || a || b || Gx || Gy || Px || Py)`，再算
  `e = SM3(Z_A || M)`（[vllm_crypto.c](../src/common/vllm_crypto.c#L565-L581)）。
  **ID_A 是签名的一部分，两侧必须一致**。本仓库 ID 约定：VQF 签名 `VQF_SM2_ID = "vllm-kestrel-vqf"`
  （[vqf_format.h](../include/model/vqf_format.h)）；出证 `"VLLM-ATTEST-1"`（schema=3）。
- `k` 是外部传入的随机数。生产签名必须用安全随机 k 且**每次唯一**（k 复用直接泄露私钥）；
  引擎经 `vc_secure_rand()`（Linux `getrandom(2)` 封装）生成（[vqf.c](../src/model/vqf.c#L441)），
  固定 k 仅用于 KAT 复现。xorshift128 等非密码学随机源**不能**用于签名。

信任根分两层：

1. **权重锚点**：签名 VQF 的验签公钥——运行时 `VLLM_VQF_SIGN_PUB`（128 hex）优先，编译期
   `VLLM_SM2_PUB_HEX` 兜底（`vqf_trusted_pub()`，[vqf.c](../src/model/vqf.c#L91-L100)）；
   无信任公钥时对签名模型 fail-closed。
2. **设备背书**：设备侧 SM2 私钥 `vllm_attest.priv`（0600）逐响应签名；私钥永不上行，
   验证方只持公钥 `vllm_attest.pub`。

## 3. 防线 A：权重存储态加密（VQF-Enc）

### 3.1 目标

- 防模型文件被盗/拷走：落盘即密文，拔卡/dump eMMC 无法恢复可用的量化权重。
- 防篡改：头/目录/数据区任何修改被 HMAC-SM3 认证拦截。

明文与密文 VQF 共用同一布局（密文长度 == 明文长度，mmap 直挂布局不变）。

### 3.2 密钥派生

口令经环境变量 `VLLM_VQF_KEY` 传入（[vqf.c](../src/model/vqf.c#L62-L70)）：

```c
static int vqf_enc_derive(const char *pass, uint8_t sm4key[16], uint8_t hmackey[16]) {
    if (!pass || !pass[0]) return 0;          /* 口令为空 → 明文模式 */
    uint8_t mat[32];
    vc_sm3(pass, strlen(pass), mat);          /* 口令 → SM3 摘要 32B */
    memcpy(sm4key,  mat,     16);             /* [0..16)  SM4-CTR 密钥 */
    memcpy(hmackey, mat + 16, 16);            /* [16..32) HMAC-SM3 密钥 */
    return 1;
}
```

一份口令派生两个独立用途密钥（SM4 + HMAC）；`VLLM_VQF_KEY` 未设/为空 → 明文模式（向后兼容）。
派生为**单次 SM3**，无盐无迭代——弱口令可被离线暴破，生产应使用高熵口令（§7.1）；
同一口令对不同文件派生相同密钥，但**每文件 IV 独立**（见下），不跨文件复用密钥流。

### 3.3 文件结构（[vqf_format.h](../include/model/vqf_format.h)）

| 偏移 | 字段 | 说明 |
|---|---|---|
| 0 | `magic` | `VQF_MAGIC (0x57465146 "VQFW")` |
| 4 | `version` | `VQF_VERSION = 2`（v2 头部追加 `VQFSig` 签名块，供防线 B） |
| 8 | `flags` | `1<<7 = VQF_FLAG_ENC` 标识加密；`1<<8 = VQF_FLAG_SIGNED` 标识签名 |
| 12 | `n_tensors` | 张量数 |
| 16 | `arch` | `VQFArch` 模型属性（自包含，164B） |
| 184 | `data_offset` | 数据区起始（4KB 页对齐） |
| 192 | `file_len` | 文件总长（**不含尾部 tag**） |
| 200 | `enc_iv[16]` | SM4-CTR 初始计数器（加密时有效） |
| 216 | `enc_rsvd[16]` | 保留 |
| 232 | `sig` | `VQFSig` SM2 签名块（200B，防线 B，见 §4.2） |

头部共 432B（`_Static_assert` 守卫），后接目录区（`VQFTensor` × n，64B/个，从 448 起），
头+目录固定 4KB 页对齐。整体布局：

```
[0 .. data_offset)        头部 + 目录（明文，参与 HMAC/摘要 D）
[data_offset .. file_len) 数据区（SM4-CTR 密文；明文文件为明文）
[file_len ..)             尾部：加密 → HMAC-SM3 tag(32B)；明文 → FNV-1a checksum(8B)
```

明文文件尾为 8B FNV-1a checksum（弱完整性，默认跳过，`VLLM_VQF_CHECK=1` 才校验）；加密文件尾为
32B HMAC-SM3（强认证）。

### 3.4 加密写出（[vqf.c](../src/model/vqf.c#L248-L330)）

1. 读 `VLLM_VQF_KEY`，口令非空则派生密钥、生成 16B IV，置 `VQF_FLAG_ENC`。
2. IV 写入 `header.enc_iv`；来源为 xorshift128（种子取 time+地址），只提供**每文件唯一性**
   （混淆级，非密码学 IV，见 §7.3）。
3. 数据区逐张量、1MB 分块 SM4-CTR 加密落盘（[vqf_emit_enc](../src/model/vqf.c#L102-L116)），
   同一连续计数器贯穿整数据区，同时把**密文**流式喂入 HMAC。
4. 回填 `file_len`（其值晚于数据写出才确定，故**不纳入 HMAC**，由加载侧 size mismatch 兜底）。
5. 文件尾追加 32B HMAC-SM3 tag。

**HMAC 认证范围**（[vqf.c](../src/model/vqf.c#L344-L353)）：头部 `VQFHeader` 全体（`file_len` 与
`sig` 两个**回填字段**按 0 参与；`arch/flags/enc_iv/data_offset/n_tensors` 全员参与）+ 目录区
（明文）+ 数据区（密文）。因此篡改 arch、enc_iv、flags、目录任字段或数据区任字节均导致 tag
校验失败。

### 3.5 加载解密 + 校验（[vqf.c](../src/model/vqf.c#L549-L566)）

1. 校验 `magic/version`；读 `flags` 判断加密。
2. size mismatch 兜底：`file_len + tag_len == 实际文件尺寸`（防截断/拼接）。
3. 加密文件：无口令拒绝加载（`encrypted model requires VLLM_VQF_KEY`）。
4. **单遍 HMAC 认证 + 原位解密**：`mprotect` 使 mmap 可写（`MAP_PRIVATE` COW，磁盘文件不变），
   边算 HMAC（对密文）边 SM4-CTR 原位解密（1MB 分块）；tag 不一致报
   `HMAC-SM3 mismatch (tampered or wrong key)` 并拒绝。
5. 返回可用的 mmap 直挂权重（零拷贝、布局不变）。

防篡改小结：

| 篡改对象 | 拦截机制 |
|---|---|
| 文件头（arch/flags/enc_iv 等） | HMAC 覆盖头部（`file_len`/`sig` 回填字段按 0 参与） |
| 目录区（offset/bytes/qtype） | HMAC 覆盖目录 |
| 数据区任意字节 | HMAC 覆盖密文数据区 |
| 文件截断/拼接 | `file_len + tag_len` size mismatch 兜底 |
| 布局 flags 错配 | `vqf_cur_flags` vs 文件 flags 一致性校验（[vqf.c](../src/model/vqf.c#L702-L713)） |

### 3.6 验证与性能（板端，RK3588）

- KAT：SM3/SM4 按国密标准向量、SM2 按 GM/T 0003-2012 附录 A.2 签名示例（固定 k 复现），
  逐字节验证（独立驱动 `vllm_crypto_test.c` 未随仓库分发，可向作者索取）。
- 端到端：板端「加密 → 加载解密 → 推理输出逐 token 一致 + 负例（错口令/篡改 arch/enc_iv/
  数据区均拒载）」8 项全 PASS。
- 实测加载：明文 VQF ≈1.27~1.29 s；加密 VQF ≈92.3~92.5 s（一次性全量解密 + HMAC 校验，
  eMMC 读 + CPU 计算）；推理阶段不再重复承担。

### 3.7 配置入口

| 环节 | 位置 | 说明 |
|---|---|---|
| 导出加密 / 签名 VQF | 离线工具 `vqf_convert/`（[conv_main.c](../vqf_convert/src/conv_main.c)） | 一条命令完成：设 `VLLM_VQF_KEY` → 加密（VQF-Enc）；设 `VLLM_VQF_SIGN_PRIV` → 内嵌 SM2 签名；二者可叠加 |

| 加载加密 / 签名 VQF | 管理页 `/admin/`（[admin.html](../src/serve/admin.html)） | 「VQF 加密口令」写入配置 `env.VLLM_VQF_KEY`；验签公钥 `VLLM_VQF_SIGN_PUB`（或编译期内嵌） |

> 已实测：`vqf_conv` 产出加密+签名 VQF 后，引擎加载日志为

> 错口令 / 篡改数据字节均被 HMAC-SM3 拒绝。

## 4. 防线 B：权重供应链签名（SM2，VQF v2）

### 4.1 相对 HMAC 补充了什么

| 能力 | HMAC-SM3（防线 A 内） | SM2 签名（本防线） |
|---|---|---|
| 防篡改（改字节） | ✅ | ✅（叠加） |
| 密钥类型 | 对称（口令派生，双方同钥） | 非对称（私钥签名 / 公钥验签） |
| 防「替换模型」 | ❌ 持有口令者即可重签 | ✅ 无签名私钥者无法伪造 |
| 私钥落点 | 口令在设备侧 | **仅发布方离线持有，设备只存公钥** |

HMAC 能防「不知道口令的人改文件」，但**持有口令的人仍可替换整个模型并重算 HMAC**；
SM2 把「模型确实出自发布方」锚定在非对称私钥上。不做运行时逐 token 验签（验签是一次性加载期
动作）。

### 4.2 签什么：明文逻辑内容的摘要 D（与口令无关）

签名对象是**模型权重本身**，不是某个加密实例：

```
D = SM3( header_canonical ‖ directory ‖ plaintext_data )
header_canonical = VQFHeader 中 **flags 含 `VQF_FLAG_SIGNED`**、file_len=0、sig 块全 0 的头
（flags 按"最终已签名"口径；file_len/sig 与 HMAC 口径一致）
```

为什么不用「签 HMAC tag」：HMAC 密钥由口令派生，不同口令 → 不同 tag → 签名失效，会把
签名与加密耦合。签明文摘要 D 则**签名一次、任意口令加密**，A 与 B 完全正交。

文件格式增量（[vqf_format.h](../include/model/vqf_format.h)）：`VQF_FLAG_SIGNED (1u<<8)`；
头部 `VQFSig`（64+32+32+32+32+4+4 = 200B：`pub[64]/r[32]/s[32]/digest[32]/id[32]/id_len/rsvd`）
随 `VQFHeader` 追加（232 → 432B），`dir_off` 相应 256 → 448（64B 对齐，自动重算）；
`VQF_VERSION` 升 **2**，加载侧按 version 判定，旧 v1 引擎对未知 `VQF_FLAG_SIGNED` 位自然忽略。

### 4.3 密钥管理

| 角色 | 持有什么 | 位置 |
|---|---|---|
| 发布方（离线） | SM2 私钥 `d` | 离线密钥机/构建机，不进入设备 |
| 设备（RK3588） | SM2 公钥 `P`（64B） | 运行时 `VLLM_VQF_SIGN_PUB` 注入或**编译期内嵌**（`VLLM_SM2_PUB_HEX`） |

公钥内嵌是信任根：文件内 `sig.pub` 只作诊断，验签**必须**用内嵌/注入的可信公钥。

### 4.4 写侧流程（`vqf_write`，签名在转换时与加密同单遍完成）

```
1. 读 VLLM_VQF_KEY 派生 SM4/HMAC 密钥（若加密，见 §3）
2. 若 VLLM_VQF_SIGN_PRIV（64 hex 私钥，来自离线签名器，非设备环境）非空：
     置 VQF_FLAG_SIGNED；读入私钥 d（[vqf.c](../src/model/vqf.c#L272-L282)）
3. D = SM3_init(); D.update(header_canonical); D.update(directory)
4. 逐张量流式写出：D.update(明文)；若加密则 SM4_CTR(明文)+HMAC.update(密文)+write
5. D.final → digest[32]
6. k = vc_secure_rand()（getrandom）；(r,s) = vc_sm2_sign(priv, D, 32, ID, ...)
   （[vqf.c](../src/model/vqf.c#L441)）
7. 填 sig 块（pub/r/s/digest/id/id_len）；写 header（file_len + sig 就绪）
8. 追加 HMAC tag（若加密）
```

注意顺序：`digest` 计算时 `sig` 块尚未填充，故 `header_canonical` 中 `sig` 按全 0 处理；验签侧
同理（与 `file_len=0` 的「回填前按 0」一致）。
**`flags` 按「最终已签名」口径参与**：写侧在 `flags |= VQF_FLAG_SIGNED` 之后才把 header 喂入
摘要（[vqf.c](../src/model/vqf.c#L288)）；离线补签工具 [vllm_vqf_sign.c](../tools/security/vllm_vqf_sign.c)
打开未签名文件时必须先 `flags |= VQF_FLAG_SIGNED` 再算摘要——否则签名时 canonical 无 SIGNED、
验签/加载时 header 已带 SIGNED，两侧摘要恒不一致（2026-09-07 板端真机踩坑后已修复）。

### 4.5 读侧流程（`vqf_load` 验签，[vqf.c](../src/model/vqf.c#L575-L697)）

```
1. 读 header，判 VQF_FLAG_SIGNED；do_verify = signed && (enc || VLLM_VQF_VERIFY=1)
2. 加密：单遍 HMAC(密文) + 原位解密 + D.update(明文)；明文：全量读数据区 + D.update（见 §7.4）
3. D.final → digest
4. 快速自检：digest == header.sig.digest？不等直接拒绝（省一次 ECC）
5. vc_sm2_verify(P_trusted, D, 32, VQF_SM2_ID, r, s)；失败 → 拒绝加载
   "[VQF] SM2 verify failed (model replaced/tampered)"
6. 交叉校验：header.sig.pub == P_trusted？不一致默认拒绝（"[VQF] SM2 pub mismatch"）
7. 布局 flags 一致性（file vs 引擎，见 §3.5）
```

验签用 `P_trusted`（可信公钥），**不是**文件内 `sig.pub`。

### 4.6 离线签名/密钥工具链

[tools/security/vllm_vqf_sign.c](../tools/security/vllm_vqf_sign.c)（随仓库分发）：

```bash
gcc -O2 -Iinclude -Iinclude/common -Iinclude/model \
    src/common/vllm_crypto.c tools/security/vllm_vqf_sign.c -o vllm_vqf_sign
./vllm_vqf_sign --genkey          # 生成 SM2 密钥对（d / P）
./vllm_vqf_sign --pub <d_hex>     # 导出公钥 hex
./vllm_vqf_sign --sign <d_hex> --in <file> --out <sig>   # 离线对摘要签名（排障用）
./vllm_vqf_sign --verify <p_hex> --in <file> --sig <sig> # 验签（排障用）
```

端到端：`--genkey` → 用 `vqf_convert/` 转换时置 `VLLM_VQF_SIGN_PRIV=<privhex>`（内嵌签名，
可与 `VLLM_VQF_KEY=<口令>` 加密**叠加**）→ 设备侧以 `VLLM_VQF_SIGN_PUB=<pubhex>`（或编译期
内嵌 `VLLM_SM2_PUB_HEX`）加载验签。已有 VQF 需补签时才用 `vllm_vqf_sign --sign`。

> **离线补签口径（v1.0 修复）**：写侧 `vqf.c` 是先 `flags |= VQF_FLAG_SIGNED` 再算摘要；
> 离线补签工具打开的是**未签名**文件（`flags` 无 `SIGNED`），因此 `tools/security/vllm_vqf_sign.c`
> 必须先把 `SIGNED` 位置位、并清零 `sig` 字段后再算 canonical 摘要，否则补签产物在验签 /
> 引擎加载侧永远 digest mismatch。该修复已随 v1.0 落地。

### 4.7 性能影响

| 场景 | 附加成本 |
|---|---|
| 加密模型验签 | 摘要与解密同单遍合并，仅增 SM3 计算（SM3 轻于 SM4+HMAC），可忽略 |
| 明文模型验签 | 明文加载原为 mmap 懒加载（~1.3s 零全读）；验签**强制全量读**数据区（数 GB） |

建议：签名模型默认走加密（验签近乎零成本）；明文模型验签用 `VLLM_VQF_VERIFY=1` 显式开启
（默认关以保留 mmap 收益）。SM2 验签本身（两次标量乘，纯 C 大数）约几十 ms，相对整体加载可忽略。

## 5. 防线 C：推理出证（attestation，schema=3）

### 5.1 核心原理

每次推理响应打一张「数字凭证」：**SM3 转录摘要 + SM2 设备签名**。验证方只需保留请求原文、
输出文本、凭证 JSON、设备公钥即可离线复算验签。安全模型是「签名设备可信、设备私钥不泄露」。

信任链（见 §0 图）：`model_fp` 把响应钉在当前加载模型上（目录 + config + 文件尺寸）；
若模型是**签名 VQF**（防线 B，`VLLM_VQF_VERIFY=1`），权重级信任由 B 提供，两链闭合。

### 5.2 摘要绑定什么（schema=3 帧规范，magic `VLLM-AT-3`）

```c
digest = SM3(  "VLLM-AT-3"
            || F(model_fp)            // 64-hex，模型加载后固化
            || F(model_id)            // 服务通告模型名（如 qwen3-vl-2b）
            || F(device_id)           // 设备画像（如 arm-rk3588-opi5）
            || F(user)                // 请求 user 字段
            || F(params)              // "t=%.4g,p=%.4g,m=%.4g,mt=%d"
            || F(n_prompt_tokens)     // 十进制定长帧
            || F(n_gen_tokens)
            || F(finish)              // "stop" / "length"
            || F(ts)                  // unix 秒（弱防重放）
            || F(body_sha)            // SM3(客户端原始请求体) 的 64-hex
            || F(output_text) )       // 最终 assistant 文本字节
// F(x) = u32be(len(x)) || x
```

- **`body_sha` 绑定「设备实际收到的那一坨字节」**（含多模态 base64 图片 URL）：取证方对自己
  保存的请求原文做一次 SM3 即可逐字节比对，无需 tokenizer、无需重建聊天模板。
- 输出文本是解码 + 标记替换后的最终内容，与客户端看到/归档的文本一致。
- 任一字段事后改写 → 验签必然失败。

### 5.3 凭证与覆盖路径

非流式响应 JSON 增顶层字段 `"attest"`；流式在 SSE 末尾发独立事件 `chat.completion.attest`：

```json
{
  "schema": 3, "algo": "SM2-SM3", "ts": 1788575803,
  "model": "qwen3-vl-2b",
  "model_fp": "<64hex>",
  "device": "arm-rk3588-opi5",
  "user": "doc-zhang-001",
  "params": "t=0,p=0.9,m=0,mt=48",
  "prompt_tokens": 23, "n_tokens": 48, "finish": "stop",
  "body_sha": "<64hex>",
  "digest": "<64hex>",
  "signature": "<128hex r||s>"
}
```

| 路径 | 出证方式 |
|---|---|
| `/v1/chat/completions` 非流式（串行/batch） | 响应体顶层 `"attest"` |
| `/v1/chat/completions` 流式（串行文本/多模态、batch） | SSE 末尾 `chat.completion.attest` 事件 |
| `/v1/completions` 非流式（串行/batch） | 响应体顶层 `"attest"` |
| `/v1/messages`（Anthropic 兼容） | 暂不出证（V1 边界） |

已覆盖路径的摘要规范完全一致，验证脚本一视同仁。签名用 SM2（GM/T 0003），消息 = 32B digest，
ID = `"VLLM-ATTEST-1"`，输出 `r||s`（各 64-hex）；验签用 `tools/security/verify_attest.py`（纯 Python 零
依赖）或任何 GM/T 0003 兼容实现。开启时每请求：请求体一次 SM3 + 转录一次 SM3 + 一次 SM2
签名（A76 毫秒级）；batch 多 worker 并发出证由 `pthread_mutex` 串行化。**默认关闭**：不设
`VLLM_ATTEST` 时零改动零开销。

### 5.4 部署与取证流程

```bash
# 启动（出证 + 自检门 + 逐请求 PASS/FAIL 日志）
VLLM_ATTEST=1 VLLM_ATTEST_DIR=./.attest VLLM_ATTEST_SELFTEST=1 VLLM_ATTEST_LOG=1 \
nohup ./vllm_kestrel --serve --model <model-dir> --auto-load --port 8090 > /tmp/att.log 2>&1 &
# 停止 / 回退：pkill -x vllm_kestrel；去掉 VLLM_ATTEST=1 重启即为默认行为
```

启动自检应见：`[ATTEST] keypair/sign-verify/digest-determ/tamper-detect/selftest : PASS`。

| 变量 | 作用 |
|---|---|
| `VLLM_ATTEST` | `1` 开启；缺省/`0` 关闭 |
| `VLLM_ATTEST_DIR` | 密钥目录（缺省 `.`），内含 `vllm_attest.priv`(0600)/`vllm_attest.pub` |
| `VLLM_ATTEST_SELFTEST` | `1` 启动跑 PASS/FAIL 自检门 |
| `VLLM_ATTEST_LOG` | `1` 每次出证打 `[ATTEST] seal digest=... verify=PASS` |
| `VLLM_ATTEST_DUMP` | `1` 打完整预映像 hex（排障用，勿常开） |

**取证归档**（必须字节精确，勿转码/勿加 BOM）：请求原文 `req.json`、响应文本 `out.txt`
（非流式 `content` / 流式各 `delta.content` 拼接）、凭证 `proof.json`（`attest` 对象），外加
设备公钥 `vllm_attest.pub`（128-hex 单行）。

**离线验证**：

```bash
python tools/security/verify_attest.py --proof proof.json --request req.json \
    --output out.txt --pub vllm_attest.pub
# [VERIFY] body_sha 复算 : PASS … [VERIFY] SM2 验签 : PASS … RESULT: PASS  (退出码 0)
# 篡改任意一字节 → RESULT: FAIL（退出码 1）
python tools/security/verify_attest.py --selftest   # 验证脚本自身 SM3/SM2 实现自检
```

**自动化回归**：引擎侧 grep `[ATTEST] selftest : PASS` + `verify=PASS`；验证侧断言
`RESULT: PASS` 且退出码 0（出证默认关闭，不参与性能对照）。

| 文件 | 职责 |

解析出请求体后 → `vatt_body_digest`；非流式响应组装 ×6 → 附加 `"attest"`；串行/batch 流式收尾 →
SSE `chat.completion.attest`。

遗留与运维：

1. **VQF 版本兼容**：本引擎（v1.0）只加载 VQF v2 单文件；旧版（v1）`model.vqf` 不兼容，
   请保留原 safetensors 源并用 `vqf_convert/` 重新转换为 v2（引擎内已无 safetensors 回退路径）。
2. **batch 内存**：`--batch-max` 每并发请求各持一份大 KV 状态；2B 模型建议 ≤2 并发或更小

3. **首次启动自动生成密钥对**：`vllm_attest.pub` 生成后请安全下发给所有验证方；`priv` 勿复制/上传。
4. **留档目录建议**（取证方视角）：`case_0001/{req.json, out.txt, attest.json, device.pub}`。
5. 后续路线：Anthropic 接口出证；`model_fp` 权重内容哈希选项；可信时间戳；batch 内存下限优化。

## 6. 端到端使用指南

### 6.1 一次转换，三道防线就位（离线）

```bash
# ① 生成供应链签名密钥对（防线 B，私钥留离线机）
./vllm_vqf_sign --genkey
# ② 一次转换同时完成加密（防线 A）+ 内嵌签名（防线 B）
#    转换工具 vqf_convert/：先 ./build.sh（Windows: build.bat）得到 vqf_conv
VLLM_VQF_KEY='<高熵口令>' VLLM_VQF_SIGN_PRIV='<privhex>' \
  ./vqf_conv --model <safetensors-dir> --convert-vqf model.vqf --wmode q4
# （仅当需要对"已有"明文 VQF 补签时，才单独用 vllm_vqf_sign --sign）
```

### 6.2 设备部署（RK3588）

```bash
# 防线 A+B：加载加密签名 VQF（验签默认随解密开启）
VLLM_VQF_KEY='<高熵口令>' VLLM_VQF_SIGN_PUB='<pubhex 128hex>' \
  ./vllm_kestrel --serve --model <dir> --wmode q4
#    · 明文模型也想验签（防线 B）：加 VLLM_VQF_VERIFY=1（强制全量读，见 §4.7）
#    · 编译期固公钥：构建时 -DVLLM_SM2_PUB_HEX="..."，运行时免注入
# 防线 C：追加 VLLM_ATTEST=1 VLLM_ATTEST_DIR=./.attest（私钥首次自动生成）
```

### 6.3 取证与核验（验证方）

见 §5.4：保存三样字节精确文件 + 公钥 → `tools/security/verify_attest.py` 一键 PASS/FAIL。

### 6.4 故障排查与回退

| 现象 | 处置 |
|---|---|
| `encrypted model requires VLLM_VQF_KEY` | 加载加密模型未带口令 → 注入 `VLLM_VQF_KEY` |
| `HMAC-SM3 mismatch (tampered or wrong key)` | 口令错或文件被改 → 核对口令/重转换 |
| `SM2 verify failed / pub mismatch / digest mismatch` | 模型被替换或公钥不符 → 用正确公钥或重新分发签名模型 |
| `signed model requires trusted public key` | 签名模型无信任公钥（fail-closed）→ 注入 `VLLM_VQF_SIGN_PUB` 或编译期内嵌 |
| 明文模型验签拖慢加载 | 权衡 mmap 收益 vs 验签全量读；或改用加密 + 签名组合 |
| 需要停用某道防线 | 去掉对应环境变量重启即可（每道防线独立开关） |

## 7. 统一安全边界与局限性（诚实清单）

### 7.1 口令/密钥派生（防线 A）

- 派生是**单次 SM3**，无盐、无迭代（非 PBKDF2/Argon2）。口令熵即密钥熵：弱口令可被离线
  字典/暴力攻击；生产必须使用高熵口令。
- 口令经环境变量传递：运行期 `VLLM_VQF_KEY` 可经 `/proc/<pid>/environ` 被同权限进程读取；
  不具备硬件级密钥隔离（TEE/安全芯片）。

### 7.2 信任根与密钥保管（防线 B/C 共同）

- **公钥信任根是安全上限**：攻击者若能同时替换引擎二进制（连同内嵌公钥/设备私钥）并用自家
  密钥重签/重出证，SM2 无法防护——依赖固件/二进制完整性（安全启动、签名固件、写保护）。
- B 的私钥 `d` 只在离线签名工具中出现，引擎二进制只含 `vc_sm2_verify` + 内嵌公钥；C 的设备
  私钥 `vllm_attest.priv` 保护依赖操作系统权限（0600 + 目录 ACL），生产建议 TEE/HSM 或受控分区。

### 7.3 随机源（防线 A）

- VQF-Enc 的 IV 是 xorshift128（种子 time+地址），满足「每文件唯一性/混淆级」，**不是密码学
  随机**（若同一口令下两个文件 IV 碰撞则密钥流复用）。SM2 签名 k 由 `getrandom` 提供，
  属密码学安全（两者性质不同，勿混淆）。

### 7.4 运行态与性能取舍

- 解密后权重明文驻留 RAM，推理全程明文计算；A 不是密态计算（HE 研究内核另见技术文档）。
- 明文模型验签（B）强制全量读数据区，抵消 mmap 懒加载收益——默认关，按需开。
- 加密加载为一次性 ~92s（明文 ~1.3s）；C 出证毫秒级，默认关闭。

### 7.5 出证（防线 C）能证明 / 不能证明

能：✅ 记录完整性（请求+输出+参数+计数+时间+模型指纹与签名时一致）；
✅ 真实来源（由持有该设备私钥的引擎签发）；✅ 模型归属（`model_fp` 钉住目录/config/尺寸）；
✅ 弱防重放（`ts` 入摘要）。

不能：❌ **语义正确性**（验签通过 ≠ 结论正确，模型幻觉仍可能）；
❌ **计算真实发生**（背书模型：签名 = 设备/机构声明，不是密码学证明计算过程；root/内核后门
可伪造任意「真」记录）；❌ **推理可复现**（`temperature>0` 不可复现，业务复现审计请用
`temperature=0` 并固定 seed）；❌ **强时间公证**（`ts` 取设备本地时钟，强证据需外接可信时间源）；
❌ **绝对权重防伪**（`model_fp` 只盖 config.json + 目录 name:size，**同字节数换权重**可绕过——
根治 = 签名 VQF 防线 B）；❌ **多模态语义绑定之外的通道**（base64 请求体已被 `body_sha`
逐字节绑定；「已解码特征直传」类接口只绑文本输出与计数）；⚠️ `finish` 语义粒度（非流式恒报
`"stop"` 自洽但无法区分截断）；⚠️ 跨 schema 兼容（凭证按 `schema` 字段选择 magic 复算：
schema=3 → `VLLM-AT-3`，schema=2 旧凭证 → `VLLM-AT-2`，两版帧布局相同）；
⚠️ 曲线参数一致性（脚本内嵌 SM2 曲线参数须与引擎同步）。

### 7.6 覆盖缺口

- Anthropic `/v1/messages` 暂不出证。
- batch 跨请求并发放大内存（见 §5.5 遗留 2）。
- 验证方责任：请求/输出/凭证须**字节精确**保存；公钥须安全下发并核对；旧凭证按旧规范验证。

## 8. 术语表

| 术语 | 含义 |
|---|---|
| VQF-Enc | 防线 A：VQF 存储态加密（SM4-CTR + HMAC-SM3，`VQF_FLAG_ENC`） |
| 供应链签名 | 防线 B：VQF v2 `VQFSig` SM2 签名（`VQF_FLAG_SIGNED`），防模型替换 |
| attestation / attest | 防线 C：出证，生成并附加签名凭证（schema=3，magic `VLLM-AT-3`） |
| digest | 摘要：对字节精确帧做 SM3 的 32B 值（hex 64） |
| model_fp | 模型指纹：加载成功后固化的 64-hex（config+目录清单） |
| body_sha | 原始请求体的 SM3（64-hex），绑定「收到什么证明什么」 |
| 背书模型 | 签名代表设备/机构声明，而非密码学证明计算过程 |
| fail-closed | 无信任公钥时拒绝加载签名模型（不静默跳过验签） |
| COW | `MAP_PRIVATE` 写时复制：解密只改 RAM 映射，磁盘密文不变 |
| KAT | Known-Answer Test：国密标准向量逐字节验证 |
