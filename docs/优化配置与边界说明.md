# 注意力优化配置与边界说明

> 基于 2026-08-28 实测（进程内直调 perf-partA，串行同条件前后对照；Qwen3-VL-8B，16 线程，greedy）。
> 机器长时间满载后有热节流/后台负载（整体较基准时刻慢 ~1.4x），跨时间绝对数值仅供参考，同条件相对结论有效。
> 注：本文为 **x86 基准机（8B，16 线程）同条件对照** 的归因分析；RK3588 板端发布级
> 绝对性能（2B，8 核，vs llama.cpp 全矩阵）见 [RK3588_性能基准报告.md](RK3588_性能基准报告.md)。
> 文中"16K+"档为评估期（当时 max_seq 上限更高）的相对结论；**当前发布版上下文窗口
> 钳制为 max_seq=8192**（[main.c](../src/main.c)），超长/多用户场景的 L3 落盘价值仍成立。

---

## 一、推荐配置组合

| 场景 | 推荐命令行 | 说明 |
|---|---|---|
| 单用户 / 服务端默认 | `--wmode q4 --sparse-attn --sparse-k 32` | KV 默认 q8；稀疏 prefill+decode 全开，速度最优 |
| 质量优先 | `--wmode dual --sparse-attn --sparse-k 32` | prefill 用 Q8 混合权重，速度与 q4 几乎持平 |
| 超长上下文（16K+，RAM 不足） | `--wmode q4 --sparse-attn --sparse-k 32 --l3-evict --l3-ratio 0.75` | 冷 KV 块 Q4 压缩落盘释放 RAM |
| 非稀疏 q8-KV decode 加速 | 无需开关（板端恒定） | 板端 q8-KV decode 固定单遍 online（`flash_attn_single_q_q8_neon`）；f32/q4-KV decode 为两遍。x86 实验开关 `VLLM_ATTN_ONLINE` **未进入 aarch64 发布树**（见 §2） |
| 多轮对话服务（推荐全开） | `--wmode q4 --sparse-attn --disk-kv ./kv_disk --spec --spec-k 4` | 前缀复用（默认开）+ 重启复用 + 推测解码，全部服务端生效（见 §3） |
| 重复文本/模板场景 | 上述组合 + `--spec-k 8` | 草稿命中率高时收益更大（见 §3.4） |

统一口径：sparse 默认 `k=32 / block=32 / probe=8`；`--perf-partA --bench-seqlen N` 为单用户基准测试入口。

## 二、优化点逐一评估（可用性 + 边界）

### 1. 稀疏注意力（prefill + decode）—— 核心有效优化 ✅

**状态**：已接入主路径（decode `sparse_attn_head`；prefill `st_attn_batched_packed_sparse`，seq_len > 2×block 时自动启用）。

**效果（8K prefill，同条件前后测）**：

| 指标 | exact | sparse k=32 | 变化 |
|---|---|---|---|
| ATTN 时间 | 61.6s (26.5%) | **16.0s (7.8%)** | **-74%** |
| prefill 总时长 | 232.5s | 206.2s | -11.3%（GEMM 有 ±10% 机器噪声） |
| 4K ATTN（历史） | 15.0s | k=8: 2.0s / k=16: 3.2s / k=32: 6.7s | ATT 占比 15%→2~7% |

**边界**：
- **质量下边界 k=32**（S=4096 验证）：needle 召回 YES、ppl 3.37；k=16 即失败（needle NO、ppl 6.2）；k=8 严重退化（答案错、ppl 7.6）。
- **decode 稀疏要求 KV 非 q4**（门控 `!use_kv_q4`）：`--kv-q4` 与 `--sparse-attn` 互斥。
- 长上下文收益更大（ATT 占比随 seq_len 上升：4K 15% → 8K 26.5%）。
- 多模态单图（~880 视觉 token）：质量与精确逐字一致，但单图场景 ATT 占比低，**无性能收益**；多图/长视觉上下文才划算。

---

### 2. online-softmax 单遍（VLLM_ATTN_ONLINE=1）—— decode 有效，prefill 回退 ⚠️

**状态**：本文为 x86 基准机实验结论（2026-08-28）。注意：`VLLM_ATTN_ONLINE` 的
读取仅存在于 x86 开发树；**aarch64 发布树未实现该开关**——q8-KV decode 恒定单遍
（`flash_attn_single_q_q8_neon`，源码即 online 逻辑），f32/q4-KV decode 恒定两遍，
板端无可切换项，下述测量仅作 x86 同条件归因参考。

**效果**：
- decode（非稀疏 + q8 KV）：单遍 INT8-KV，省一次 KV 扫描，**有效**（该路径为 decode 内存带宽瓶颈而设）。
- prefill（本次实测 S=2048 同基准）：total 46.0s vs 2-pass 43.5s（**+5.7%**）；ATTN 4.04s vs 3.45s（**+17%**）。

**边界**：
- **prefill 在 x86 上不划算**：单遍需在热循环用标量 `expf`（依赖运行时 max，无法像 2-pass 那样向量化 `exp_ps512`），省下的 KV 扫描不足以抵消。**内存带宽受限平台（如 RK3588）才可能转正。**
- 稀疏 decode 走 `sparse_attn_head` 提前 return，**不经此路径**（稀疏 decode 自身已是 online 逻辑）。
- 正确性已验证：S=2048 needle YES、ppl Q8=3.738（2-pass 3.755，一致）。
- 顺带修复：原 prefill 单遍的 imp_head 立即重缩放是 O(n²)（8K 下极慢），已改为 deferred O(n) 物化。

---

### 3. Flash Attention（flash_attn_blocked_single_q）—— 结构性不适用 ❌

**状态**：未接入主路径。门控：`!use_kv_q8 && !g_sparse_attn && seq_len ≥ 64`。

**边界**：
- 要求 **f32/q4-KV 且非稀疏**——与当前 q8-KV + 稀疏栈**互斥**（KV 默认 q8，`use_kv_q8=1`，flash 永远不可达）。
- flash = 全量注意力，与稀疏 top-k 块设计天然冲突。
- 唯一适用场景：多模态 q4-KV 注意力（`vllm_mm_attn_flash_worker`，已在使用）。
- **结论：当前配置下无接入价值，保持现状。**

---

### 4. Q8Q4 混合权重（dual / --prefill-q8）—— 质量档，速度与 q4 持平 ✅

**状态**：`--wmode dual` 即默认混合模式（wmode=0）；`--prefill-q8` 可单独强制 prefill 走 Q8_0。

**效果（4K prefill）**：dual total 101.3s vs q4 98.9s（**+2.4%**，GEMM 82.3 vs 81.1s 持平）；decode（Q4）TPOT 130ms 正常。

**边界**：
- 定位是**质量档而非速度档**：Q8 prefill 精度显著高于 Q4，成本几乎为零。
- `--wmode q8`（纯 Q8）与 `--wmode q4`（纯 Q4）是两个极端；`dual` 是其混合默认。
- 与稀疏注意力正交，可叠加（`--wmode dual --sparse-attn`）。

---

### 5. L3 evict 磁盘稀疏 —— 超长上下文专用，8K 单用户不触发 🟡

**状态**：已实现但默认未开（此前对比中选择了 RAM 稀疏）。

**边界**：
- 依赖 `--sparse-attn`（冷块需稀疏选择信号），`--l3-ratio` 默认 **0.75**（evict 每层最冷 75% 块）。
- **单用户 8K 只用 ~11.7GB RAM，不触发**，测不出收益；价值在 **16K+ 或多用户并发**（RAM 耗尽时才压缩落盘）。
- 恢复路径：稀疏 decode 从磁盘 Q4 状态读回，首次访问有 I/O 延迟。
- 旧激进记录参考：`--prefill-q8 --sparse-attn --l3-evict --l3-ratio 0.9 --sparse-k 16`（注意 k=16 已低于质量边界）。

## 三、ds4（DeepSeek-V4/DwarfStar）工程思想优化（serve 侧）

以下优化均借鉴 DeepSeek-V4/DwarfStar 的工程做法实现（2026-08-26/27，均已单测 PASS），服务于多轮对话与并发场景；单用户 perf-partA 不涉及。

### 3.1 min-p 采样（`--min-p P`）—— ✅ 可用（ds4/DwarfStar 默认采样器）
- 机制：特殊 token 抑制后、top-p 之前应用 min-p 过滤；请求体可覆盖；`--min-p 0`=关闭（默认）。
- 验证：OpenAI/Anthropic 兼容层全 PASS（min_p/stream/缺 max_tokens）。
- 边界：与 top-p 正交叠加；采样类参数，贪婪模式不生效。

### 3.2 serve 内存 KV 前缀复用（默认开启，`--no-prefix-kv` 关闭）—— ✅ 可用，**4.99x**
- 机制：多轮对话第二轮起，与上轮 token 序列最长公共前缀（LCP≥16）命中时保留 KV，只 prefill 差异部分（模型层零改动，serve 层 `ist_reset(keep)`）。
- 验证：R0 全量 vs R1 vs R2 复用，输出逐字节一致；prefill 加速 4.99x（253 复用 231 token）。
- 边界：**`--l3-evict` 开启时自动降级全量**（L3 释放前缀块为 NULL，prefill 无 NULL 检查会崩）；多模态路径全量 reset（视觉 KV/mrope 不参与文本前缀）；`--no-prefix-kv` 关闭。

### 3.3 磁盘 KV 持久化（`--disk-kv DIR`）—— ✅ 可用，**5.27x**
- 机制：每次成功文本请求后把 F32 KV 快照落盘 `DIR/kv_<fnv64>.kv`；启动扫描建索引；请求时与 checkpoint 求 LCP（≥16）→ 加载 KV → 只 prefill 差异。跨进程/重启复用。
- 验证：prefill 1328ms→285ms（4.66-5.27x），输出逐字节一致，日志 `[KV-DISK] loaded/saved`。
- 边界：上限 8192 token/文件（`DISKKV_MAX_TOKENS`，覆盖 max_seq=8192 窗口）、8 文件（LRU 按 mtime）；F32 保证位级一致但体积大；与 `--no-prefix-kv` 解耦（`ist_reset` 复用门槛为 prefix_kv **或** disk_kv）。

### 3.4 推测解码（`--spec [--spec-k N]`）—— ✅ 可用（条件性），**1.30x 文本 / 1.64x 多模态**
- 机制：n-gram 自推测——上下文末尾窗口（最长优先 8→3 token）在历史找重复，取其后的 K token 作草稿；`st_qwen_model_prefill_batch` 一次并行 prefill 验证（每位置 lm_head top-1），贪婪接受，KV 回滚。
- 验证：输出与正常逐字节一致（数学无损）；文本草稿命中 75%（tpot 25.3→19.5ms，1.30x）；多模态命中 92%（28.8→17.6ms，1.64x）。
- **边界（诚实）**：
  - **仅贪婪文本路径**（temp≤0/top_p≥1/min_p≤0），L3/batch/稀疏（`!g_sparse_attn`）模式禁用。
  - n-gram 只对**精确重复文本**（固定格式列表/代码模板/叠句）生效；自由文本命中率低。
  - 编号递增类重复（"第N点"）草稿系统性给旧值、被拒（实测 0% 命中）。
  - 草稿超过 mini-batch 时 invalid 标记自动回退；默认关闭（`--spec` 开启）。
  - 收益依赖 decode 本身耗时：2B 本地仅 25ms/token，verify 开销 ~28ms 吃掉了大部分增益；**RK3588（341ms/token）上理论增益 2-3x**。

### 3.5 分层精度 q2mix-tail（`--q2mix-tail N`）—— ❌ 已定案关闭
- 机制：前 N 层 FFN 用 Q2_1，尾部 N 层保留 Q4（借鉴 ds4 分层精度思想）。
- 验证：tail=28（全 Q4）cjk=0.66 正常、tail=12 cjk=0.11 乱码 → 机制链路正确，但 **2-bit 误差在稠密模型主残差路径累积不可救**。默认已改 0。
- 边界：2B 稠密模型关闭；MoE 类模型（注意力 Q4 + FFN Q2）另议。

### 3.6 连续批处理（`--batch-max N`）—— ✅ 可用，**1.7x**
- 机制：独立后台线程每步 1 次前向 B token（复用 `st_qwen_model_forward_batch`），HTTP worker 提交 per-request 状态；max 32。
- 验证：8 并发全 PASS；串行 22.0 vs 批量 13.1 tok/s（约 1.7x，K=8）；**位级一致性在跨 prompt 下存在 near-tie 双内核翻转风险**（margin 0.71 vs 0.032 级别），非普遍保证。
- 边界：16 线程下 8B 模型 decode 已是内存带宽瓶颈，批增益有限；NPU/更大模型受益更大。

| 8K | **167.9s** | 184.2s（vllm 快 9%） | 127ms | 121ms |
| 16K | **349.5s** | 448.7s（vllm 快 22%） | 149ms | 155ms |

## 五、已知问题

1. **8K+ quality 路径间歇性 prefill 崩溃**（在 5120/6400 及 512/2049 处复现过）：与上述优化无关，属既有问题，建议另查。
2. 跨时间性能对比受热节流/后台进程影响（本机曾出现整体 1.5x 波动）；正式基准应在干净控制台、低负载时段串行执行。
3. `VLLM_ATTN_ONLINE`（x86 实验开关，aarch64 发布树不读取）同时影响 prefill 与 decode：**prefill 收益为负**，按需单点开启（建议仅 decode 场景或内存带宽受限平台使用）。

## 六、性能归因与总体边界

### 这些优化解决了什么（分场景收益归因）

| 场景 | 主贡献优化 | 实测收益 |
|---|---|---|
| 单用户长上下文 prefill | 稀疏 prefill | ATTN **-74%**；total -11.3%（8K） |
| decode / 长上下文吞吐 | 稀疏 decode | TPOT 127ms（8K，胜过 llama 121ms） |
| 多轮对话服务 | 前缀复用（默认开）/ `--disk-kv` | prefill **4.99x** / **5.27x** |
| 并发用户 | `--batch-max` | ~**1.7x**（8 并发） |
| 精确重复文本 | `--spec` | **1.30x** 文本 / **1.64x** 多模态 |
| prefill 精度 | `--wmode dual` | Q8 精度，速度与 q4 持平（+2.4%） |

### 没解决什么（诚实边界）

- **GEMM 是单用户 prefill 的真正大头**：8K 下 GEMM 占 ~71%、ATTN 只占 ~27%。稀疏优化省的是 ATTN 部分，所以即便 ATTN 降 74%，prefill 总时长也只降 11%。**要再提单用户 prefill 速度，方向是权重量化/内核效率，而非注意力侧**；decode 与超长上下文（注意力占比高）才是稀疏的主场。
- **无帮助 / 负收益项**：online prefill 单遍（+5.7%，x86 回退）、flash attention（q8+稀疏栈不可达）、q2mix-tail（已关闭）、L3 evict（8K 单用户不触发）。
- **推测解码收益依赖平台**：2B 本地 decode 仅 25ms/token，verify 开销 ~28ms 吃光增益；RK3588（341ms/token）才有理论 2-3x。
- **批处理受硬件上限约束**：16 线程下 8B 模型 decode 已是内存带宽瓶颈，批增益有限；NPU/更大模型受益更大。
- **位级一致性非普遍保证**：batch 跨 prompt 存在 near-tie 双内核翻转风险（margin 0.71 vs 0.032 级别）；spec/prefix/disk-KV 在验证场景下输出与全量逐字节一致。
