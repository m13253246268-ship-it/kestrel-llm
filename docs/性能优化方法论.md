# 性能优化方法论（以 prefill 注意力为例）

> 本文沉淀一次完整、可复用的性能优化流程，供后续任何性能工作套用。范例是
> 2026-09-23 的「prefill 注意力 P×V 保序分块」优化（结果：2B 全精度 prefill 在
> 256/1024/2048 上下文相对 llama.cpp flash 快路领先 +3.5%~+7.3%，位级不变）。
> 口径与边界照实标注：本文的绝对数字是 RK3588 板端热态串行 A/B，不代表跨时间、
> 跨机器可外推；方法论本身与具体数字无关。

---

## 一、总纲：五条铁律

1. **先公平、后归因、再动手** —— 没对齐对照条件就测出的"差距"是伪命题。
2. **位级对拍是硬门槛，不是可选** —— 只有输出逐字节相同，才谈得上"无损提速"。
3. **保序优化** —— 只重排彼此独立、可交换的累加；不碰归约树。
4. **默认关闭 + 逃生舱** —— 新路径默认关，验证通过、性能领先才默认化，且保留 `=0` 回退。
5. **分桶计时，确认动了哪里、没动哪里** —— 优化要能自证"只动了目标阶段"。

## 二、定位瓶颈：分桶计时归因

不拍脑袋。先把 prefill 拆成可测的桶，看谁随上下文增长：

- 本引擎 `[PREFILL-TIMING]` 已输出 `GEMM / ATTN / OTHER` 三桶（`--stream-test` 内建）。
- 判据：**GEMM 严格线性（ms/token 恒定）而 ATTN 随 n 线性增长（总 Θ(n²)）**，则瓶颈在 ATTN。

范例（2B Q8）：

| n | total | GEMM | ATTN | 结论 |
|---|---|---|---|---|
| 256 | 3239 ms | 2846 (87.9%) | 254 (7.8%) | GEMM 主导 |
| 1024 | 15965 ms | 11535 (72.2%) | 3858 (24.2%) | ATTN 快速上升 |
| 2048 | 39413 ms | 22786 (57.8%) | 15516 (39.4%) | ATTN 逼近 GEMM |

> 归因结论必须由分桶数据支撑，不能靠"感觉哪个慢"。上一轮曾把差距误归给 GEMM，
> 分桶一看 GEMM 每 token 恒定、ATTN 是唯一增长的项，才把方向对准 attention。

## 三、设计公平 A/B：对齐四要素

对照第三方引擎（或改前/改后）前，四要素必须逐一对齐，否则结论作废：

| 要素 | 做法 | 本次怎么对齐 |
|---|---|---|
| **同权重** | 逐字节验证量化块，不是"同一模型名" | Q8_0 采样 126/126 逐字节一致（`inspect_models.py`） |
| **同 token 流** | 用同一次 tokenize 结果喂两边 | warmup 时截获引擎真实 prompt id，回灌对端 |
| **同 batch/ubatch** | 显式对齐，别用各自默认 | 两侧都 batch=256 |
| **同 KV 精度** | 显式指定第三方的 KV 精度，别吃它的默认值 | 见 §十一：llama 缺省 f16，本引擎 f32，差 16% |
| **同线程 + 亲和 + 热态** | `taskset` 固定大核、各自 warm、drop_caches 后同口径 | `taskset -c 4-7`、`--warmup`、governor=performance |

**附加纪律**：每个 arm 至少 3 次重复、交错腿序、记录 boot_id/温度/频率、报告极差。
归一化后 <3% 的差异按噪声处理，不据此下结论。

> 教训：上一轮 kestrel 用 batch=256、llama 用 batch=2048，导致"落后 8%"的数字
> 本身不可靠。本次严格对齐 batch=256 后，llama-flash 在 n2048 仍是 55.9 tok/s
> （说明它对 batch 不敏感），但 kestrel 的真实位置才被正确地定出来。

## 四、保序优化：只重排可交换的累加

这是"无损提速"和"近似提速"的分水岭。

### 4.1 什么可以重排

对固定输出元素 `O[q][d]`，如果累加是 `O = Σ_s w_s · V_s[d]` 这种**沿位置 s 的一维 FMA 链**，
且各 `s` 项之间没有跨项依赖，那么：

- 可以**任意分块**（s 方向分块），只要块与块之间**续接原累加器**（不是各块求部分和再合并）；
- 可以**改变遍历次序**（先 d 后 s、先 s 后 d），只要每个 `O[q][d]` 内部的 `s` 升序不变；
- 可以**让多个 query 共享同一次 V 载入**，只要各自累加链独立。

### 4.2 什么绝不能动

- **归约树**：`Q·K` 的 `hsum_neon4`（4 维分组求和）、softmax 的分母求和——这些的求和顺序
  一变，浮点结果就变，不是位级中立。
- **softmax 本身**：online-softmax / 分块 softmax 数学等价但改变中间舍入，**不能冒充位级无损**。
- **FMA 融合**：标量尾 `o += wgt * vp` 不能改成 `fma`，乘加次序变了。

### 4.3 本次的具体做法

[`vllm_attn_pv_tile128`](../src/model/vllm_safetensors.c) 只重排 F32 注意力的 `P×V` 段：

- 每个 `O[q][d]` 仍沿 `s` 全局升序做同一条 `vfmaq_f32`；
- 两个 query 共享一次 V 载入（GQA 下 kv head 复用），16 个输出累加器常驻寄存器；
- QK 点积、softmax、importance 累加顺序**逐字不动**。

结果：位级不变（见 §五），ATTN 桶 −27%（2048 token），总 prefill −10.9%。

> 关键判断：能不能重排，取决于"该累加链是否有跨项依赖"。有归约树的地方（QK/softmax）
> 一律不动；纯一维 FMA 链（PV）才敢动。

## 五、验证门槛：四级位级对拍

只比较"生成文本 / top-1 token 相同"不构成位级证明。按代价从低到高过四级：

| 级别 | 验证内容 | 门禁 |
|---|---|---|
| **L1 隔离探针** | 直接调 worker，比 `out / scores / importance` 的**原始 float 字节** | 全等，含主批与尾 1/2/3、prev_len、GQA、多 head |
| **L2 完整模型** | 逐层 hidden、完整末位 logits、KV 行哈希 | 逐字节/哈希全等 |
| **L3 TOKIDS + 关闭回归** | 贪心序列一致；候选关闭档 vs 基线一致 | 全等 + 关闭档无漂移 |
| **L4 推广** | 其他模型 / 精度 / 驻留档 | TOKIDS 一致 |

本次结果：L1 通过 547 组形状 × 3 模式 × {1,4} 线程；L2 通过 256 与 2048+尾批；L3/L4 全过。

**额外硬门槛：汇编检查寄存器溢出。** 历史教训（见 CHANGELOG §14.3）：源码把累加器
"看起来"放进了寄存器，实际可能整体落栈（栈帧 +256 B），收益归零甚至变负。
必须 `objdump` 看目标热循环：累加器是否真在 `v0..v31`、V 载入是否共享、有无 `sp` 写回。

## 六、默认化决策

一个优化通过位级对拍、且实测领先，才允许默认开启。默认化必须同时满足：

1. **位级等价**：新路径输出与旧路径逐字节相同（见 §五）；
2. **性能领先**：同条件 A/B 全面领先，且极差稳定（<1%）；
3. **逃生舱保留**：环境变量 `=0` 能显式关回旧路径，且关回后输出仍与基线一致；
4. **自动回退**：不满足启用条件（如非 hd=128、QB≠4）时静默走原路径。

本次：`VLLM_ATTN_PV_TILE` 默认 `2`，`=0` 关闭、`=1` 单 query/d64、`=2` 双 query/d32。

## 七、参数扫描

分块尺寸等参数先参数化（编译期宏或运行时 env），再扫点确认：

- 本次把 KV 位置分块宽参数化为 `ST_ATTN_PV_BLK`，扫 64/128/256；
- 结果 64 > 128 > 256（58.48 / 57.73 / 57.34 tok/s），64 仅快 1.3%；
- **决策：保持默认 128** —— 128 是完整位级对拍验证过的历史定值，64 只跑了 TOKIDS 冒烟。
  小于噪声阈值的收益不值得引入未充分验证的默认值。

> 教训：参数扫描的"最优值"若只是 1% 级差异，且未过完整位级对拍，就记为开放项，
> 不要因为"看起来更快"就改默认。

## 十、诚实边界与教训（复用前必读）

1. **位级一致 ≠ 数学等价**：online-softmax / 分块 softmax 属"数学等价但非位级"，
   要单独归为"近似/改变数值"路线，不得并入保序路线，更不得宣称无损。
2. **寄存器溢出只能看汇编**：源码写的是 `float32x4_t acc[16]`，编译器可能落栈。历史上
   单独 OREG（INT8 路径）因此零收益甚至微负，本次是"寄存器驻留 + V 共享"联合才转正。
3. **单点优化可能负收益，要看组合**：历史 OREG 单独 +1%~+8%，VBLK 联合 −20% ATTN。
   别因为某个单点失败就判死整条路线。
4. **对照的 batch/线程不一致会毁掉结论**：本次已踩过，务必用 §三 的四要素自查。
5. **别顺手修无关 bug**：`VLLM_KV_F32=1` 在冻结基线会崩溃（调用点访问未分配的 Q8 缓存），
   与本优化无关，本轮绕开不修，避免把修复和优化混在一起。
6. **绝对数字不跨机器/跨时间外推**：本引擎文档多次强调，x86 仅作功能自检与位级对照，
   热节流/页缓存状态都会影响绝对值；只信"同条件同 session 的相对对照"。
7. **"更快"的路径要先测再信，适用区间必须实测界定**：int8-K 直算路径按其设计在
   16K 流量受限档有收益，但 8B n1024/2048 实测 ATTN 反而慢 46%~81%（int8 解包开销
   吃掉了流量收益）。路径的收益区间是实测出来的，不能从指令预算推。

8. **归因必须先分离"读侧"与"写侧"，验收判据的难度也要校准**（2026-09-24 补）：
   prefill 稀疏档捞针失败，表面症状是"选块没选到针"，但把两个量分开量就翻了结论 ——
   decode（读侧）在 8K 档 `MISSED 0`（每次都 attend 到针块）却答错，而 4K 档 75% 的调用
   没看到针块却答对 ⇒ **读侧选块的好坏与结果不相关**；真正单调相关的是 **prefill（写侧）
   把针块选进 top-k 的比例**（4K 42.93% → 8K 32.17% → 16K 15.00%，对应 YES→NO→NO）。
   prefill 的 attention 输出就是写进 KV 的 K/V 来源，所以污染在**写入侧**。
   教训两条：
   - 先证读侧（`MISSED` 计数）、再证写侧（选块命中率），**两个量必须分别量化**，
     否则一定把病因归到"选块策略"上，去修一个与结果无关的量；
   - **判据难度要校准**：内置针 `...favorite food is ramen`（高频可预测）在同一配置的 4K 档
     判 YES，而多轮稀有码 `KX2B739`（低先验、要求逐字抄写）同档判 NO。宽松判据只能用来
     快速探界，**不能用来判"可用"**。

## 十一、口径对齐的隐藏变量：KV 精度与量化格（2026-09-24 补）

§三 的四要素之外，**KV 精度**与**权重量化格**是两个最容易漏掉的隐藏变量。漏掉它们，
会得出方向完全相反的结论。

### 11.1 KV 精度：第三方引擎的"默认"往往是 f16

`llama_exact` 的用法是 `model.gguf tokens.bin batch flash(0|1) [f16|f32]`，
**第 5 参缺省即 f16**（源码 `kv_f32 = (argc==6 && argv[5]=="f32")`）；而本引擎精确档
读 **f32 正典**（Q8 KV 缓存的反量化副本）。二者不是同口径。

8B / n=2048 / batch=256 / 同 token 流（TOKIDS 全一致）实测：

| llama KV | flash=0 | flash=1 |
|---|---|---|
| f16（默认） | 115.6 s | 113.8 s |
| **f32** | **134.1 s** | **111.7 s** |

**f16 KV 让 llama 的非 flash 路径白赚 16.1%** —— 这是精度口径差，不是实现效率差。
同口径（f32）下 8B：本引擎 125.0 s vs llama 精确路径 134.1 s → **本引擎反超 6.8%**。
此前"8B 落后 8%~10%"的结论，正是拿本引擎 f32 比 llama f16 的产物，须以此订正。

### 11.2 量化格：不同格则单个桶不可比

8B 两侧权重不是同一份：本引擎 group-16 Q4（≈4.25 bpw）vs llama Q4_0（4.5 bpw），
**GEMM 桶因此不可比**。唯一完全干净的对照是 **2B**（Q8_0 逐字节一致 126/126）：

| 2B / n=2048 / batch=256 | 秒 | 相对本引擎 |
|---|---|---|
| **本引擎**（同权重 + f32 正典） | **35.0** | — |
| llama f0，f16 KV | 36.3 | −3.5% |
| llama f0，**f32 KV** | 42.9 | **−18.3%** |
| llama f1(flash)，f16 KV | 37.2 | −5.8% |
| llama f1(flash)，**f32 KV** | 37.5 | **−6.7%** |

**在唯一完全同口径的对照上，本引擎全面领先，且领先 llama 的 flash 快路。** 这也说明
照搬 llama 的 tiled attention 不是必需项——它的优势在本引擎的口径下并不成立。

### 11.3 纪律

1. 对照第三方前先读它的参数语义，把**缺省值**当隐藏变量列出（KV 精度、KV 类型、
   rope 类型、是否 flash、ubatch…），逐一显式对齐。
2. 权重不是同一份量化时，**只比总时间**，不要把单个桶的差异归因于实现效率。
3. 口径未对齐前**不得下"落后/领先"结论**；已下过的要用对齐后的数据订正。
4. 结论若依赖某个精度档（f16 vs f32），必须写明该档，并说明它是"精度取舍"还是
   "实现差距"——前者不属于优化缺口。
