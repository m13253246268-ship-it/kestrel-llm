## 1. 概述

vllm_kestrel 是面向 RK3588 的边缘端 LLM 推理引擎，特点：

- **纯 CPU/NEON 路径**：不依赖 NPU/GPU/RKNN 即可运行；RK3588 的 4×A76 大核并行，
  ARMv8.2 dotprod（`vdotq_s32`）INT8 点积、8x8/4x4 权重重排。
- **自研线程池**：以 `vllm_tp` 替代 OpenMP 运行时，持久工作线程 + 调用线程参与，
  消除并行区间的线程唤醒开销。
- **自研量化格式 VQF**：把"量化 + 布局 repack"固化到文件，加载 = mmap + 指针直挂
  （秒级），同时保留位级一致（转换与推理共用同一量化代码路径）。
- **多模态**：内置 Qwen3-VL 视觉塔（ViT + Merger + DeepStack），支持图片/视频帧输入；
  图片视觉 token 缓存、客户端预处理协议（`vision_tokens`）。
- **服务化**：OpenAI 兼容 HTTP API、管理页、转换页、进程守护脚本，自带 HTML 内嵌。

引擎定位"边缘单机推理"：单一 SSE 流服务、串行推理队列、可选 NPU 透明卸载。

### 2.2 线程模型

推理与 HTTP 两层线程模型（[vllm_tp.h](../include/core/vllm_tp.h)）：

| 层 | 线程 | 默认 | 说明 |
|---|---|---|---|
| 推理 | `VLLM_THREADS` | 4 | 绑定 4×A76 大核；**勿设 8**（A55 拖累，见 §11.4） |
| HTTP worker | `--threads` | 8 | 并发连接处理；推理本身串行（单 SSE 流） |

`vllm_tp` 设计要点：

- 持久工作线程（惰性创建），任务间 spin-then-event 等待，并行区间分发 ~µs 级；
- **调用线程参与执行**自己分块并 join，常见情况无空闲线程唤醒延迟；
- 静态连续 chunk（对应 `schedule(static)`），行成本均匀；
- 创建时绑定物理核（RK3588 固定 A76 集群）；
- API 与引擎实际使用的 OpenMP 面 1:1 镜像：`vllm_tp_parfor / parcall /
  worker_id / threads / init / wtime`。

### 2.3 推理数据流

```
HTTP 请求
  → vllm_server 路由
    → 文本：qwen_tokenizer_encode → run_completion
         ├─ 前缀复用判定（内存 last_ids LCP / disk-kv LCP）
         ├─ prefill（st_qwen_model_prefill_batch，GEMM + 注意力）
         └─ decode 循环（逐 token，采样/推测解码）
    → 多模态：build_multimodal_prompt
         ├─ image_url   → 图片解码 → 视觉缓存命中? → 回放 : st_vision_encode_image
         ├─ video_frames→ 帧解码 → st_vision_encode_video
         └─ vision_tokens→ 客户端预处理特征直接注入（跳过 ViT）
         └─ 拼接文本/视觉 token → run_multimodal_completion
  → SSE / JSON 响应
```

### 3.1 编译配置（RK3588 专用）

| 项 | 值 | 说明 |
|---|---|---|
| C 标准 | C11 | |

```bash

./build_rk3588.sh --static        # 板端原生构建（全静态，零 .so 依赖，发布包所用）
./build_rk3588.sh --cross         # x86 交叉（需 toolchain-aarch64-rk3588.cmake）
./build_rk3588.sh --run-tests     # 构建后跑 PASS/FAIL 自检
```

> 日志 **0 条内存错误报告**（越界 / use-after-free 在所测路径为零）。

> -DCMAKE_C_FLAGS="-fsanitize=address -O1 -g -mcpu=cortex-a76 -march=armv8.2-a+dotprod+fp16 -fopenmp -D_GNU_SOURCE"
> -DCMAKE_EXE_LINKER_FLAGS="-fsanitize=address"` 后构建并运行上述自检。

### 3.2.1 零依赖静态构建

`--static`（`-DVLLM_STATIC=ON`）产出 `build-rk3588-static/vllm_kestrel`，链接加 `-static`，
glibc/libm/libgomp 全部内联，pthread 已并入 glibc 2.35 libc.a：

- `file` 输出 `statically linked`；`ldd` 输出 `not a dynamic executable`；`readelf -d` 无 NEEDED。
- 体积 1.5MB（vs 动态 0.69MB），对 eMMC/内存无实际影响。
- 数值行为与动态一致（同一 glibc 2.35，libm 同为该版本代码），文本冒烟输出逐字一致。
- 静态 glibc 下 NPU rknn 后端（dlopen）编译产生 warning、运行时加载失败回退 CPU；
  NPU direct 后端（默认，零依赖直写 /dev/rknpu）不受影响。
- 前提：板端装有静态库 `libc.a / libm.a / libgomp.a`（Ubuntu `libc6-dev` 自带，
  libgomp.a 随 gcc 提供）。

## 4. 权重格式 VQF

定义见 [vqf.h](../include/model/vqf.h) / [vqf_format.h](../include/model/vqf_format.h)。动机：
safetensors 加载需"mmap → 逐层 F32→Q8/Q4 量化 → repack 8x8/4x4"，2B 模型板端约 23s；
VQF 把量化 + 布局固化到文件，加载 = mmap + 元数据校验 + 指针直挂（零转换零计算）。

**当前为 v2**（`VQF_VERSION=2`，头部追加 SM2 签名块 `VQFSig`，见下 §4.6）。

### 4.1 文件结构

```
┌─ 头 VQFHeader（固定 432B，magic "VQFW" 0x57465146, version 2）
├─ 目录 VQFTensor[]  （name[32], qtype, rows/cols, offset, bytes；64B/个）
├─ 对齐填充          → 头+目录 4096B（页对齐）
├─ 数据区            （张量 64B 对齐；Q8 8x8 tiled / Q4 4x4 nibble 原生布局）
└─ 尾部              （加密：HMAC-SM3 tag 32B；明文：FNV-1a checksum 8B）
```

### 4.2 布局 flags（转换时固化，加载时校验，错配拒绝）

| flag | 含义 |
|---|---|
| `Q8_8X8` | q8_* 为 8x8 tiled 布局 |
| `Q4_4X4` | q4_* 为 4x4 nibble 布局（`repack_q4_0_4x4`） |
| `X8` | x8_* 8x8l decode 副本存在 |
| `Q8BUF_Q4` | q8_* 实际存 pre-unpacked Q4 int8（q4i） |
| `G256` | q8_* 为 G=256 分组量化 |
| `EMB_F16` | token_embed 存 F16（省 ~0.6GB） |
| `VISION` | 含视觉张量（v_q8_ 系列） |
| `ENC` | 数据区 SM4-CTR 加密 + 尾部 HMAC-SM3 tag（VQF-Enc，见 §4.5） |
| `SIGNED` | 含 SM2 签名块（供应链防替换，见 §4.6） |

qtype：`F32 0x01 / Q8_0 0x02 / Q4_0 0x03 / Q4_8X8L 0x04 / F16 0x05`。

> 布局守卫：`vqf_format.h` 以 `_Static_assert(sizeof(VQFSig)==200,
> sizeof(VQFHeader)==432, sizeof(VQFTensor)==64)` 防三方（引擎/离线工具/KAT）漂移。

### 4.3 模型属性自包含

VQF 头部携带全部推理所需属性（`VQFArch`）：`dim / n_layers / n_heads / n_kv_heads /
head_dim / ffn_dim / vocab_size / rope_theta / norm_eps / has_mrope / kv_lora_rank /
has_vision / vis_depth / vis_hidden / vis_patch / vis_merge / vis_out_dim /
vis_ds_count / vis_ds_idx / vision_start_id / image_token_id / video_token_id` 等，
不再依赖 config.json / safetensors index。

### 4.4 加载与预热

- `vqf_load`：mmap + 校验，成功时记录 mmap 区（`st_weights_free` 统一释放）。
- `vqf_prewarm`（`VLLM_VQF_PREWARM=1`）：后台线程 `madvise(WILLNEED)` + 逐页 touch，
  把 eMMC→RAM 页 fault 成本挪到就绪后的空闲期。
- 实测加载 0.3-0.4s（明文）；加密模型加载需全量解密 + HMAC 校验（约 92s，一次性），
  详见 [权重保护与可验证推理方案.md](权重保护与可验证推理方案.md) §3。

### 4.5 VQF-Enc 存储态加密（v2）

VQF v2 支持**国密存储态加密**：`VLLM_VQF_KEY`（口令）经 SM3 派生 SM4-CTR 加密密钥 +
HMAC-SM3 认证密钥；写侧逐张量 SM4-CTR 加密落盘并流式喂 HMAC，加载侧
`mprotect(MAP_PRIVATE COW)` 单遍"认证 + 原位解密"（磁盘密文不变，失败拒绝加载）。
认证覆盖头（`file_len` 按 0）+ 目录 + 密文数据区，防任何字节篡改。
设计取舍与安全边界见 [权重保护与可验证推理方案.md](权重保护与可验证推理方案.md) §3/§7。

### 4.6 SM2 供应链签名（v2）

VQF v2 头部追加 `VQFSig`（200B，pub/r/s/digest/id），对**明文逻辑内容**摘要
`D = SM3(header_canonical ‖ directory ‖ plaintext)` 做 SM2 签名（ID=`"vllm-shs-vqf"`）。
签名与加密/口令正交（同一签名对明文版与任意口令加密版成立）；设备侧只内嵌/注入
公钥（`VLLM_VQF_SIGN_PUB` 或编译期 `VLLM_SM2_PUB_HEX`），私钥仅在离线签名工具
[vllm_vqf_sign.c](../tools/vllm_vqf_sign.c) 使用。加载侧验签：
加密模型默认开启，明文模型经 `VLLM_VQF_VERIFY=1` 显式开启（避免强制全量读抵消
mmap 收益）；自检 `digest` 先比对，再 `vc_sm2_verify`，`sig.pub` 与可信公钥
不一致默认拒绝。详见 [权重保护与可验证推理方案.md](权重保护与可验证推理方案.md) §4。

### 4.7 转换路径（三种，见 README）

1. `--convert-gguf <model.gguf> --wmode q8`：GGUF → VQF（Q4_0…Q8_K 反量化，
   详见 [vllm_gguf.c](../src/model/vllm_gguf.c)，含 chunked 大张量处理）
2. `--convert-vqf <out.vqf> --model <hf_dir> --wmode q8`：safetensors → VQF
   （与 serve 完全相同的加载/量化序列，转换后自检重载 checksum）
3. 管理页 `/convert/` 图形化转换（`POST /admin/api/convert` 子进程，前端轮询进度）

> `--wmode` 须与转换时一致（q8/q4/dual/f16），布局 flags 错配会拒绝加载——设计如此，
> 防位级错配。

## 5. 推理内核

### 5.1 GEMM（引擎内核在 [vllm_safetensors.c](../src/model/vllm_safetensors.c)：`gemm_q8_0_8x8_neon` / `st_gemm_q4_0_4x4_batched` / `llama_gemm_q8_0_4x4_q8_0_neon` 等；`core/vllm_matmul.c` 为同树 SHS 参考栈 vmm_*，非引擎路径）

- **Q8 8x8 tiled**：权重按 8×8 分块重排，ARMv8.2 `vdotq_s32` SDOT INT8 点积；
  激活 Q8 量化（与 LLM GEMM 同精度策略）。
- **Q4 4x4 nibble**：4-bit 权重 nibble 重排。
- **8x8l decode 副本**（`VQF_QT_Q4_8X8L`）：decode 用权重副本。
- **混合精度 dual**（`--wmode dual`）：prefill 用 Q8 混合权重，decode 用 Q4——
  质量档，速度与 q4 几乎持平（见 §11）。

### 5.2 注意力（引擎内核在 [vllm_safetensors.c](../src/model/vllm_safetensors.c)：`sparse_attn_head` / `flash_attn_single_q_q8_neon` / `st_attn_batched_packed_sparse*`；`core/vllm_attention.c` 为 SHS 参考实现）

| 路径 | 条件 | 说明 |
|---|---|---|
| exact | 默认 | Q8 KV 块化注意力（INT8-KV 单遍） |
| sparse | `--sparse-attn`，k=32/block=32/probe=8 默认 | prefill（seq>2×block 自动启用）+ decode top-k 块 |
| online | q8-KV decode 恒定单遍（NEON `flash_attn_single_q_q8_neon`） | 非稀疏 + q8 KV 的 decode 单遍 online-softmax；x86 实验开关 `VLLM_ATTN_ONLINE` 未进入本 aarch64 树 |
| flash | `!use_kv_q8 && !sparse && seq≥64` | 与当前 q8+稀疏栈互斥，仅多模态 q4-KV 在使用 |

质量下边界（S=4096 验证）：**k=32 是下边界**（needle 召回 YES、ppl 3.37）；k=16 失败
（needle NO、ppl 6.2）；k=8 严重退化（ppl 7.6）。`--kv-q4` 与 `--sparse-attn` 互斥。

### 5.3 推测解码（`--spec [--spec-k N]`）

n-gram 自推测：上下文末尾窗口（最长优先 8→3 token）在历史找重复，取其后的 K token
作草稿；`st_qwen_model_prefill_batch` 一次并行 prefill 验证（每位置 lm_head top-1），
贪婪接受，KV 回滚。默认关闭。

**无损性修复（2026-08-31）**：批量验证（prefill_batch）与单 token decode 是两条数值
路径（fused-batched GEMM vs single-row GEMM），浮点差异会逐轮累积进 KV，在模型停止
边界（eos/`<|im_end|>` 竞争）暴露：repeat_same 场景曾输出 90 vs 86 token。修复为
**验证后 KV 回滚 + decode 路径逐 token 重放确认**（`[SPEC-DBG] probe/replay`），KV
与正常解码 bit-exact，输出严格一致（4 类 prompt 实测 PASS）。

**边界（诚实）**：
- **实测在 8B Q8 + RK3588 为负优化**（比无 spec 慢 15-45%，即使 repeat_fixed 92% 接受
  率也只打平）——批量验证计算量 ≈ K×decode，接受率收益覆盖不了，符合 DFlash 2 文档
  "接受长度 ≠ 吞吐" 的警告；无损重放修复后更是无加速。生产不建议开启。
- 仅贪婪文本路径；仅对精确重复文本（模板/代码/叠句）有效，自由文本与编号递增类
  （"第N点"）命中低；草稿超过 mini-batch 自动回退。

### 5.4 连续批处理（`--batch-max N`）

独立后台线程每步 1 次前向 B token（复用 `st_qwen_model_forward_batch`，max 32）；
HTTP worker 提交 per-request 状态。8 并发全 PASS。**位级一致性在跨 prompt 下存在
near-tie 双内核翻转风险（margin 0.71 vs 0.032 级别），非普遍保证。**

## 7. 多模态视觉编码

### 7.1 ViT 结构（[vllm_vision.c](../src/model/vllm_vision.c)）

Qwen3-VL 视觉塔（Qwen3-VL-8B 实测属性，VQF mmap 加载）：

| 属性 | 值 |
|---|---|
| 层数 | **24**（`vis_depth`；源码顶部"27-layer"注释为陈旧错误，以启动日志 `ViT 24 layers` 为准） |
| hidden | 1024 |
| FFN | 4096 |
| patch | 16（temporal=2，图像按 T=1） |
| merge | 2（2×2 spatial merge） |
| DeepStack | 3 条 merger（`vis_ds_count=3`，deepstack 层输出过 merger 注入 LLM 前层） |
| 注意力 | 双向（无 causal mask） |
| 激活 | tanh 近似 GELU |

编码流水线：patch_embed（3D conv）→ pos_embed → 24 层 ViT（block 输出在
DeepStack 层截取）→ spatial 2×2 merge → main merger + DeepStack mergers → LLM
embedding 空间。

**关键事实**：喂给 LLM 的视觉 token 是 **2048 维（= LLM hidden dim）**，不是 HF
`get_image_features` 的 4096 维 `pooler_output`（那是 fc1 中间输出）——客户端预处理
协议按 2048 维实现。

### 7.2 图片视觉 token 缓存（2026-08-31 新增）

位置：`encode_media_item` 的 `image_url` 分支（vllm_server.c）。

- **键**：原始图像字节的 128-bit FNV-1a（`h1 = fnv1a64_buf(raw, 1469598103934665603ull)`，
  `h2 = 另一个偏移种子`），224 与 512 图字节不同 → 键正确区分。
- **缓存内容**：视觉 token（256×2048 fp32）+ 网格 `[gt,gh,gw]` + DeepStack 3 条；
  LRU 4 条，每条 ≈8MB。
- **命中路径**：跳过 ViT 编码，`ds_accum_append_rows` 逐字节回放与重编码一致
  （`ds_accum_append` 同款累积器），日志 `[VIS-CACHE] hit (WxH, n vis tokens, skip ViT)`。
- **实测**：同图命中 TTFT **5.2s** vs 新图 **28.3s**（**-82%**，板端 curl 权威计时）；
  512 图编码 21.5-21.8s（MMDBG 25 轮全平）。

### 7.3 客户端预处理协议 `vision_tokens`（M1）

浏览器/上位机本地完成 ViT 编码，只上传特征，服务端校验后直接注入 prefill：

```json
{
  "type": "vision_tokens",
  "grid": [gt, gh, gw],
  "tokens_b64": "<base64: fp32 LE, n*2048>",
  "ds_b64": ["<base64>", "..."]     // 可选，≤3 条，每条 n*2048
}
```

校验规则（`encode_media_item`，vllm_server.c）：

- `gt/gh/gw ≥ 1` 且 `gt*gh*gw ≤ 4096`；
- `tokens_b64` 解码后字节数必须 == `n*d*4`（n = gt*gh*gw，d = 2048）；
- `ds_b64` 每条与 tokens 同尺寸，最多 3 条；任一不符返回失败（400）；
- 成功日志 `[VIS-TOKENS] client-preprocess n= d= ds= grid=`。

512 图 fp32 特征 ≈2MB（fp16 ≈1MB）。**已知缺陷**：合法请求曾返回 400
`Media decode/encode failed (base64 data URLs required)`，根因未定位（见 §13）。

### 7.4 视频帧（`video_frames`）

`media_load_image_memory` 逐帧解码（需同尺寸），`st_vision_encode_video` 按时间维
patch 编码；grid 首维 = `n_frames_eff`。

## 8. 上下文管理

### 8.1 内存 KV 前缀复用（默认开启；`--no-prefix-kv` 关闭）

- 上一请求完整 token 序列 `last_ids` 保留在内存（`ctx->last_n`）；
- 新请求与 `last_ids` 求 LCP（`kv_lcp`），`l ≥ PREFIX_KV_MIN_LCP` 且 `l < n_ids`
  时 `keep = l`，只 prefill 差异部分（`ist_reset(ctx, keep)`）；
- **正确性防护**：若新 prompt 被上次 KV 完全覆盖（`l == n_ids`），prefill rest=0
  不会刷新 logits，decode 首步会采到上次请求末尾的陈旧 logits（预测 eos）→ 立即
  停止 → 空响应。因此强制 `l < n_ids` 回退全量 prefill。
- 实测 prefill 加速 **4.99x**（253 复用 231 token），输出逐字节一致。
- `context_tokens` 精确变体：客户端回传序列与 last_ids LCP==n_ctx 时 KV 行真实存在，
  可直接 keep。

### 8.2 磁盘 KV 持久化（`--disk-kv DIR`）

- **格式**（vllm_safetensors.c `st_kv_disk_save/load`）：magic `0x564C4B56("VLKV")`、
  version 1、64B 头（nl/nkv/hd/bs/tokens 几何 + token FNV-1a hash），K 块后 V 块
  **fp32 逐字节 fwrite/fread**（`kv_row_f32` 返回 fp32 块直接指针）；
  文件名 `kv_<fnv64>.kv`；上限 8192 token/文件（`DISKKV_MAX_TOKENS`，2026-09-05 由
  768 放宽以覆盖 max_seq=8192 窗口）、8 文件（LRU 按 mtime）。
- **流程**：每次成功文本请求后快照（`dkv_save`）→ 启动扫描建索引（`[KV-DISK]
  index: N checkpoint(s)`）→ 请求时与 checkpoint 求 LCP（≥16）→ `st_kv_disk_load`
  加载 → 只 prefill 差异。
- **跨进程/重启复用**：模型卸载、引擎重启后 `last_ids` 失效，disk-kv 精确恢复
  （`[KV-DISK] context restore N-token KV prefix`），多轮对话跨重启延续
  （页面只需重发 `context_tokens`）。
- 实测 prefill 1328ms→285ms（4.66-5.27x），输出逐字节一致。
- `--l3-evict` 开启时两者自动降级全量 prefill（L3 释放前缀块，prefill 无 NULL 检查）。

### 8.3 重启一致性（2026-08-30 定案）

验证问题："引擎重启后恢复上下文 vs 未关闭连续运行，推理是否存在差异？"（用户关注
GEMM 量化分支差异）。

**结论：字节级一致（PASS）**。机制：

1. KV 由 prefill 一次算出后即固定；
2. disk-kv 以 fp32 无损逐字节落盘/读回，无任何量化往返；
3. 连续运行（内存 last_ids 复用）与磁盘恢复（`st_kv_disk_load`）两路消费**同一份
   KV 字节**，后续 decode 内核输入完全相同 → GEMM 量化分支的浮点实现细节不构成
   重启差异。

实测：R2A（内存复用）与 R2B（磁盘 context restore）的 `content / history_tokens`
全 EQ，仅 `created / metrics` 不同。
**唯一真实风险**：重建引擎后混用旧检查点（KV 头无内核版本指纹）。

## 9. 位级确定性

引擎数值路径（GEMM/attention/softmax/采样）完全确定：同输入同参数输出逐位一致
（多线程 40/40 一致实测；2026-08-29 修复 attention 尾部路径数据竞争）。

注意事项：
- 默认前缀复用属正常（复用路径与全量重算的舍入顺序不同）；严格复现加

- `spec / prefix-kv / disk-kv` 在验证场景下输出与全量逐字节一致；
- `batch`（`--batch-max`）跨 prompt 存在 near-tie 双内核翻转风险，非普遍保证。

## 11. 性能基准

### 11.1 文本（2B Q8，RK3588）

| 指标 | 实测 | 条件 |
|---|---|---|
| prefill | ~480-520ms/9token（≈18 tok/s） | 4 线程 |
| decode TPOT | ~50ms | |

### 11.2 多模态图片（Q8 权重 + Q8 激活 SDOT 批量 matvec）

| 图片 | 编码 | TTFT |
|---|---|---|
| 64×64 | ~4s | — |
| 128×128 | ~6s | — |
| 512×512 | ~22s（MMDBG 25 轮 21.5-21.8s 全平） | ~28s |
| 512×512 同图缓存命中 | 跳过 ViT | **~5s（-82%）** |

较早期版本 5+ 分钟提速约 10 倍；`VLLM_VIS_ACT_F32=1` 可回退 FP32 激活内核
（牺牲 ~60% 速度换取位级一致的旧数值路径）。

### 11.3 注意力/上下文优化（Qwen3-VL-8B，x86 基准机，同条件前后对照）

> 本节为**优化归因**（同机前后对照的相对结论），模型/平台口径与上两节（RK3588 2B）不同；
> RK3588 板端发布级性能与 llama.cpp 对照见
> [RK3588_性能基准报告.md](RK3588_性能基准报告.md)。

| 优化 | 实测 |
|---|---|
| 稀疏 prefill 8K | ATTN **-74%**（61.6→16.0s），total -11.3% |
| 稀疏 decode | TPOT 127ms（8K） |
| prefix-kv | prefill **4.99x** |
| disk-kv | prefill **5.27x**（1328→285ms） |
| spec | **1.30x** 文本 / **1.64x** 多模态（RK3588 341ms/token 理论 2-3x） |
| batch-max 8 并发 | **~1.7x**（22.0→13.1 tok/s 串行对比） |
| dual 混合权重 | +2.4%（质量档） |

与 llama.cpp 对比（各自最快档，1 轮对 1 轮）：

| 上下文 | vllm prefill | llama prefill | vllm TPOT | llama TPOT |
|---|---|---|---|---|
| 4K | 88.9s | 80.3s（llama 快 11%） | 192ms | 100ms |
| 8K | **167.9s** | 184.2s（vllm 快 9%） | 127ms | 121ms |
| 16K | **349.5s** | 448.7s（vllm 快 22%） | 149ms | 155ms |

### 11.4 线程数

- **4 线程最优**（4×A76）；**8 线程摊到 A55 反而慢 2 倍**（图片编码 21.7→47s、
  文本 prefill 也变慢）——根因：A55 小核拖慢 GEMM + 争 8 核。
- `-O2` vs `-Os`：快 ~5%（2B Q4，132-token prefill）。

### 11.5 其他

- VQF 加载 0.3-0.4s（mmap 直挂）；`--auto-unload` 空闲卸载 RSS 回落 2-3GB。
- 内存：8B Q8 ≈8.7GB（需 16GB+）；服务有 `free_ram_min` 保护（内存不足 503）。

| core dump | 崩溃时生成在启动目录 `core.*` |
| `status.sh` / `vllm_mgr.py status` | 进程状态 + 健康检查 |

MMDBG 使用纪律：粗粒度 `VIS_STEP` 是权威；细粒度日志因无 fflush 在 stderr 全缓冲
下不可靠，须以粗粒度为准或单独 flush 插桩。

## 13. 已知问题与边界（诚实清单）

1. **`vision_tokens` 合法请求返回 400**（M1 缺陷，未定位）：错误体
   `Media decode/encode failed (base64 data URLs required)`；该错误信息在源码中的
   确切来源尚未找到。实现已完成但端到端验证未真正通过。
2. **8K+ quality 路径间歇性 prefill 崩溃**：在 5120/6400 及 512/2049 处复现过，
   与优化无关，属既有问题。
3. **多模态 prefill 概率性悬挂**：MMDBG 第 25 轮板端流式 prefill 悬挂（日志停在
   `[MMDBG] n_tokens` 与 `prefill done` 之间），与原 60s 超时一致，待复现定位。
4. **batch 跨 prompt 位级一致非普遍保证**（near-tie 翻转，margin 0.71 vs 0.032）。
5. **重建引擎后混用旧 disk-kv 检查点**：KV 头无内核版本指纹（唯一重启一致性的真实
   风险）。
6. **8 线程负优化**：A55 小核拖慢，保持 `VLLM_THREADS=4`。
7. **热节流/后台负载**：跨时间绝对性能数值会波动（曾见整体 1.5x），正式基准应干净
   控制台、低负载时段串行执行。
8. **`VLLM_ATTN_ONLINE` 的 prefill 收益为负**（x86 实验 +5.7%，见 [优化配置与边界说明.md](优化配置与边界说明.md)；该开关仅存在于 x86 开发树，aarch64 发布树不读取，板端 q8 decode 已恒定单遍）。
9. **推测解码仅对精确重复文本有效**，编号递增类系统性 0% 命中；且实测在 8B Q8 +
   RK3588 上整体负优化（2026-08-31 三阶段对比，详见 §5.3）。
10. **TTFT/prefill 指标不含视觉编码时间**（`met->start_s` 在
    `run_multimodal_completion` 入口计时，结构性问题，已记录）。
11. **`--test-sparse` 自检段错误**（2026-09-05 板端 Release 构建实测）：该入口
    （`st_test_sparse_attn`，合成 KV 无模型加载）段错误；**主仓同世代产物在板端
    同样崩溃**，属既有问题而非发布树整理引入。不影响推理路径（`--bench-mixed`
    / `--test-l3` 冒烟 PASS、serve 正常）；`build_rk3588.sh --run-tests` 会执行到
    该入口，排查前建议以 `--bench-mixed` + `--test-l3` 作为构建冒烟。根因待定位
    （疑似 Phase-1 稀疏自检的静态数据/栈问题）。

## 14. 部署形态说明（参考）

从本仓库构建出的 `vllm_kestrel` 为单文件可执行程序；建议部署目录形态：

```
<deploy-root>/
├── vllm_kestrel            # aarch64 可执行文件（全静态链接时零 .so 依赖）
├── start.sh            # 启动（模型目录自动探测；VLLM_THREADS=4；WMODE=q8 默认）
├── stop.sh / status.sh
├── tools/vllm_mgr.py   # 进程守护（start/stop/restart/HTTP 状态页）
├── vocab.bin           # 词表
├── 技术文档.md          # 完整技术文档
├── 目前支持的模型.txt
└── README.md           # 使用手册
```

> 二进制为 glibc 全静态链接（2026-08-31）：`ldd` 输出 `not a dynamic executable`，
> 可拷贝到任意 aarch64 Linux 设备直接运行，无需预装 glibc/libm/libgomp。
> 注意：`admin.html / chat.html / convert.html` 已内嵌进二进制，无需随包分发；
> 如后续部署独立 html 副本，运行时会优先于内嵌版。

生产运行参数（板端实测）：`--serve --wmode dual --disk-kv <kv-dir>
--auto-load --load-on-use`，推理线程 `VLLM_THREADS=4`。
