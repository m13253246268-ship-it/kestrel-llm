本目录是 **Qwen3-30B-A3B（MoE）在本机（N1/aarch64 云实例）** 的原始产物归档：线程 scaling、
全层 vs 逐层驻留对照、稀疏注意力对照。结论只做解读，引数请回这里的 `bench*/` 与 `*.log` 核对。

二、冻结口径（预注册，未事后改动）
================================================================================
命令：vllm_kestrel --stream-test --model <30b-dir> --warmup --stream-ctx <CTX> --stream-n 32
线程：OMP_NUM_THREADS = VLLM_THREADS = T（引擎计算线程池唯一入口 vllm_tp_init）；
      VLLM_TP_SPIN 未设（默认 200000）；VLLM_TP_BIND 未设（默认不绑核）
页缓存：热；每格自带 --warmup（丢弃 1 prefill + 8 decode），脚本开头另有全局丢弃预跑
轮次：**同轮内交错**（每格一个独立进程；升/降序交替）；单实例 flock 锁防并发污染
G0 门：同一档位内、同轮内所有 T 的 TOKIDS 必须逐位相同 —— **全部 PASS**
线程档核验：逐格采样引擎 /proc/<pid>/status Threads，实测 nlmax == T
自证：每格落盘 `<cfg>` 全名与整机 ENV 头（含 binary sha256 / model.vqf md5 / load / buff/cache）

三批（K_CTX / T 臂 / 轮数）：
  A. 主扫描   ctx=256，T ∈ {1,2,4,8,16,32,64}，2 轮，档位 {full}
  B. 核心数+驻留 ctx=256，T ∈ {32,40,48,56,64}，2 轮，档位 {full, stream}  ← 同轮交错 A/B
  C. 稀疏对照 ctx=4096，T ∈ {32}，2 轮，档位 {full, sparse}                ← 同轮交错 A/B
稀疏档 = `--sparse-attn --sparse-k 32`（**保持全层驻留**）；block=32 / probe=8 均为代码默认，
故 k*block = 1024 是剪枝阈值，ctx=4096 的 decode seq_len≈4118 > 1024 才真正剪枝。
前置自检：`--test-sparse` 本机 **9/9 PASS**（见 test_sparse.log），证明稀疏路径可用。

已作废并留证：
 · bench/sparse_VOID_stream_mixed —— 首版 harness 把稀疏档误配成"逐层+稀疏"，测得 decode 407 ms
   被误读为稀疏代价；实为逐层的固定开销（见下 §3.2）。修好后重跑得 §3.3。
 · 主扫描的第 3 轮（r3_*）被作者主动中止删除（前 2 轮已收敛到 0.06% 以内，项目自身亦为 2 轮口径）。

三、结果
================================================================================
3.1 线程 scaling（档位 full，ctx=256，2 轮中位）
  T  | prefill_s [min~max]      | 加速  | decode ms/tok [min~max] | 加速
 ----+--------------------------+-------+-------------------------+-------
   1 | 132.930 [132.892~132.967]| 1.00x | 951.5 [950~953]         | 1.00x
   2 |  78.092 [ 77.181~ 79.003]| 1.70x | 485.5 [485~486]         | 1.96x
   4 |  40.219 [ 39.453~ 40.986]| 3.31x | 251.5 [251~252]         | 3.78x
   8 |  19.530 [ 19.369~ 19.692]| 6.81x | 135.0 [135~135]         | 7.05x
  16 |  11.561 [ 11.487~ 11.636]|11.50x | 117.0 [117~117]         | 8.13x
  32 |   7.155 [  7.133~  7.177]|18.58x | 110.0 [110~110]         | 8.65x
  64 |   4.543 [  4.533~  4.552]|29.26x | 129.5 [129~130]         | 7.35x
  → **MoE 的 decode 在 8.65x 处饱和（t32 最优），prefill 则一路到 t64（29.26x）。**
    与 8B（decode 17.19x / prefill 21.65x）形成鲜明对比：MoE 每 token 只激活 top-8/128 专家
    （约 1.6 GB），激活权重少、专家 gather 的访存模式差，故并行效率低得多。

3.2 核心数细化 + 全层 vs 逐层（ctx=256，5 臂 × 2 轮，同轮交错）
  T  | full prefill/decode  | stream prefill/decode | prefill比 | decode比 | RSS full→stream
 ----+----------------------+-----------------------+-----------+----------+-----------------
  32 | 6.892 / 109.5        | 6.981 / 387.0         | 1.01x     | 3.53x    | 13,602 → 556 MB
  40 | **6.337 / 109.5**    | 6.633 / 390.5         | 1.05x     | 3.57x    | → 535 MB
  48 | 5.522 / 111.5        | 5.743 / 404.5         | 1.04x     | 3.63x    | → 526 MB
  56 | 5.112 / 113.5        | 5.416 / 405.5         | 1.06x     | 3.57x    | → 502 MB
  64 | 4.472 / 130.5        | 4.783 / 437.0         | 1.07x     | 3.35x    | → 486 MB
  → **decode 最优平台 = t32~t40（109.5 ms 完全并列）**；t48 +1.8%、t56 +3.7%、t64 +19.2%。
    t40 在 prefill 上还比 t32 快 8%（6.337 vs 6.892），故 **t40 是两指标都不吃亏的点**；
    **t64 不是 decode 的好选择**（虽然 prefill 最快）。
  → 逐层的 TOKIDS 与全层**逐位相同**（md5 b1304c6459e0，0/32 差异）→ 语义不变，本机独立复现。
  → **逐层的 decode 代价是一笔"固定摊还"**：stream − full = 277.5 / 281.0 / 293.0 / 292.0 / 306.5
    ms per token（t32→t64），几乎不随线程数/算力变 —— 就是 17.67 GB 权重每 token 重建页映射的
    成本。**机器算得越快，这笔固定成本占比越高**：板端 RK3588 只慢 1.77x，这里慢 3.4~3.6x。
    用该模型反推 8B（6.15 GB）约 283 × 6.15/17.67 ≈ **98 ms/token**，与 README 板端 8B
    实测的 +133 ms（185→318）同量级 —— 预测与实测自洽。
  → 常驻内存 full 13.6 GB → stream 486~556 MB，**降 24~28 倍**。

3.3 稀疏注意力 / 稀疏解码（档位 full vs sparse，ctx=4096，t32，2 轮）
  | 档位   | prefill_s [min~max]       | decode ms/tok [min~max] | ids md5      |
  |--------+---------------------------+-------------------------+--------------|
  | full   | 127.334 [124.595~130.072] | 133.0 [133~133]         | 3b3d1f0435a9 |
  | sparse | 130.194 [129.362~131.026] | **127.0** [127~127]     | 3df354a7fbd0 |
  | 比     | 0.98x（sparse 慢 2.2%）   | **1.05x（sparse 快 4.5%）** | 9/32 位不同 |
  → 稀疏在 decode 上**只赢 4.5%（−6 ms/token）**，prefill 反而付 2.2%（重要性记录的建表成本）。
  → 机制（可核）：ctx 256→4096 使全驻 decode 从 109.5 → 133.0 ms，即**注意力的全部代价只有
    ~23.5 ms/token（占 18%）**；k=32 块 / 129 块把 KV 读压到 25%，理论上限省 ~18 ms，扣掉
    top-k 选块与探针（probe=8）开销后净剩 6 ms。**在本机 30B-A3B 上，decode 是"专家权重读取"
    受限而非注意力受限，所以稀疏注意力没有发挥空间**。
  → 稀疏档与全驻档的 TOKIDS 有 9/32 位不同 —— 这既是"换轨才改数值"的正常表现，也**反证
    `--sparse-attn` 确实生效**（不是静默没挂上）。

================================================================================
四、必须一并引用的边界
================================================================================
1. **这是 Neoverse-N1 / aarch64 云实例数据，不是 RK3588 板端数据**；绝对数字不跨机器、不跨
   session 外推。README「性能」章的板端数字不可与本表并列或混引。
2. RK3588 的「--threads 8 比 4 慢 1.8~2.5 倍」是 big.LITTLE 特异性结论，**不是本机预期**：
   本机同构 64 核，decode 最优平台在 32~40 核，t64 才退化 19%。
3. 本机无 cpufreq / thermal 节点，**记不到 governor 与温度**；steal_ticks=0 是唯一可得的
   "未被抢占"证据。load average 高（20~27）来自引擎自身的 spin 工作线程，已核 0 个 D 状态进程。
4. **ctx 与 8B 那批不同**（8B=512，本批=256 / 4096）。同一批内所有臂同 ctx，故"加速比/档位
   比值"这一结论对象不受影响；但**跨模型的绝对时间不可直接比**（还有模型本身的量级差）。
5. **稀疏对标的是"本版精确轨"**（`--sparse-attn` 缺省关闭），不是与第三方引擎对照；
   §3.3 只说明"在本机本上下文，稀疏相对本版稠密路径的净收益"。README §7 的对照是
   "本版稀疏 vs llama.cpp"，两者口径不可混引。
6. 稀疏档是**近似轨**（9/32 位不同）；本归档不主张它无损。要求位级一致的场合用 full 档。
7. 稀疏在 prefill 侧**本来就不参与**：代码里 prefill 恒走精确注意力，稀疏只作用于 decode
   （见 src/model/vllm_safetensors.c L18300-18312 的结论段；`VLLM_SPARSE_PREFILL=1` 是已被
   作者实测判否的诊断门，默认不接线）。故 §3.3 的 prefill "0.98x" 是重要性记录的副作用，
   不是"稀疏 prefill"。
8. 只测单请求串行（--stream-test 骨架），**不含并发服务**；服务工作线程 `--threads` 与计算
   线程池无关，本表未涉及。
9. 30B 的 KV 会随上下文增长：ctx=4096 时全驻 rss_end 14.8 GB（含 KV），ctx=256 时 13.6 GB。
10. 逐层的 decode 固定开销数值（§3.2）**依赖本机存储/内存层级**：本机权重全在页缓存里，
    那 283 ms 是纯"重缺页/建页表"成本；若权重在慢介质上，逐层还要叠加真实 I/O 时间。
