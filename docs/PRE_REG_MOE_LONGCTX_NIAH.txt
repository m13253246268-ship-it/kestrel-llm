================================================================================
PRE_REG_MOE_LONGCTX_NIAH —— MoE 30B-A3B 长上下文「多轮积累 × 捞针」性能与质量协议
（跑前冻结，禁止事后回改阈值/口径）
================================================================================
0. 目的（用户指令原文要点）
   在**逐层驻留**档下，用**官方可用优化组合**，对 MoE 模型跑一次长上下文测试：
   ctx ∈ {1K, 2K, 8K, 16K}，**用多轮对话积累上下文长度**，**用真实文本**，
   **冷、热各一轮**，并且要**同时收 推理质量 与 推理性能**，**含内存占用峰值**。
   ⇒ 只出「优化档」一份结论；**不加精确轨对照**（用户已裁决）。

1. 测点身份（冻结）
   机    ：orangepi5plus / RK3588 / 8 核（4×A76+4×A55）/ RAM 15,964 MB / swap 7,982 MB
   模型  ：/mnt/VQF/qwen3-30B-A3B-q4/model.vqf = 17,665,601,544 B（Qwen3MoE，48 层，128 专家，
           top-8，moe_ffn=768，vocab=151,936，max_position_embeddings=40960，头内 max_seq=8192）
   引擎  ：/mnt/emmc/saprobe/vllm_kestrel（sha256 跑前落盘；与 build-rk3588/ 同为 `90614b2e…` 系）
   线程  ：OMP_NUM_THREADS=VLLM_THREADS=**4**（铁律：threads 8 会把 A55 拉进 GEMM）
   头部补丁：头内 `max_seq_len` 8192 → **20480**（只改 4 字节元数据，脚本自动备份 4096B 头；
           既有做法，见 README §7 的 16K 档）。跑完 **--restore** 回滚。

2. 优化档（用户「开启可用优化」的落地口径 —— 逐层 + 组合① + 组合⑤）
   VLLM_VQF_STREAM=1        （逐层驻留；用户指定）
   VLLM_L3_PREFIX_REUSE=1   （组合①铁律：不置它则前缀复用被静默打掉、多轮全量重算）
   VLLM_ACTQ=1              （组合⑤：MoE 专家激活量化）
   VLLM_MOE_BATCH=1         （组合⑤：专家批量）
   VLLM_NPU_FORCE_CPU=1     （无 NPU 后端，显式走 CPU 路径）
   --serve --port 18180 --device arm-rk3588-opi5 --model <模型目录> --auto-load
   --threads 4 --sparse-attn --sparse-k 32
   --l3-evict --l3-ratio 0.75 --l3-min-seq 128 --l3-path /mnt/emmc/niah_mt_l3
   **性质声明（必须同引）**：`VLLM_ACTQ=1` 与 `--sparse-attn` 都是**近似轨**（会改变数值/TOKIDS）。
   故本协议的**质量结论只对「优化档」成立**，不得表述为精确轨质量。

3. 多轮积累协议（冻结）
   真实语料：/mnt/emmc/prefill_lab_20260923/corpus_manual.txt（611,639 B，中文；去 CR/LF 与引号后使用）
   密钥    ：唯一串 `KX2B7415`。埋针文本「【档案】唯一激活码是 KX2B7415，请牢记。」
   埋针位置：**固定绝对位置**——放在第 1 轮内容的 ~25% 处（≈目标 1K 的 0.25），此后**不再改动**，
             故随上下文增长，针的**相对深度递减**（1K≈50% → 2K≈25% → 8K≈6% → 16K≈3%）。
   提问    ：每一轮的**最后一条 user 消息**都以「请只回答：文档中的唯一激活码是什么？」结尾。
   累加机制：第 1 轮带全部内容建上下文；第 2..4 轮**回传引擎给的 `history_tokens`（context_tokens）**
             并只追加本轮新增语料 ⇒ 由引擎做**前缀复用**，只 prefill 增量（这正是组合①要测的能力）。
   轮次    ：一轮 = 走完 1K→2K→8K→16K 四轮（同一 serve 进程内）。
   长度控制：首轮用「字符数 ÷ 1.5」估 token 建内容，随后用引擎回报的 `prompt_tokens` 反推
             **实测字符/token 比**再建后三轮；**报告里一律写引擎实测的 `prompt_tokens`**（不写目标值）。

4. 冷 / 热定义（冻结）
   冷轮：`pkill -9` → `sync; echo 3 > /proc/sys/vm/drop_caches` → **清空 L3 KV 目录** → 起 serve → 跑四轮。
   热轮：**同一 serve 进程**，冷轮结束后**不做任何清缓存**，立即**原样重跑同一套四轮**
         （此时页缓存最热 + 前缀 KV 已在内存/L3）。
   诚实边界：30B 权重 17.67 GB **大于** 物理内存 15.6 GB ⇒ 逐层档下「热」也只能是**部分热**
             （每趟仍要把 48 层权重各读一遍）；本项的"热"= 页缓存尽量热 + 前缀 KV 热。

5. 采集项（每格一行，落盘 niah_mt/summary.tsv）
   质量：`answer` 原文 + `YES/NO`（判据 = 回答文本中是否出现 `KX2B7415`，**按文本判，不看引擎日志**）
   性能：`prompt_tokens`（引擎回报）、`prefill_ms`、`ttft_ms`、`tpot_ms`、`total_ms`、`tok_s`、
         `reused_prefix`（是否命中前缀复用）、HTTP 墙钟
   内存：`VmRSS` 与 **`VmHWM`（峰值）**（/proc/<pid>/status，每轮结束后采样；另记进程存活期峰值）
   过程：serve 启动耗时、`[KV-PREFIX]` 行、异常/重试记录
   文件：每轮原始 SSE 落盘 `niah_mt/turn_<round>_<target>.sse`；serve 日志 `niah_mt/vllm_<round>.log`

6. 判据（跑前冻结）
   G0   四档均须拿到 `prompt_tokens` 与内存采样；缺任何一格即该格标 `MISSING`（不得由邻档插补）。
   Q-CTX 质量曲线：四档的 `YES/NO` 序列**如实报告**（本协议**不设**"必须全 YES"的门槛——
        它是测量而非验收；长上下文失效点就是结论本身）。
   P-CTX 性能：逐档报告 `prefill_ms / ttft_ms / tpot_ms`，并报告**前缀复用的增量 prefill**
         （即第 2..4 轮的 `prefill_ms` 应显著小于第 1 轮同长度全量 prefill）。
   M-PK  峰值：逐档报告 `VmHWM`；**必须**与 `VmRSS` 并列（长上下文只有峰值能说话）。
   R-热  冷/热两轮的同比：报告每档 热/冷 的 `tpot_ms` 比与 `VmHWM` 比。
   崩溃处置：8K+ 已知有「quality 路径间歇性 prefill 崩溃」（wiki 优化页 §口径警告）。
         规则：**任一格若进程死亡 ⇒ 记录 `CRASH`，重启 serve 后重试该轮至多 1 次**；
         再失败则该格记 `CRASH×2` 并**继续下一档**；禁止静默跳过、禁止事后删格。

7. 必引边界
   · 结论只对**本机（RK3588/4 线程）+ 本优化档（近似轨）**成立，不得外推为精确轨质量或他机性能。
   · 「热」是部分热（见 §4）；不得与 N1（245 GiB 全缓存）的"热"混引。
   · 语料是**单一中文文档**，不是多领域/多文档语料；捞针是**单针单密钥**，不是 NIAH 全扫。
   · 头内 max_seq 被临时抬到 20480（§1）；跑完必须 `--restore`，不得留补丁状态。

8. 不做事项
   1. 不加精确轨对照臂（用户已裁决）。
   2. 不跑 sparse-prefill（`VLLM_SPARSE_PREFILL`）——它另有质量门未过（8B 未验），与本轮无关。
   3. 不改任何阈值/口径；不删格；不用目标长度冒充实测长度。
   4. 不把本轮结果并入已收口的形态 A（PRE_REG_STREAM_SA §9）账目。

9. 跑前勘误（2026-09-25，在跑判据臂**之前**；据冒烟实测，**不改质量判据本身**）
================================================================================
冒烟（`NIAH_TARGETS=1024 NIAH_ROUNDS=cold`）实测：`prompt_tokens=468`、`prefill=305,132ms`、
`ttft=305,133ms`、`tpot=673.1ms`、`rss=595,672kB`、**`hwm=977,888kB`**、`reused_prefix=false`、
`got=NO`；引擎侧 `[PREFILL-TIMING] n=468 total=295,733ms | GEMM=292,613ms(98.9%) ATTN=2,414ms(0.8%)`。

  (E1) **长度公式修正**：目标 1024 只得到 468 token —— 原式写成 `字符 = 目标 ÷ cpt`（方向反了）。
       实测语料 **1.60 字符/token**，正确式 `字符 = 目标 × cpt`。已改，并仍以引擎回报的
       `prompt_tokens` 为**唯一**长度口径（报告只写实测值）。**判据 Q-CTX/P-CTX 未动。**
  (E2) **`max_tokens` 64 → 256**：冒烟的回答在 token 64 处被**截断在半句**（原文已引到「【档案」），
       故 `got=NO` 是**截断伪影，不是丢针**。本模型为思考型，64 不足以走完「推理 + 作答」。
       ⇒ 生成上限改 256；并在 summary 增加 `finish` 列（`stop`/`length`），
       **凡 `finish=length` 的格，其质量判读必须标注"可能被截断"**（不得直接当作丢针）。
  (E3) 副产物（性能口径的重要发现，须同引）：1K 档 prefill 的 **98.9% 是 GEMM**、注意力仅 0.8%
       ⇒ 板端 prefill 在 ≤2K 是**权重读主导**（17.67 GB / ≈290 s ⇒ ≈61 MB/s），
       注意力项要到 8K/16K 才显著（按 468→8K 的 S² 外推约 +12 min）。
