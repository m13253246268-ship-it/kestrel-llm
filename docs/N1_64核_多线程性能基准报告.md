## 1. 测量口径（运行前冻结）

### 1.1 命令与线程口径

```bash
/usr/bin/time -v env OMP_NUM_THREADS=T VLLM_THREADS=T \
    ./vllm_kestrel --stream-test --model <model-dir> \
    --warmup --stream-ctx <CTX> --stream-n 32
```

**必须知道的一个事实**（否则线程实验做错）：`--threads` 只设 **HTTP worker 线程数**（1..32），
**不参与计算并行**；计算线程池的唯一入口是 `vllm_tp_init()`，它只读 `OMP_NUM_THREADS`，
为空再读 `VLLM_THREADS`。本报告因此统一用 `OMP_NUM_THREADS = VLLM_THREADS = T`，
并**逐格采样引擎 `/proc/<pid>/status` 的 `Threads` 字段核验**（实测 `nlwp_max == T`，
即设定确实生效，不是"设了没起作用"）。

### 1.2 固定项与门

| 项 | 取值 |
|---|---|
| `VLLM_TP_SPIN` | **未设**（代码默认 200000） |
| `VLLM_TP_BIND` | **未设**（默认不绑核；开启后 worker 轮转绑到性能集群、caller 绑最后一个逻辑核） |
| 驻留档 | 默认**全层驻留**；`stream` 档显式置 `VLLM_VQF_STREAM=1`（逐层） |
| 近似轨 | 默认关闭；`sparse` 档显式加 `--sparse-attn --sparse-k 32`（block=32 / probe=8 均为代码默认） |
| 页缓存 | **热**（权重全量进页缓存，`buff/cache` 全程 101 GiB）；每格自带 `--warmup`（丢弃 1 prefill + 8 decode），另在批前做一次全局丢弃预跑 |
| 轮次 | 同轮内**对每个线程数交错跑完所有档位**；每格一个独立进程；升序/降序交替以抵消顺序效应 |
| 并发 | 单实例 `flock` 锁硬拒绝并发（并发实例会互相污染计时，采集期已实际发生过一次，见 §6） |
| G0（硬门） | **同一档位内、同轮内所有 T 的 TOKIDS 必须逐位相同**；违反则该格 VOID |

**G0 结果**：8B 21/21 格 PASS；30B 全部批次 PASS。即**线程数不改变数值**——与 README
「并行按 idx 静态切分、不改任何浮点步序」一致，本机独立复现。

### 1.3 稀疏注意力 / 稀疏解码的开关事实（先纠正一个常见误解）

- **prefill 恒走精确注意力，稀疏只作用于 decode**（`src/model/vllm_safetensors.c` L18300-18312
  的结论段：作者实测"稀疏 prefill"会污染选块信号，使针块重要性名次从 12/513 掉到 188/513）。
  `VLLM_SPARSE_PREFILL=1` 是**已被判否的诊断门**，默认不接线。
- 因此"稀疏注意力"与"稀疏解码"在本版**是同一个开关** `--sparse-attn`（Phase 1：块级 top-k 稀疏 decode）。
- **剪枝阈值 = `sparse_k × sparse_block` = 32 × 32 = 1024 token**：`st_sparse_k_eff()` 在
  `--sparse-ratio` 未设时恒返回 `g_sparse_k`(32) 块，而块数 = `ceil(seq_len/32)`，
  **只有 `seq_len > 1024` 才真的丢块**；阈值以下不剪枝、只白付重要性计算。
- 前置自检：`--test-sparse` 在本机 **9/9 PASS**（含 top-k 位级确定性、INT8-KV 一致性、needle 召回），
  证明稀疏路径在本机可用、不是静默降级。

### 1.4 三批测点

| 批 | 模型 | `--stream-ctx` / `--stream-n` | 线程臂 | 档位 | 轮数 |
|---|---|---|---|---|---|
| A | 8B | 512 / 32 | 1,2,4,8,16,32,64 | full | 3 |
| A′ | 8B | 512 / 32 | 32,40,48,56,64 | full | 4 |
| A″ | 8B | 512 / 32 | **不设任何线程环境变量** | full | 2 |
| B | 30B-A3B | 256 / 32 | 1,2,4,8,16,32,64 | full | 2 |
| C | 30B-A3B | 256 / 32 | 32,40,48,56,64 | full, stream | 2 |
| D | 30B-A3B | 4096 / 32 | 32 | full, sparse | 2 |

> 30B 的 prompt 用 256 而非 8B 的 512：MoE 每 token 成本约为 8B 的 7 倍，ctx=512 时 t1 单格约
> 12.5 分钟。ctx 在**同一批内所有臂一致**，故"加速比 / 档位比值"这一结论对象不受影响。

| 4 | 18.725 [18.714~18.726] | 3.86× | 162.0 [161~162] | 3.82× |

### 2.2 t32 以上细化（批 A′，4 轮交错）

| T | prefill 中位 [极差] | decode ms/tok 中位 [极差] |
|---|---|---|
| 32 | 3.336 [3.330~3.344] | 36.0 [36~36] |
| 40 | 3.151 [3.142~3.160] | 35.0 [35~36] |

**结论**：decode 在 **t32~t56 是一段平台（35~36 ms）**，到 t64 **掉到 61.5 ms（−42%）**，
且 t64 逐 token 出现 133/109 ms 级尖刺（见 §6 机制）。prefill 则一路改善到 t64。

### 2.3 引擎默认档（批 A″，不设 `OMP_NUM_THREADS`/`VLLM_THREADS`）

`aarch64` 分支的默认推导是"按 `cpu_capacity` 取性能集群规模，推导不可用则退回全部逻辑核"；
在本机（同构 64 核、容量全相等）**实取 64 线程**（`nlwp_max == 64`，两次复现）：

| 运行 | prefill | decode |
|---|---|---|
| default #1 | 2.476 s | 62 ms/tok |
| default #2 | 2.489 s | 53 ms/tok |

即 **本机"不配线程"= 全核 = decode 最差档**：prefill 最优（2.48 s），但 decode 落在悬崖上
（61.5 ms 档），比 t32~t56 的平台慢约 45%。

| T | full prefill / decode | stream prefill / decode | prefill 比 | decode 比 | RSS full → stream |
|---|---|---|---|---|---|
| 32 | 6.892 / 109.5 | 6.981 / 387.0 | 1.01× | 3.53× | 13,602 → 556 MB |

| 64 | 4.472 / **130.5** | 4.783 / 437.0 | 1.07× | 3.35× | → 486 MB |

（`stream` 档的 TOKIDS 与 `full` **逐位相同**，md5 `b1304c6459e0`，0/32 差异。）

### 3.3 结论：MoE 与稠密模型的线程曲线形状**不同**

| 维度 | Qwen3-VL-8B（稠密，6.15 GiB） | Qwen3-30B-A3B（MoE，17.67 GB） |
|---|---|---|
| decode 最佳加速比 | **17.19×**（t32） | **8.65×**（t32） |
| 饱和点 | t32~t56 平台，t64 −42% | t32~t40 平台，t48 +1.8% / t56 +3.7% / t64 +19.2% |
| prefill 最佳加速比 | 28.97×（t64） | 29.26×（t64） |
| 原因（可核） | 稠密 decode 每 token 读全部 4.25 bpw 权重，**带宽受限** | 每 token 只激活 top-8/128 专家（约 1.6 GB），激活量小、专家 gather 访存模式差，**并行效率低得多** |

**工程结论**：在本机这类 many-core 同构 aarch64 上，**decode 的最优线程数是 32~40，不是 64**；
prefill 则越大越好。因为 `aarch64` 分支默认取"全核"，在 64 核机上**默认档正好是 decode 最差档**。

## 4. 全层驻留 vs 逐层驻留（`VLLM_VQF_STREAM=1`）

批 C 的同轮交错对照（同 T 匹配）：

- **常驻内存：13.6 GB → 486~556 MB，降 24~28 倍。**
- **prefill 几乎不付代价**：逐层只慢 1.0%~7.0%（t32 1.01× → t64 1.07×）。
- **代价全在 decode：慢 3.35×~3.63×**，且这笔代价是**固定摊还**——

| T | stream − full（ms/token） |
|---|---|
| 32 | 277.5 |
| 40 | 281.0 |
| 48 | 293.0 |
| 56 | 292.0 |
| 64 | 306.5 |

差值 277~307 ms 且**几乎不随线程数变化**，说明它是"每 token 把 17.67 GB 权重重建一次页映射"
的固定成本，与算力无关。**推论：机器算得越快，这笔固定成本占比越高。**
README 板端实测逐层 decode 只慢 **1.72~1.76×**（8B `--stream-test` t4 热：全层 185 → 逐层 320/318 ms，
即 +73%、差 +135/+133 ms；30B-A3B 精确轨 t4 热：全层 325 → 逐层 572/573 ms，即 +76%），
本机 30B 却慢 **3.5×**。

**自洽性检查（预测 vs 实测）**：按权重体积线性外推，8B（6.15 GB）的固定成本
≈ 283 × 6.15/17.67 ≈ **98 ms/token**；README 板端 8B 实测差值 **+133 ms**——同量级。

**语义**：逐层与全层的 TOKIDS **逐位相同**（md5 `b1304c6459e0`），即"驱逐只丢干净文件页、
内容由文件重建"，本机独立复现。

## 5. 稀疏注意力 / 稀疏解码（`--sparse-attn --sparse-k 32`）

批 D：**全层驻留**下、ctx=4096（decode `seq_len ≈ 4118 > 1024`，真正剪枝）、t32、2 轮交错：

| 档位 | prefill 中位 [极差] | decode ms/tok 中位 [极差] | TOKIDS md5 |
|---|---|---|---|
| full（精确轨） | 127.334 s [124.595~130.072] | 133.0 [133~133] | `3b3d1f0435a9` |
| sparse | 130.194 [129.362~131.026] | **127.0** [127~127] | `3df354a7fbd0` |
| 比 | **0.98×（sparse 慢 2.2%）** | **1.05×（sparse 快 4.5%）** | 9/32 位不同 |

**净收益只有 decode 的 4.5%（−6 ms/token），prefill 反而倒亏 2.2%。** 机制可核：

1. ctx 256 → 4096 只让全驻 decode 从 109.5 涨到 133.0 ms，即**注意力的全部代价仅 ~23.5 ms/token（占 18%）**；
2. `k=32` 块 / 129 块把 KV 读压到 25%，理论省约 18 ms；
3. 扣掉 top-k 选块 + `probe=8` 探针的固定开销后，净剩 6 ms；
4. **本机 30B-A3B 的 decode 是"专家权重读取"受限、不是注意力受限，所以稀疏注意力没有发挥空间。**

**开关确实生效的证据**：sparse 与 full 的 TOKIDS 有 9/32 位不同（"换轨才改数值"的正常表现），
且 prefill 因重要性记录多花 2.2%。另 `--test-sparse` 自检 9/9 PASS。

> 边界：本节对照的是**本版精确轨**（`--sparse-attn` 缺省关闭），**不是**与第三方引擎对照。
> README §7 的"本版稀疏 vs llama.cpp"是另一套口径，二者不可混引。稀疏档为**近似轨**，本报告
> 不主张其无损。

## 6. 测量纪律记录（含两次作废与修正，留证）

1. **VOID ①（8B）**：首次启动时旧实例未退出，**两个 `k_bench.sh` 并发**（因中途覆盖运行中的
   脚本，bash 按偏移续读新内容）→ 计时互相污染。除 t64 外各档与干净轮复现一致（±0.1%），
   但整轮判 VOID。留证：`20260924-n1-thread-scaling/bench_run_VOID_2instances.log` +
   `SUMMARY_VOID_2instances.tsv`。此后 harness 加 `flock` 单实例锁。
2. **VOID ②（30B 稀疏）**：harness 把 `sparse` 档误配成"**逐层** + 稀疏"（复制粘贴 `VLLM_VQF_STREAM=1`），
   测得 decode 407 ms，一度被误读为"稀疏慢 3 倍"。核对后：407 ≈ 逐层的固定开销（133 + 274），
   与本项目 §4 的固定摊还模型吻合。修正档位定义（sparse 保持全层）后重跑得 §5。
   留证：`bench/sparse_VOID_stream_mixed/` + `bench_sparse_VOID_stream_mixed.log`。
3. **主动裁剪**：30B 主扫描的第 3 轮被主动中止删除——前 2 轮已收敛到 0.06% 以内（t1：
   132.892 / 132.967 s），且项目自身亦采用 2 轮口径。
4. **t64 decode 的形态**：不是均匀变慢，而是逐 token 尖刺（8B t64 首 8 个 =
   `[48, 37, 37, 37, 87, 37, 37, 114]` ms；30B t64 = `[116, 137, 128, 133, 139, 118, 130, 150]`），
   典型"提交线程被 spinning worker 抢占整段调度量子"的形态——与代码注释里 x86 分支的
   `nc − 2` 结论同机理（那是 x86 分支专属实测，**不可外推到 aarch64**，本机需自行实测）。
5. **`--warmup` 不可省**：30B ctx=512 实测，带 `--warmup` 的计时 prefill 为 40.908 / 38.638 s，
   不带为 45.994 s——差约 13%，即冷专家页的建页成本。故全部测点保留逐格 `--warmup`。
6. **线程档核验**：逐格采样 `/proc/<pid>/status` 的 `Threads`，实测等于 T（1/2/4/8/16/32/40/48/56/64），
   排除了"设了但没生效"。`--threads`（HTTP worker）与计算线程池无关，本报告未涉及。

## 7. 诚实边界（引用本报告必须一并引用）

1. **这是 Neoverse-N1 / aarch64 云实例数据，不是 RK3588 板端数据**；绝对数字不跨机器、
   不跨 session 外推。README「性能」章的板端数字**不可与本报告并列或混引**。
2. **RK3588 的"`--threads 8` 比 4 慢 1.8~2.5 倍"是 big.LITTLE 特异性结论**（t8 会把 4 个 A55
   小核拉进 GEMM 并行区），**不可作为本机预期**：本机同构 64 核，decode 最优平台在 32~40 核，
   t64 才退化（8B −42%、30B −19%）。反过来，本报告的 t32/t40 结论同样**不可外推到板端**。
3. **无 governor / 温度**：虚拟化实例不暴露 cpufreq 与 thermal，故无法记录降频证据；
   `steal_ticks = 0` 是唯一可得的"未被宿主抢占"证据。`load average` 在 30B 批次里高达 20~27，
   已核实**是引擎自身 spin 工作线程计入 runnable**，且全程 `D` 状态进程数为 0、无第二个引擎实例。
4. **口径为热页缓存**；冷页缓存（首次从盘读 6.15 GB / 17.67 GB）不在本报告范围内。
5. **ctx 与板端测点不同**（本报告 8B=512、30B=256/4096；README §1 用默认短 prompt）。同一批内
   全部臂同 ctx，故"加速比 / 档位比值"不受影响；但**跨模型的绝对时间不可直接比**。
6. **只测单请求串行**（`--stream-test` 骨架），**不含并发服务**；服务工作线程 `--threads` 与计算
   线程池无关。并发吞吐场景需另测。
7. **不做位级一致对拍于跨轨**：`full` / `stream` 两档 TOKIDS 逐位相同（已验）；`sparse` 是近似轨，
   与精确轨 9/32 位不同，**要求位级一致的场合不得使用 sparse 档**。
8. **稀疏的结论限于"本机 + 本上下文（ctx=4096）"**：§5 的 4.5% 是"稀疏 vs 本版稠密"，
   与"稀疏 vs llama.cpp"（README §7 口径）不是同一件事。VQF 头 `max_seq=8192` 决定了本机
   无法把上下文推到让注意力成为瓶颈的档位（需改 4 字节元数据，工具见
   `tools/bench/patch_vqf_max_seq.py`）。
9. **逐层的 decode 固定开销（约 283 ms/token）依赖本机内存层级**：本机权重全在页缓存里，
   该数是纯"重缺页 / 重建页表"成本；若权重在慢介质上，还要叠加真实 I/O 时间。
10. **8B 的首选档是 `--threads 4`（板端）这一点不适用于本机**：本机 `--threads` 与计算并行无关，
    本机最优是 `OMP_NUM_THREADS/VLLM_THREADS = 32~40`。

## 8. 结论速览

| 问题 | 结论（本机 / 本次 boot 会话内 / 热缓存 / 单请求串行） |
|---|---|
| 多线程对 8B 有加成吗 | 有，且近线性到 t32：decode **17.19×**、prefill **28.97×**（t64）；decode 在 t32~t56 平台、t64 崩 42% |
| 多线程对 30B-A3B（MoE）有加成吗 | 有，但 decode 只到 **8.65×** 就饱和（t32）；prefill 仍到 **29.26×**（t64）。MoE 的 decode 并行效率显著低于稠密模型 |
| 32 核是不是最优解 | **是（更准确说是 32~40）**：30B decode 在 t32/t40 完全并列最优（109.5 ms），t48/t56 缓降、t64 +19%；**t40 因 prefill 更好而略优** |
| 引擎默认线程数在本机是多少 | **64（全核）**——恰好是 decode 最差档（8B 61.5 ms vs 平台 35~36；30B 130.5 vs 109.5） |
| 全层 vs 逐层 | 内存 **13.6 GB → 486~556 MB（24~28×）**、prefill 仅慢 1~7%、**decode 慢 3.35~3.63×**；代价是**固定约 283 ms/token 的重建页映射**，机器越快相对越亏 |
| 开稀疏注意力/稀疏解码有用吗 | 在本机本上下文**几乎无用**：decode 仅 **+4.5%**、prefill **−2.2%**。原因是 30B decode 是专家权重受限而非注意力受限（注意力仅占 18%） |
| 语义是否受线程数影响 | **不受**：同档位内所有线程数 TOKIDS 逐位相同（G0 全 PASS）；逐层与全层也逐位相同 |
